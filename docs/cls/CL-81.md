# CL 81: validate upstreams at config time (ROADMAP #28)

## Description

A malformed upstream was accepted in silence. `Validate()` checked only
`block_mode`, `log_queries`, and `query_privacy`, so a bad upstream (a missing
`:53`, a typo, any non-`host:port` string) passed `Load`, `Validate`, and
`-check-config`, and the service started. The failure surfaced only at runtime,
per query: `exchange` errored on the bad address, the entry was marked failed,
and if every upstream was malformed the client got SERVFAIL while the handler
logged `upstream forward failed` on every query.

This CL makes the misconfiguration loud at config time. `config.Load` drops any
upstream that is not `host:port` (with a WARN), and `config.Validate` fails when
nothing can forward and notes when there is no fallback.

## Motivation

This is the same silent-misconfig class the empty-blocklist alarm (CL 29) and
the admin bind-failure banner (b/052) exist to make loud, from the config side.
`-check-config` (CL 66) already promises that a config the installer accepts is
one the service will start on; a config that cannot forward at all slipped
through that promise. Catching it at the same gate closes the gap on the path
the #1 hardware deploy depends on.

## What it does

- **`internal/config/config.go`**:
  - New `filterUpstreams([]string) (valid, dropped []string)` helper. An entry
    is valid only if `net.SplitHostPort` succeeds and both host and port are
    non-empty, so `1.1.1.1` (no port), `:53` (no host), and `1.1.1.1:` (no
    port) are all dropped. Order is preserved. It mirrors `filterWhitelist` and
    `filterClientNames`.
  - `Load` calls it after `applyDefaults`/`applyEnvOverrides` and WARNs each
    dropped entry, so the DNS handler only ever receives `host:port` upstreams.
  - `Validate` gains two branches on the (already filtered) list length: `0`
    returns a fatal error (every configured upstream was malformed), and `1`
    logs an INFO note that there is no forwarding fallback.

## Design decisions

- **Shape check, not reachability.** `net.SplitHostPort` proves the string is
  `host:port`, not that the host is a real or reachable resolver. The check
  resolves no name and dials nothing, so it adds no network call and no new
  attack surface. Active detection of a fallback resolver was rejected in the
  ROADMAP, not deferred: any probe of an operator-supplied address, wired to the
  unauthenticated admin API, would be an SSRF and LAN-scanning primitive. A
  well-formed but dead or typo'd address stays a runtime concern that the
  upstream cooldown tracker already handles.
- **Drop the bad entry, do not keep it.** A malformed upstream is removed from
  the pool (with a WARN) rather than left to fail one dial per query. This
  matches the whitelist and `client_names` loaders, which also drop and warn to
  keep DNS up when one entry is a typo.
- **Split across Load and Validate.** `applyDefaults` seeds the two default
  upstreams before the filter runs, so a genuinely absent list holds two valid
  entries at `Validate` time. An empty list there can only mean every configured
  upstream was malformed, which lets the fatal check be a simple length test
  next to the other fatal enum checks, with the input-cleaning WARN kept in
  `Load` where the whitelist and `client_names` cleaning already lives.
- **INFO, not WARN, for the single-upstream note.** A single upstream (a
  deliberate LAN Unbound, for example) is a valid setup, not a misconfiguration.
  WARN would cry wolf on every startup and reload for that operator and train
  them to ignore the WARN channel; the note is informational about a resilience
  tradeoff, so INFO is the honest level. It is never fatal.
