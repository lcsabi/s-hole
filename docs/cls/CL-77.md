# CL 77: Failed-query visibility (per-query outcome)

## Description

Record a per-query outcome and surface failures in the three places the query
pipeline already feeds: the query-volume graph, the recent-query filter, and
`/metrics`. The query log gains an `rcode` and a `synthesized` column; the graph
draws two failure lines (unresolved and upstream error); the recent-query filter
gains two matching segments and a per-row status badge; the flat log marks a
failed query with a trailing ` FAILED` token; and `/metrics` gains three failure
counters. Implements ROADMAP #31.

## Motivation

s-hole classified each query only as blocked or allowed. A query that got
SERVFAIL was logged as an ordinary allowed row, indistinguishable from one that
resolved, so an operator could not answer "is my sinkhole holding up, and which
queries failed?" from the app. The only signal was the `upstream forward failed`
WARN in the service log.

Two failure kinds must stay distinct, because both reach the client as SERVFAIL
and cannot be told apart by rcode alone:

- **Unresolved.** `forward` returned an error (every upstream failed at the
  transport level, or the deadline hit) and the handler answered with
  `dns.HandleFailed`. The "does the app hold up" signal, and the operator's to fix.
- **Upstream error.** A live upstream returned a valid DNS message whose rcode is
  a failure (SERVFAIL or REFUSED), and s-hole relayed it verbatim. Usually not
  s-hole's fault, so collapsing it into the first kind would make the graph lie.

NXDOMAIN is a valid answer, not a failure, and stays on the allowed side.

This reuses the CL 76 machinery (the `Record` struct and the `ensureColumn`
migration), as the observability-group note in ROADMAP planned.

## What it does

- **querylog (`internal/querylog/logger.go`)**: `Record` gains `Rcode int` and
  `Synthesized bool`. `Synthesized` is true when s-hole built the reply itself (a
  block, a local PTR answer, or a synthesized SERVFAIL) and false when it relayed
  an upstream or cached message. Three helpers derive the operator-facing outcome
  from the pair: `Unresolved` (`synthesized && rcode==SERVFAIL`), `UpstreamError`
  (`!synthesized && rcode in {SERVFAIL, REFUSED}`), and `Failed` (either). Local
  `rcodeServerFailure`/`rcodeRefused` constants keep the package free of a
  miekg/dns import. `FileLogger` appends ` FAILED` to an ALLOW line for a failure
  (mutually exclusive with ` CACHED`).
- **querylog (`internal/querylog/db.go`)**: the `queries` table gains `rcode` and
  `synthesized` columns (`INTEGER NOT NULL DEFAULT 0`). `migrate` adds each with an
  idempotent `ensureColumn` call. The `entry` struct and the batched INSERT carry
  both. `History` sums the two failure kinds per bucket with a `CASE` (rcode 2, or
  2/5, gated on `synthesized`), filling new `Bucket.Unresolved`/`UpstreamError`
  fields. `QueryFilter` gains an `Outcome` field; `Search` adds the matching WHERE
  clause and selects the two columns; `QueryRow` and `scanRows` carry them.
- **handler (`internal/dnsserver/handler.go`)**: each per-outcome log call now sets
  `Rcode`/`Synthesized` (the block reply's rcode from `blockMode`, the local-PTR
  NXDOMAIN, the cached reply's rcode). The forward-path log call moved from before
  `forward` to after it, so the outcome is known when the row is written: a forward
  error logs a synthesized SERVFAIL and bumps `RecordForwardFailure`; a relayed
  SERVFAIL/REFUSED logs the relayed rcode and bumps `RecordUpstreamError`. The query
  is still always logged in both branches, so the move loses no row.
- **stats (`internal/stats/stats.go`)**: two counters, `forwardFailures` and
  `upstreamErrors`, with `RecordForwardFailure`/`RecordUpstreamError` and
  `Summary.ForwardFailures`/`UpstreamErrors`. Both are bumped after `RecordQuery`,
  so `Snapshot` reads them before `total` (LOAD-ORDER INVARIANT).
- **dnsserver (`internal/dnsserver/upstream.go`)**: `upstreamTracker` gains a
  cumulative per-upstream `failures` map, bumped in `recordFailure` (a success does
  not reset it). `FailureCounts` and the package-level `UpstreamFailures` expose it.
- **api (`internal/api`)**: `parseQueryFilter` reads `?outcome=`. `handleMetrics`
  emits `shole_forward_failures_total`, `shole_upstream_errors_total`, and, when the
  accessor is wired, per-upstream `shole_upstream_failures_total{upstream}`. A new
  `Server.SetUpstreamFailures` setter takes the accessor; `main` wires
  `dnsserver.UpstreamFailures` (api does not import dnsserver, so main bridges them).
- **Dashboard (`internal/api/static/index.html`)**: amber `--amber` and orange
  `--orange` line colors, two legend entries, two `drawSeries` calls (drawn under
  `all`, scaled to the total max, hidden with total/cached under `blocked`), and two
  tooltip lines. The status filter gains "Unresolved" and "Upstream error" segments
  mapping to `?outcome=`, and the recent-query rows render UNRESOLVED/UPSTREAM ERR
  badges.

## Design decisions

- **rcode + synthesized flag, not a single outcome enum.** The rcode is richer for
  a future per-rcode breakdown, and the synthesized bit is exactly the "did s-hole
  make this reply or relay it" distinction the two failure kinds need. It is two
  columns and two `ensureColumn` calls rather than the one the ROADMAP sketched; the
  helper handles each independently.
- **Graph and filter split the two failure kinds; the flat log does not.** The
  graph draws two lines and the filter offers two segments, so an operator sees
  which kind is spiking. The flat log keeps a single ` FAILED` marker for a quick
  tail; the split lives in the richer surfaces and the two `/metrics` counters.
- **The forward log call moved to after `forward`.** CL 76 logged before the
  forward so a failed query was still logged. This CL needs the outcome, which is
  known only after the forward, and it logs in both branches, so the row is still
  always written, now with the correct outcome.
- **Failure colors are amber and orange, not red.** Red means blocked in this UI.
  Amber/orange read as trouble without a collision, and each failure line is a
  subset of the forwarded remainder, so both scale under the total envelope.
- **Two aggregate counters in `stats`, the per-upstream counter in the tracker.**
  The process-wide counts are subsets of `total` and belong with the other
  per-query counters (same load-order rule and `*NeverExceeds*UnderLoad` tests). The
  "which upstream is flaky" attribution belongs with the cooldown tracker, keyed by
  the upstream address, which the query log cannot give (forward aggregates several
  upstreams into one generic error). `shole_upstream_errors_total` (relayed rcodes)
  and `shole_upstream_failures_total` (per-upstream transport failures) are distinct;
  their sums differ, and the HELP text says so.
- **Forward-only.** Rows written before the upgrade take `rcode=0, synthesized=0`
  and read as not-failed, so the failure lines under-report for earlier buckets,
  matching the forward-only behavior of CL 72 (privacy) and CL 76 (cache-hit).
- **No new index.** `History` sums with a `CASE` over the existing `ts` range and
  the filter is `LIMIT`-bounded; a new index would slow every INSERT on the
  single-connection pool (b/038) for no read gain, the same shape decision as CL 74
  and CL 76.

## Hot-path cost

None beyond forwarding values the handler already computes. The outcome is decided
on the serving path (the handler already branches on blocked, cache hit, local PTR,
and the forward result), so this sets two fields on the value-struct `Record` and
bumps one atomic counter. `BenchmarkHandler_ServeDNS` shows no allocation or latency
regression (Blocked 5 allocs/264 B, Cached 7 allocs/304 B, unchanged). The two
columns, the batched INSERT, and the `SUM(CASE ...)` aggregate live off the hot path.
Storage grows by about two bytes per row on a retention-bounded table.

## Testing

- `make check` clean (fmt, vet, lint, lint-sh, test); `-race` clean on `querylog`,
  `dnsserver`, `api`, and `stats`.
- Coverage floors held: `querylog` 86.2%, `dnsserver` 88.2%, `api` 92.8%, `stats`
  100% (all at or above their floors).
- `TestServeDNS_LogsOutcome` drives the three forward outcomes (ok, unresolved via
  unreachable upstreams, upstream error via a mock upstream that relays
  SERVFAIL/REFUSED) and asserts the logged `Record` and the matching counter.
  `TestDBLogger_OutcomeRoundTrip` drives the full write path for each outcome and
  asserts the `History` sums. `TestMigrate_AddsOutcomeColumns` proves the two
  columns are added to a pre-CL77 database, existing rows read 0/0, and a second
  migrate is a no-op. The two `stats` race tests hold each failure counter at or
  below `total` under parallel writers. `BenchmarkHandler_ServeDNS` shows no
  regression.
- Manual smoke: ran the binary with `query_db` and `log_file` set, `S_HOLE_LISTEN=:5353`.
  Pointed one upstream at an unreachable address and drove a query (client got
  SERVFAIL; the flat log wrote `ALLOW ... FAILED`; `/api/history` reported
  `unresolved: 1`; `shole_forward_failures_total` and the per-upstream
  `shole_upstream_failures_total` incremented). Drove a query against a resolver that
  answers SERVFAIL and confirmed `upstream_error: 1`, the relayed rcode, and
  `shole_upstream_errors_total`. `/api/queries?outcome=unresolved` and
  `?outcome=upstream-error` each narrowed the set. The live browser rendering of the
  two lines and the badges was not driven headless; the data side it consumes was
  checked over the API, as CL 74 and CL 76 did.
