# CL 74: query-log search / filter

## Description

Add filters to the recent-query log. `GET /api/queries` gains `?domain=`
(substring), `?client=` (exact), and `?blocked=true|false` parameters, and the
dashboard Recent Queries panel gains matching controls. The filter runs in SQL over
the stored columns, so it can only match what the privacy mode (CL 72) wrote.
Implements ROADMAP #23.

## Motivation

The recent-query panel streamed the last rows but could not answer a question about
them, so false-positive triage was a scroll. A filter turns triage into a query.
The feature inherits the CL 72 privacy guarantee for free: the filter reads the
stored client value, which is masked once at write time, so a filter can never
reach behind the mask. This is the forcing function that validates the CL 72
placement: a read-time mask would let search (and the future #24 export) undo the
privacy setting.

## What it does

- **querylog (`internal/querylog/db.go`)**: a new `QueryFilter` (domain substring,
  exact client, optional blocked flag) and `Search` method. `Search` builds the
  WHERE clause dynamically from the non-empty fields, binds every value as a
  parameter (no caller input reaches the SQL text), and orders newest-first under
  the same `LIMIT`. `Recent` now delegates to `Search` with an empty filter, so the
  two share one query builder. `escapeLike` escapes the LIKE metacharacters
  (`\`, `%`, `_`) so a typed wildcard is literal, and the domain term is lowercased
  to match the lowercase-stored domains. This is the package's first dynamic
  multi-clause WHERE.
- **API (`internal/api/api.go`)**: `parseQueryFilter` reads the three parameters
  (`domain` and `client` trimmed, `blocked` accepting only `true`/`false`), and
  `handleQueries` calls `Search`. The `?limit=` clamp, the `s.db == nil` empty
  response, and the CL 73 label-attach loop are unchanged. The package-doc route
  line records the new parameters.
- **Dashboard (`internal/api/static/index.html`)**: the Recent Queries header gains
  a domain input (debounced), an All/Blocked/Allowed segmented toggle, and a client
  picker seeded from the Top Clients list. The filter state persists in
  `localStorage` under `shole.queryFilter`. An active-filter row with a "Clear
  filters" button shows while a filter is set. The row is tinted and its
  "Filtering: …" summary is accent-colored and semibold, so an active filter
  stands out from the neutral panel caps (accent, not red, which means "blocked"
  in this UI). The empty state reads "No queries match the filter" (distinct from
  the db-off message). The page header shows the active `query_privacy` mode at all
  times.

## Interaction with `query_privacy` (CL 72)

The filter reads `client_ip` from the row, which CL 72 masked once at write time, so
the filter matches only the stored, already-masked value:

| `query_privacy` | stored client | client filter | client control |
|---|---|---|---|
| `raw` | full IP | exact match, per-device | shown |
| `subnet` | network address | exact match on the whole masked segment | shown |
| `drop` | empty | meaningless (matches all-empty) | hidden |

The domain and status filters touch no client field, so they are always available.
The `drop`-hides-the-control rule is the one the UI can detect from the mode on
`/api/stats`. The "flat `/24` collapses to one subnet" case is not UI-detectable (no
LAN-topology knowledge) and stays a documentation caveat, as CL 72/73 did.

## Design decisions

- **Substring domain, exact client, no CIDR.** Substring domain is the useful
  default for "show me everything under this tracker". The client filter is an exact
  match on the stored (masked) value. CIDR was rejected: SQLite has no inet
  functions, so CIDR containment would force fetch-then-filter in Go and break the
  "`LIMIT` bounds the scan" property. The client is surfaced as a picker seeded from
  Top Clients, so only an existing value can be chosen and the exact match never
  reads as "typed a prefix, got nothing".
- **One query builder.** `Recent` delegates to `Search`, so the filtered and
  unfiltered reads cannot drift and the `waitForRows` test helper is unchanged.
- **No new index.** `blocked`/`domain` are already indexed, a leading-wildcard LIKE
  cannot use a b-tree index anyway, and a new `client_ip` index would slow every
  INSERT on the single-connection pool (b/038) to speed a read that, on a
  retention-bounded home table bounded further by `LIMIT`, does not need it. This is
  a shape decision, not a measured one; the trigger to revisit is a real deployment
  with slow filtered reads.
- **Filter state persists, made safe by a visible indicator.** A stale filter that
  silently hides the stream on reload would be a foot-gun, so the always-visible
  active-filter row, the Clear button, and the distinct "no match" empty state make
  a restored filter impossible to mistake for a broken log. On load the client
  filter is reconciled against the mode: it is cleared under `drop`; otherwise it is
  kept and shown in the picker even when it is not in the current Top Clients list,
  so a filter for a less-chatty device survives.
- **Privacy mode always visible.** A compact header badge reads the active mode from
  `/api/stats`. It complements the Top Clients captions (which keep their
  mode-specific explanation), is never hidden by a collapsed panel, shows under `raw`
  too, and makes the client-picker gating self-explanatory.

## Security considerations

No new endpoint and no new stored data: the filters are parsed from the existing
`/api/queries` request and every value is bound as a SQL parameter, so no caller
input reaches the SQL text. The filter cannot expose more than the active
`query_privacy` mode already stores, because it reads the masked column. The
mitigation is the existing one: keep `api_listen` on localhost or a trusted LAN.

## Testing

- `make check` clean.
- `TestDBLogger_Search` covers each filter dimension, combinations, LIKE-metachar
  escaping (an underscore matches literally), case-insensitivity, and the
  zero-filter equals `Recent` equivalence.
- `TestParseQueryFilter` covers trimming, the `blocked` true/false/garbage parse,
  and combined parameters. `TestQueriesEndpoint_Filtered` drives the filters
  end-to-end through a real DBLogger.
- `TestHandleQueries_AttachesClientLabels` now also asserts a label attaches on a
  filtered fetch.
- Manual smoke: ran the binary with `query_db` on, drove mixed allow/block traffic,
  and exercised `?domain=`, `?client=`, and `?blocked=true|false` on `/api/queries`;
  each narrowed the set and combined parameters AND together, a substring domain
  matched case-insensitively, and a non-matching term returned zero rows. Repeated
  under `query_privacy` `raw`/`subnet`/`drop`: `/api/stats` echoed the active mode,
  the stored client value was the full IP under `raw`, the `/24` network address
  under `subnet`, and empty under `drop`, so the exact-match client filter keys on
  exactly what is stored. Confirmed the dashboard is served with the new controls
  and JS wired (`qf-domain`, `qf-status`, `qf-client`, the active-filter row, the
  Clear button, and the `privacy-mode` badge). The live browser interaction (clicks,
  the persisted-filter reload, the picker show/hide) was not driven headless; the API
  side it consumes was checked, as CL 73 checked its `label` field over the API.
