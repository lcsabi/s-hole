# CL 102: DNS server limits and DoT TLS 1.3

## Description

Four hardening changes to the DNS listeners and the DoH upstream client:

- At most 512 queries wait for an upstream at the same time. A query over
  this limit gets SERVFAIL at once, counts as unresolved, and counts in the
  new metric `shole_forward_limited_total`.
- The plain-TCP listener caps open connections at 256 with the limiter that
  DoT uses, and sets the same read and idle timeouts as DoT.
- The DoT listener accepts TLS 1.3 only.
- The DoH client follows no redirect (b/102). A DoH upstream that answers
  with a redirect is a failed attempt, and s-hole tries the next upstream.

Review findings: SEC-12, PRIV-12, SEC-21 (b/102). Target release: v2.1.0.

## Motivation

- **SEC-12.** miekg/dns runs one goroutine per query, with no cap. A cache
  miss can wait up to 10 s for the upstreams, so one LAN device that sends
  many unique names could hold thousands of goroutines, sockets, and upstream
  connections. The plain-TCP listener had no connection cap (only DoT had
  one), so one device could also open idle TCP connections until s-hole ran
  out of file descriptors.
- **PRIV-12.** DoT accepted TLS 1.2. In TLS 1.2, a resumed session sends its
  session ticket in clear text, so a passive observer on the LAN can link the
  DoT connections of one device. TLS 1.3 encrypts the ticket.
- **SEC-21 (b/102).** `dohClient` used Go's default redirect policy: up to 10
  redirects, with no check of the scheme or the host. On a 307 or 308, Go
  sent the POST again, with the DNS query in its body, to the `Location` URL;
  on a 301, 302, or 303 it connected to the new host with a GET. A redirect
  to `http://` sent the queried name in clear text, and the plaintext
  fallback count did not see it. A redirect to another host sent the query to
  a host that is not in the config.

## What it does

- **Forward limit** (`internal/dnsserver/handler.go`): `Handler.forwardSlots`
  is a buffered channel with `maxForwards` (512) slots. `ServeDNS` takes a
  slot before `forward` and frees it after. When no slot is free, it does not
  wait: the query gets SERVFAIL, `forwardLimited` (exported as
  `ForwardLimited`) goes up, and the query goes the same way as one that
  every upstream failed: `RecordForwardFailure`, a synthesized SERVFAIL row
  in the query log, and the failure summary. A blocked, cached, or local
  answer takes no slot.
- **Failure summary** (`internal/dnsserver/failures.go`): a forward-limit
  failure adds the cause `forward limit: too many queries were waiting for an
  upstream`, and the hint says that the limit was reached. The line still
  names no domain and no client.
- **Metric** (`internal/api/api.go`, `metrics.go`, `cmd/s-hole/main.go`):
  `SetForwardLimited` wires `dnsserver.ForwardLimited` to
  `shole_forward_limited_total`, a counter with no labels.
- **TCP connection cap** (`internal/dnsserver/server.go`): `Listen` wraps the
  TCP listener in `newLimitListener(ln, maxTCPConns)` (256). When the cap is
  reached, a new connection waits in the kernel's accept queue. The plain-TCP
  server sets `ReadTimeout` and `IdleTimeout` explicitly, like DoT, so a
  change of the miekg/dns defaults cannot remove the bound. The two shared
  constants are now `tcpReadTimeout` and `tcpIdleTimeout`.
- **TLS 1.3** (`internal/dnsserver/dot.go`): `ListenDoT` sets
  `MinVersion: tls.VersionTLS13`.
- **No DoH redirect** (`internal/dnsserver/upstream.go`): `dohClient` has
  `CheckRedirect: refuseRedirect`, which returns `errDoHRedirect` for every
  redirect. The redirected request is not sent. The error (not
  `http.ErrUseLastResponse`) makes the attempt fail like a transport error,
  so `forwardWith` records the failure in the cooldown tracker and in
  `shole_upstream_transport_failures_total`, and tries the next upstream.
  The cause in the failure summary is `DoH request to <redacted URL>:
  redirect refused`; it names no query and not the redirect target.

## Design decisions

- **Global caps only.** Decided with the maintainer: no rate limit for each
  client. A token bucket for each client would keep raw client addresses in
  memory, which the first design rule does not allow without a need.
  Revisit it only if a real deployment needs it (ROADMAP #44).
- **SERVFAIL at once, no queue.** A query over the forward limit does not
  wait for a slot. A queue would hold the goroutine that the limit is there
  to bound, and a client retries a SERVFAIL on its own.
- **A limited query is unresolved.** It counts in
  `shole_forward_failures_total` and gets a synthesized SERVFAIL row in the
  query log, like a query that every upstream failed. So the counter
  relations hold (`total = blocked + local + cached + forwarded`), and the
  dashboard's unresolved count and the `?outcome=unresolved` filter show it.
  `shole_forward_limited_total` is a subset that tells the two causes apart.
- **512 forwards, 256 TCP connections.** A home LAN rarely has more than a
  few dozen forwards in flight. A client uses plain TCP only after a
  truncated UDP reply and closes the connection after the answer. Both are
  constants, like `maxDoTConns`.
- **TLS 1.3 only, not TLS 1.2 without session tickets.** Decided with the
  maintainer: Android 9 Private DNS no longer works with s-hole's DoT.
  Android 10 and later, iOS 14 and later, and current stub resolvers support
  TLS 1.3. In Automatic mode an Android 9 phone sends plain DNS instead.
- **Refuse every DoH redirect.** RFC 8484 does not need redirects, and
  s-hole requires an IP-literal DoH URL. Following only HTTPS redirects to
  the same host would add a policy to audit for no known use.

## Privacy impact

- **Collects:** nothing new. The new metric is one aggregate counter with no
  label.
- **Sends:** less. A DoH upstream can no longer send a query to another host
  or over plain HTTP with a redirect.
- **Log:** the failure summary can have two new causes (`forward limit`, and
  `redirect refused` with the redacted upstream URL). Neither names a domain
  or a client.
- **Who can read:** DoT connections of one device can no longer be linked by
  a passive observer through the TLS 1.2 session ticket.
- **No per-client state:** the limits hold no client address.

## Testing

A separate sub-agent wrote the tests from the requirements, without the
diff. It listed its cases first, then wrote:

- `internal/dnsserver/admission_test.go`: with 512 forwards held by a UDP
  upstream that does not answer yet, query 513 gets SERVFAIL in under 1 s
  and is not forwarded; `ForwardLimited` rises by 1, the query counts as a
  forward failure, and the query log gets one synthesized SERVFAIL row; a
  blocked, cached, local PTR, localhost, and `.onion` query is answered
  while the limit is full; after the release, the held queries and a new
  one are answered. The summary has one line with the `forward limit` cause
  and a hint that names 512, and the log holds no domain, client address,
  or port. A mixed interval keeps both causes, and the next interval resets
  the limit flag. 552 failed and 552 successful forwards in a row never reach
  the limit (each slot is freed). 256 plain-TCP connections get answers,
  connection 257 waits, and it is answered when one connection closes.
- `internal/dnsserver/dot_test.go`: a TLS 1.2-only client fails with a
  protocol version error; a TLS 1.3 client and a client that offers 1.2 and
  1.3 both negotiate TLS 1.3 and get an answer.
- `internal/dnsserver/redirect_test.go` (b/102): 301, 302, 303, 307, and 308
  to an HTTP and to an HTTPS target are each a failed attempt; the next
  upstream answers, the target gets no request, the tracker counts one
  transport failure, and the upstream is in cooldown. The 3xx body (a valid
  DNS answer) is not used. Through `ServeDNS`, the failure counts in
  `UpstreamTransportFailures`. With user info and a token in the upstream
  URL, the summary shows the redacted URL, and the log holds no query name,
  credentials, redirect target, or client address. The tests swap only
  `dohClient.Transport`, so the production redirect policy is under test.
- `internal/api/forwardlimit_test.go`: `shole_forward_limited_total` is
  absent until the accessor is set; then it is a counter with the
  accessor's value and no label.

Mutation testing by the sub-agent: each mutation was caught (a blocking slot
acquire, a slot not freed, no count, the query treated as answered, other
limit sizes, each hint case, the flag not reset, the TCP limiter removed or
resized, TLS 1.2 as the floor, no `CheckRedirect`, a labeled metric, a gauge
type). One equivalent mutation survived: `refuseRedirect` returning
`http.ErrUseLastResponse`. The status check then rejects the 3xx, and no
request reaches the target, so no test can tell the two apart. The rule to
return an error is kept by the code comment and review.

`make check` passes. The new tests pass under `-race` and with `-count=5`.
Per-package coverage meets the floors (`dnsserver` 96.5%, `api` 94.1%).

Live check on the Debian 13 VM (amd64), as a plain user on high ports:

- `dig +tls` to the DoT port gets an answer; `openssl s_client -tls1_2` fails
  with `alert protocol version`; `openssl s_client -tls1_3` negotiates
  TLS 1.3.
- 400 idle TCP connections to the plain port: s-hole holds 256 of them.
- 700 unique queries in under 1 s, with one upstream that receives and does
  not answer: 512 were forwarded and 188 got SERVFAIL at once.
  `shole_forward_limited_total` was 188, and the summary line had the
  `forward limit` cause and the limit hint, with no domain or client.
- All s-hole files and processes were removed from the VM afterwards.

Android check on Bliss OS 16.9.7 (Android 13, VirtualBox, bridged on the
LAN), with Private DNS in the default Automatic mode. This build ran as root
on the Debian VM on ports 53 and 853 with a self-signed certificate. A
temporary `iptables` DNAT rule on the Android VM (over `adb root`) sent its
port 53 and 853 traffic for the router to s-hole, in place of a DHCP change.

- `dumpsys connectivity`: `UsePrivateDns: true`, with the server in
  `ValidatedPrivateDnsAddresses`. s-hole logged Android's DoT probe
  (`...-dnsotls-ds.metric.gstatic.com`).
- A `tcpdump` capture of port 853 on the Debian VM: two connections from the
  Android VM, and both ServerHellos carry `supported_versions` TLS 1.3.
- App lookups (`ping`) went over port 853 at the time of the lookups:
  `doubleclick.net` got `BLOCK` and `0.0.0.0`, and other names were
  answered.
- Afterwards, the DNAT rules were removed, Private DNS was set back to its
  default, and the s-hole files were removed from both VMs.

`systemd-resolved` check on the Debian 13 VM (systemd 257), with s-hole on
