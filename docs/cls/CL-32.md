# CL 32 — Benchmark companions for the hot path

## Description

Adds the two hot-path benchmarks the roadmap deferred until subdomain
blocking landed:

- `BenchmarkCache_Get` (`internal/cache`) — the cache **hit** path, whose
  cost and per-op allocations are dominated by the defensive `msg.Copy` plus
  the `decrementTTLs` walk performed on every hit.
- `BenchmarkHandler_ServeDNS` (`internal/dnsserver`) — two sub-benchmarks
  (`Blocked`, `Cached`) that drive `Handler.ServeDNS` through the existing
  stub `ResponseWriter` (`fakeWriter`) on the two paths the handler can serve
  without touching the network.

Both call `b.ReportAllocs()` so a per-query allocation regression shows up
alongside the ns/op number. They join `BenchmarkStore_IsBlocked` and
`BenchmarkStore_IsBlocked_Miss` (CL 30) to cover the whole in-process hot
path: blocklist decision → cache lookup → request routing.

Roadmap item #8.

## Motivation

`docs/ROADMAP.md` #8 held these two benchmarks open, gated on #3 (subdomain
blocking) so the cache/handler numbers would be measured against the final
lookup semantics rather than the exact-match ones. #3 shipped in CL 30, which
also added the `_Miss` companion for the suffix walk; the cache and handler
were the remaining gaps. Per the roadmap's own rule — "benchmarks nobody
watches are suite weight; these earn their place the day the hot path
changes" — these guard the two most allocation-sensitive hops on every
answered query, so a future change that adds a copy or an allocation to the
cache-hit or sinkhole path is caught by `make bench` (which runs each
benchmark once as a regression smoke) instead of in production on a Pi.

## Design decisions

**Cache: benchmark the hit, not the miss.** The miss path is a bare
`RLock`'d map lookup and an atomic add — no allocation, nothing that can
silently regress. The hit path clones the stored `*dns.Msg` and walks its
sections to decrement TTLs; that is where the cost lives and where
`ReportAllocs` earns its keep. A `_Miss` companion (as `Store` has) would be
noise here, so it is deliberately omitted and the reason is stated in the
benchmark comment.

**Handler: two in-process paths, forwarding excluded.** `ServeDNS` has three
terminal paths — sinkhole (blocked), cache hit, and upstream forward. The
first two are pure handler code and are benchmarked as `b.Run` sub-benchmarks
under one `BenchmarkHandler_ServeDNS`, matching the single name the roadmap
listed. The forwarding path is bounded by the upstream round-trip, not by
handler code, and cannot be measured without standing up a network stub — a
benchmark of a `net.Dial` timeout would measure the stub, not s-hole — so it
is deliberately left out and the omission is documented in the comment.

**Reuse the existing stubs.** The handler benchmark uses the test file's
`fakeWriter`/`fakeClient` and `buildResp` helpers rather than introducing a
benchmark-only harness; the cache benchmark uses `buildResponse`. No
production code changes — this CL is test files and docs only.
