# CL 76: "Cached" line on the query-volume graph

## Description

Record a per-query cache-hit flag and draw it as a third line on the "Queries
over time" graph, next to total and blocked. The query log gains a `cache_hit`
column, `GET /api/history` reports a `cached` count per bucket, and the flat log
file marks a cache hit with a trailing ` CACHED` token on the ALLOW line.
Implements ROADMAP #29.

## Motivation

The query-volume graph (CL 70) drew total and blocked per bucket. The third
per-query outcome an operator cares about, a cache hit, was invisible, because
the query log recorded only `blocked`. The cached line makes caching
effectiveness over the day, and the cache warm-up after a restart, visible; the
cache hit rate reads off the chart as the ratio of the cached line to the total
line, with no second axis.

This is also the lowest-risk vehicle for the write-path refactor the
observability group shares. It introduces the per-query `Record` struct and the
first idempotent `ALTER TABLE ... ADD COLUMN` migration in their simplest form
(one already-counted boolean, no new metric). ROADMAP #31 (failed-query
visibility) then adds one `Outcome` field to the same `Record` and one more
`ensureColumn` call.

## What it does

- **querylog (`internal/querylog/logger.go`)**: a new `Record` struct
  (`ClientIP`, `Domain`, `Blocked`, `CacheHit`) replaces the positional
  `Log(clientIP, domain string, blocked bool)` signature on the `Logger`
  interface, so a new per-query field no longer churns every implementation.
  `Multi` forwards the `Record`. `FileLogger` appends ` CACHED` to an ALLOW line
  when `CacheHit` is set.
- **querylog (`internal/querylog/db.go`)**: the `queries` table gains a
  `cache_hit INTEGER NOT NULL DEFAULT 0` column. A new `migrate`/`ensureColumn`
  pair adds the column to an existing database when it is absent (SQLite has no
  `ADD COLUMN IF NOT EXISTS`, so the ALTER is gated on a `PRAGMA table_info`
  probe); it is a no-op on a freshly created database, which already has the
  column. The `entry` struct and the batched INSERT carry `cache_hit`. `History`
  adds `SUM(cache_hit) AS cached` and fills `Bucket.Cached`; the dense zero-fill
  covers the new field. `Search`/`scanRows`/`QueryRow` are untouched: the
  recent-query list does not show the flag, and they select explicit columns.
- **handler (`internal/dnsserver/handler.go`)**: the `Logger` interface takes a
  `querylog.Record`, so the package now imports `querylog` for the type (no
  import cycle: `querylog` does not import `dnsserver`). The single pre-cache
  `Log` call moved to the point each outcome is decided: the blocked branch logs
  `Blocked: true`, the cache-hit branch logs `CacheHit: true`, and the cache-miss
  path logs a plain forwarded record before `forward`, so a query whose upstream
  later fails is still logged as before. The private-PTR path logs a plain record.
- **Dashboard (`internal/api/static/index.html`)**: a teal `--teal` line color, a
  "Cached" legend entry, the third `drawSeries('cached', ...)` call (drawn only
  under `all`, scaled to the same total max), and a teal `cached` tooltip line.
  Under `log_queries: blocked` the cached line and its legend hide with Total,
  because a cache hit is an allowed query and is never logged in that mode.

## What counts as a hit

A blocked query short-circuits before the cache and a local-PTR answer never
reaches it, so both log `cache_hit=0`. A cache miss that forwards also logs
`cache_hit=0`. So `total = blocked + cached + forwarded`, a clean decomposition
(forwarded is the remainder). The three graph lines do not overlap.

## Design decisions

- **A `Record` struct, not a fourth positional argument.** The next log field
  (ROADMAP #31's outcome) would otherwise churn every `Logger` implementation's
  signature again. The struct absorbs it with a one-field addition.
- **The log call moved to each decided outcome.** The cache-hit result is known
  only after the cache lookup, which runs after the old single `Log` call site.
  Logging per outcome records the flag without a second pass, and it sets up #31,
  which computes the unresolved and upstream-error outcomes on the same paths.
  The cache-miss record is logged before `forward` on purpose, so a forwarded
  query is logged even when the upstream later fails, matching the behavior
  before the move.
- **Text-log format gains a trailing ` CACHED` marker.** A cache hit is worth
  seeing when tailing the flat file. The marker is additive (the leading fields
  are unchanged), appears on ALLOW lines only, and never on BLOCK (a blocked
  query never reaches the cache).
- **No new metric.** The cache hit is already counted
  (`shole_cache_hits_total`), so this is API, UI, and text-log only.
- **Forward-only.** Rows written before the upgrade take the column DEFAULT and
  read as not-cached, so the cached line under-reports for earlier buckets. This
  matches the forward-only behavior CL 72 set for privacy masking.
- **No new index.** `History` sums `cache_hit` over a `ts` range with a
  `GROUP BY` on the bucket key; it never filters on `cache_hit`. A new index would
  slow every INSERT on the single-connection pool (b/038) for no read gain, the
  same shape decision as CL 74.

## Hot-path cost

None beyond forwarding a boolean that already exists. The cache-hit outcome is
computed on the query path (the `cache.Cache.Get` branch) and already counted by
`stats.Counter`. `Record` is a value struct, so it adds no allocation on the
serving goroutine; `BenchmarkHandler_ServeDNS/Cached` is unchanged (7 allocs,
304 B/op). The column, the batched INSERT, and the `SUM` aggregate all live off
the hot path. Storage grows by about one byte per row on a retention-bounded
table.

## Testing

- `make check` clean; `-race` clean on `querylog`, `dnsserver`, and `api`.
- Coverage floors held: `querylog` 86.1%, `api` 92.4%, `dnsserver` 89.7% (all
  >= 85%).
- `TestDBLogger_History` asserts `Cached` per bucket; `TestDBLogger_CacheHitRoundTrip`
  drives the full write path (Log -> channel -> flush) for a cache-hit row;
  `TestMigrate_AddsCacheHitColumn` creates a pre-upgrade database, opens it
  through `NewDBLogger`, and asserts the column is added, an existing row reads
  `cache_hit=0`, and a second migrate is a no-op. `TestServeDNS_LogsCacheHit`
  asserts the cache-hit path logs `CacheHit: true` and the blocked path logs
  `false`. `TestHistoryEndpoint_WithRealDB` asserts the `cached` count end-to-end
  through `/api/history`.
- `BenchmarkHandler_ServeDNS/Cached` shows no allocation or latency regression.
- Manual smoke: ran the binary with `query_db` and `log_file` set, sent the same
  query twice (first a cache miss, then a hit). The flat log wrote
  `ALLOW ... example.com.` then `ALLOW ... example.com. CACHED`, and
  `/api/history` reported `{total: 2, blocked: 0, cached: 1}` in the current
  bucket after the flush. The live browser rendering of the third line was not
  driven headless; the data side it consumes was checked over the API, as CL 74
  checked its fields.
