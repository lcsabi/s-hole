# s-hole: Network-Level DNS Sinkhole

**Authors:** Laszlo (@lcsabi)  
**Created:** 2026-06-23  
**Last Updated:** 2026-10-06  
**Status:** Implementation Complete

---

## Background

Advertising and tracking domains are a persistent source of unwanted traffic on home and small-office networks. Blocking them at the DNS layer, before a connection is even established, is more effective than browser-level filtering, which only protects devices with the extension installed and can be circumvented by per-app DNS-over-HTTPS.

Pi-Hole is the canonical tool for this problem, but it carries significant operational weight: a web stack, a database engine (FTL/dnsmasq fork), and an installer that assumes a Debian-like system. For users who want a lightweight, portable, self-contained binary they can reason about and modify, there is no widely-adopted alternative.

s-hole ("sinkhole") is a minimal DNS sinkhole written in Go. It is designed to be deployed on any always-on machine on the local network, with the router's DHCP server advertising its IP as the DNS resolver for all clients. This gives network-wide ad blocking without per-device configuration and without running software on the router itself.

---

## Goals

- Block DNS queries for domains on community-maintained blocklists before any network connection is made.
- Forward all other queries to configurable upstream resolvers, encrypted by default (DoH to Quad9, then Cloudflare, with plain DNS only as a fallback).
- Cache DNS responses in memory to reduce upstream load and improve latency on embedded hardware.
- Keep the least data the operator asks for. By default record no queries and no client addresses. When the operator opts in, keep a query history in SQLite (and optionally text lines) with a finite retention that erases rows from the file, and a purge that deletes everything at once. Warn loudly about every setting that records more than the default.
- Expose statistics: total queries, block rate, cache hit rate, and, when the query log records them, top blocked domains and top active clients.
- Surface an admin web UI and REST API for observability and runtime allowlist management.
- Ship as a single static binary with a single YAML config file and no runtime dependencies.
- Be auditable: the full codebase should be small enough for a single engineer to read in an afternoon.
- Run efficiently on low-power ARM hardware (Raspberry Pi) with SD card–friendly I/O patterns.

## Non-Goals

- **Serving DNS over HTTPS (DoH) to LAN clients.** LAN clients reach s-hole over plain UDP and TCP on port 53 or, opt-in, over DNS over TLS on port 853 (CL 86; see the DNS Server section). A client-facing DoH endpoint is not built. On a LAN it opens no new network path, because nothing blocks port 853 between a client and its own resolver. It would reach clients that speak DoH but not DoT, such as Windows desktops and browsers, and waits for that demand (`docs/ROADMAP.md` #39). Encrypted *upstream* forwarding is a separate feature (DoH upstream, CL 85).
- **Running on the router.** We assume the router is a commodity device that does not support arbitrary software. Network-wide coverage is achieved by pointing the router's DHCP DNS field at the host running s-hole.
- **DNSSEC validation.** DNSSEC records are passed through transparently; we do not validate or strip them. The cache key holds the query's CD and DO bits, so one client's DNSSEC choice does not decide what another client gets (CL 97, b/096).
- **Per-client policy.** All clients share the same blocklist and allowlist.
- **Admin UI authentication (for now).** The UI is intended for LAN use and has no login. It defends against the browser attacks that need no login (DNS rebinding, cross-site requests; see Admin Interface), binds to localhost by default, and warns while it listens elsewhere. Authentication is reopened as a planned feature, a device-pairing design (`docs/ROADMAP.md`), not as a password form.
- **Negative caching.** NXDOMAIN responses are not cached. Only successful (NOERROR) responses with at least one answer record enter the cache.

### DNS Server (`internal/dnsserver/`)

We use `github.com/miekg/dns` rather than the standard library's `net` package because it provides a complete RFC-compliant DNS message codec, a `ServeMux`-style handler interface, and handles both UDP and TCP transports. Rolling our own DNS codec would be a source of subtle correctness bugs.

Both UDP and TCP listeners are started on the same address:port (default `":53"`, a dual-stack wildcard, so IPv4 and IPv6 clients are served by the same listener; CL 23). DNS clients fall back to TCP automatically when a UDP response is truncated (TC bit set), so both must be active. The forwarder mirrors that fallback on the upstream side: it queries upstreams over UDP first and, when the reply comes back truncated, retries the same upstream over TCP before returning. Without that retry the client's own TCP fallback would dead-end: a TCP query to s-hole would still be forwarded over UDP and yield the same truncated answer. If the TCP retry itself fails or returns a reply that does not match the query (`checkReply`), the truncated UDP reply is passed through (the upstream is demonstrably alive, and TC plus a partial answer beats SERVFAIL); truncated responses are never cached.

`main` binds both sockets itself (`dnsserver.Listen`) right after config validation, next to the DoT bind, and hands them to miekg/dns, which serves them through `ActivateAndServe`. A port conflict (often the `systemd-resolved` stub on port 53) is then a clear startup error (`dns listen failed`). It also lets `Shutdown` close every socket even when it runs before a server has started; when each server bound its own socket inside `Start`, such a server stayed bound and serving (b/063). If a listener fails later, at runtime, `Start` returns the error and `main` runs the ordered shutdown before it exits non-zero, so the query log is flushed and systemd's `Restart=on-failure` restarts the service (b/064). `Listen` wraps the TCP listener in the same connection limiter as DoT (256 open connections, CL 102): when the limit is reached, a new connection waits in the kernel's accept queue until one closes. The plain-TCP server sets the same 2 s first-read and 8 s idle timeouts as DoT, so a silent or idle client cannot hold a slot for long.

An optional DNS-over-TLS listener (RFC 7858; CL 86) serves LAN clients that want an encrypted channel. It is aimed at Android's default Automatic Private DNS mode, which uses DoT on the network's DNS server when it answers and does not check the certificate, so any certificate works and the phone needs no setup. Strict mode (a provider hostname) checks the certificate. Android rejected a user-installed CA in testing, so strict mode needs a publicly trusted certificate for a name the phone can resolve (that route is untested). It is off unless `dns.dot_listen` is set. It is a third `dns.Server` (`Net: "tcp-tls"`) that dispatches to the same handler as the plain listeners, so blocking, the cache, stats, the query log, the LAN-only check, and the `query_log.clients` mask apply unchanged; `remoteIP` still sees the client's `*net.TCPAddr` under the `tls.Conn`. `main` binds the port itself (`dnsserver.ListenDoT`) right after config validation, before anything else opens, and hands the pre-bound listener to miekg/dns, which serves it through `ActivateAndServe`. A bind or certificate failure is fatal. The admin UI fails open because it is not the DNS service, but an enabled DoT listener that did not come up would silently cut off the clients that depend on it. Under the TLS layer, a small limiter caps open connections at 256 (a constant, not a knob). The DoT server's 2 s read timeout for the first read also bounds the TLS handshake, which runs inside that read, and its 8 s idle timeout and 128-query cap bound each connection. TLS 1.3 is the floor (CL 102): in TLS 1.2, a resumed session sends its session ticket in clear text, so a passive observer on the LAN could link the DoT connections of one device. Android 10 and later support TLS 1.3; Android 9 Private DNS cannot use s-hole's DoT. The operator supplies the certificate (`dns.dot_cert`, `dns.dot_key`). Only the operator knows the hostname clients connect with (the SAN) and can make clients trust the issuer, and a public CA cannot issue for a private name, so s-hole generates nothing. The certificate is served through `tls.Config.GetCertificate` from an atomic pointer (`dnsserver.CertReloader`). The single-flight reload path swaps it, so a renewal reaches new connections without a restart; open connections keep the old certificate until they reconnect, and a reload whose files do not load keeps the current certificate. s-hole logs a WARN at startup and on each reload when the certificate has expired or expires within 14 days. Android Automatic mode was tested on an Android 13 VM (Bliss OS), and Android strict mode rejected a user-installed CA; `docs/ROADMAP.md` #36 records the results and the routes that are still untested.

The `Handler` struct is the core routing point. For each query:

0. Refuse a query from outside the LAN (`lan.go`, CL 93, b/080). Loopback, private IPv4, link-local, and IPv6 unique-local sources are answered, and so is any source inside an IPv6 subnet of one of the host's interfaces (a global IPv6 address counts as its /64, the size of an IPv6 LAN). An IPv4 interface subnet counts only inside the private ranges (CL 101): a public or shared (CGNAT, 100.64/10) IPv4 subnet usually faces the internet provider or a VPN, so it is not admitted, and `refresh` logs a WARN that names it at startup and at the first read after it appears. Anything else gets REFUSED before it touches the stats, the cache, or the query log; only `shole_refused_total` counts it. A source that `remoteIP` cannot read is refused too, so the check fails closed (b/100). The interface subnets are read again on a miss, at most every 30 s, so a renumbered IPv6 prefix needs no restart. When the read fails (a sandbox without `AF_NETLINK`), the last good list stays and `refresh` logs a WARN at most once an hour. There is no setting to widen the rule: an open resolver would let strangers use s-hole, put their queries in the household's statistics, and probe the cache. A query without exactly one question gets SERVFAIL and one with an opcode other than QUERY gets NOTIMP. A LAN query with RD=0 gets REFUSED (CL 97): it reads only the cache, so a device could read the cache without adding to it, and the remaining TTL of a cached answer tells when another device looked the name up. Unbound refuses it by default, and stub resolvers always set RD. None of these three replies touches the stats, the cache, or the query log.
1. Extract the question's domain name, lowercased (b/082: a dns-0x20 forwarder randomizes the case, which split one domain across Top Blocked rows; the reply still echoes the name as sent), and the client IP. The client IP is then masked once, per `query_log.clients` (`querylog.MaskClientIP`), at this single write-time choke point (`full` keeps it, `drop` stores nothing, `subnet` masks to IPv4 /24 or IPv6 /64; an unknown or empty mode drops it, so a bad value fails closed). Because the mask runs before any step records the query, the stats counter (Top Clients) and every query-log sink record the same masked value. The application log never records the client address (see Observability). Masking is forward-only.
2. If `dns.local_ptr` is enabled and the query is a PTR for a private reverse zone or for the LAN's own IPv6 prefix, record it and return authoritative NXDOMAIN locally, with no blocklist check, no cache, and no upstream call (CL 27, CL 101). The zones (`privateReverseZones`, a set matched label by label) are the locally served zones of RFC 6303 (0/8, 10/8, 127/8, 169.254/16, 172.16/12, 192.168/16, the three IPv4 documentation networks, 255.255.255.255, `::`, `::1`, fc00::/7, fe80::/10, 2001:db8::/32) and 100.64/10 (RFC 6598). The own prefix (`ownPrefixPTR`) is a name under `ip6.arpa` that `ip6Prefix` reads as a prefix inside a global IPv6 subnet of the host's interfaces, from the `lanACL` list; a miss reads the interfaces again, like a source miss. NXDOMAIN, not `0.0.0.0`: a PTR answer must be a name, and NXDOMAIN is the RFC 6303 answer. No public resolver can answer the private zones, and a reverse lookup of a LAN address tells the upstream which LAN addresses are in use; an EUI-64 IPv6 address holds the device's MAC address.
3. Answer or route a local-only name (`localnames.go`, CL 94). A `localhost` name gets the loopback address (RFC 6761). A name under `.onion`, `.invalid`, or `.alt` gets authoritative NXDOMAIN. A LAN-only name (a single-label name, a name under a built-in private suffix such as `.lan` or `home.arpa`, or under a `dns.local_domains` entry) may go only to the LAN upstreams; with none, it gets authoritative NXDOMAIN. A local answer is counted (`RecordLocalName`, `shole_local_names_total`) and logged as synthesized, and skips the blocklist, the cache, and the upstreams. See "Minimal upstream query and local names" below.
4. If the domain (or any of its parent domains) is on `blocklist.Store` (and no parent is allowlisted), write a sinkhole reply and return.
5. Check the DNS response cache, keyed by the question and the query's CD and DO bits. If a valid (non-expired) entry exists, decrement its TTLs and go to step 7 with it.
6. If 512 queries already wait for an upstream, answer SERVFAIL at once and count the query as unresolved (the forward limit, below). Otherwise build a fresh upstream query (`upstreamQuery`) and forward it to the first responsive upstream (for a LAN-only name, the first responsive LAN upstream). A reply counts only when it matches the query (`checkReply`, CL 97): the QR bit set, opcode QUERY, and one question with the same name (in any letter case), type, and class. Any other reply is a failed attempt, so a spoofed reply for another name on a plain-DNS upstream cannot enter the cache. On success, remove the reply's OPT record (`stripOPT`) and store the reply in the cache. Then go to step 7 with the reply.
7. Check the CNAME targets in the reply, from the cache or the upstream (`chainBlocked`, `cname.go`, CL 117). If `blocking.cname_inspection` is on, the queried name is not allowlisted, and a target is on `blocklist.Store`, write the same sinkhole reply as in step 4. Otherwise relay the reply. See "CNAME inspection" below.

Each step records the query in `stats.Counter` and the `querylog` loggers when its outcome is known: a query that step 7 blocks counts as blocked, not as a cache hit or a forward. The counters count every query. The Top Domains and Top Clients tallies get the domain and client only when `query_log.mode` records the query (`Handler.SetQueryLogMode`), so they never hold more than the query log. The per-minute graph follows the same rule (`stats.Counter.SetQueryLogMode`, CL 99).

#### CNAME inspection

A tracker can hide behind a subdomain of the site that uses it: the site adds `metrics.shop.example CNAME shop.example.tracker.example`, the browser sees a first-party name, and the site's cookies go to the tracker. The name is on no list. The resolver follows the chain and returns it in the Answer section, so s-hole has every target without a further lookup. Step 7 checks the target of each CNAME record with `IsBlocked`; one blocked target blocks the query.

- **Every serve.** The raw upstream reply is cached, and the check runs after a forward and on each cache hit. A blocklist reload or an allowlist change applies to the next query, and a repeated query for a cloaked name does not go upstream again.
- **The allowlist wins.** An allowlisted queried name (`Store.IsAllowlisted`, the same suffix walk) skips the check, so allowlisting the name that the device asks for repairs a site. An allowlisted target does not count, because `IsBlocked` applies the allowlist to it.
- **Only CNAME targets.** The final A/AAAA address is not checked (s-hole has no address lists, and CDN addresses are shared). A DNAME is covered by the CNAME that the resolver makes from it, and an HTTPS/SVCB target by the name check, because the client looks that name up through s-hole.
- **Counted and recorded as a block.** The query counts as blocked and in `cnameBlocked` (`shole_cname_blocked_total`, a subset of `shole_blocked_total`). The query-log row holds the queried name with `block_source` = 1 (`blocked_by: "cname"`). The query history, the query log file, the stats, and the application log never hold the target; the response cache keeps the raw answer until its TTL, as for any answer.
- **Limits.** The upstream sees the name, because s-hole needs its answer. s-hole cannot see CNAME flattening (the site's DNS provider returns A records only) or a site server that sends the data on to a tracker.

Every reply except the REFUSED to a source outside the LAN goes to the client through one writer, `send` (`edns.go`), including the SERVFAIL, NOTIMP, and RD=0 REFUSED replies (`writeRcode`): it sets the client's query ID, gives the reply an OPT record with the client's UDP size and DO bit and no options when the query had one (and none otherwise), truncates a UDP reply to 512 bytes or the client's EDNS0 size with TC set (`fitUDP`, b/081: after a TC retry over TCP, or from a DoH upstream, a reply can be larger than the client accepts), and pads a DoT reply when the client padded its query.

When every upstream fails, the forwarder returns a `*ForwardError` that names each upstream and its error, never the query name. The handler does not log one WARN per query: an outage would write every failed name to the system log (b/078). A summary (`RunFailureReport`) logs one `queries could not be resolved` line a minute with the count and each upstream's last error, never a domain, and its hint names the system clock when an error is an expired or not-yet-valid certificate, or the forward limit when it was reached. A reply that cannot be written to a client does not get a line of its own either: the same report logs one `replies could not be sent` line a minute with the count and the distinct errors, never a domain (CL 99). The errors are logged without the socket addresses, which would hold the client's address (`redact.NetError`).

Upstream forwarding uses a 3-second per-upstream timeout. Upstreams are tried in order; the first successful response wins. Forwarding accepts a `context.Context` so the overall query has a hard deadline (default 10 s) and is cancelled if the calling DNS handler exits.

At most 512 queries wait for an upstream at the same time (`maxForwards`, CL 102). miekg/dns runs one goroutine per query, and a cache miss holds its goroutine, a socket, and an upstream connection for up to the 10 s deadline, so without a cap one LAN device that sends many unique names could hold thousands of them. A query over the cap is not forwarded: it gets SERVFAIL at once and counts as unresolved (`shole_forward_failures_total`, a synthesized SERVFAIL row in the query log, and the failure summary with the cause `forward limit`), and `shole_forward_limited_total` counts it too. A query that does not need an upstream (blocked, cached, or answered locally) is not limited. The cap is global. A limit for each client would keep client addresses in memory, which the privacy rules do not allow without a need; `docs/ROADMAP.md` #44 records the decision.

An in-process upstream health tracker remembers which upstream failed most recently. On the next query, upstreams that failed within the last 30 seconds are skipped on the first sweep, so a primary outage no longer adds 3 s of round-trip latency to every subsequent query. If every upstream is in cooldown, the tracker is bypassed and every upstream is retried (we never want a transient outage to turn into a hard failure).

An upstream is either a plain resolver (`host:port`, queried over UDP with a TCP retry when the reply is truncated) or a DNS-over-HTTPS endpoint (`https://<IP>/dns-query`, RFC 8484; CL 85). The default list (CL 93) is DoH to Quad9, DoH to Cloudflare, then the same two over plain DNS. Because the list is tried in order, a plain entry is used for a public name only after every DoH entry has failed (a local name goes only to the LAN upstreams, which may be plain); such a query is counted (`dnsserver.PlaintextFallbacks`, `shole_upstream_plaintext_fallback_total`) and logged once a minute as `queries were sent unencrypted`, so a downgrade is never silent. A list with no DoH entry at all is a config choice that the privacy warnings report instead. DoH requests send `User-Agent: s-hole`, and their error texts show the URL through `redact.URL`. A DoH upstream carries the same wire-format query in an HTTPS POST over port 443, so the ISP interception and on-path tampering that plain port-53 traffic is exposed to no longer apply to the upstream hop. Plain and DoH upstreams share one ordered list and the same failover, cooldown, and per-upstream failure metric, because those all key off the upstream string; an operator lists a DoH endpoint first and a plain resolver after it to keep a fallback. A DoH endpoint must use an IP host, not a hostname: s-hole is often the LAN's own resolver, so resolving a DoH hostname could loop back into s-hole, and an IP host removes that bootstrap lookup (the major providers' certificates carry IP SANs, so TLS still verifies against the IP). DoH reuses the 3-second per-attempt budget; one shared HTTP client keeps the TLS connection alive, so only the first query after startup or a long idle gap pays the handshake. A DoH query is sent with ID 0 (RFC 8484) and padded to a multiple of 128 bytes (CL 94); the reply gets the query's ID back. The DoH client follows no redirect (`refuseRedirect`, b/102): Go's default policy sent the POST again, with the query in its body, to the `Location` URL of a 307 or 308, which could be another host or a plain `http://` URL. RFC 8484 does not need redirects. A redirect is a failed attempt like a transport error, so the forwarder tries the next upstream and `shole_upstream_transport_failures_total` counts it. This is upstream (client) DoH only; serving DoH to LAN clients is deferred (see Non-Goals and `docs/ROADMAP.md` #39).

Blocked and local replies get the same OPT record through `send` as a forwarded reply, so a client that advertises EDNS0 (and DNSSEC OK) does not fall back to legacy DNS for the sinkholed response.

#### Minimal upstream query and local names (CL 94)

s-hole never relays the client's message. A relayed message carried the client's query ID and its EDNS options: a COOKIE is a per-device token that lets the upstream tell the household's devices apart behind one public address, and a Client Subnet is part of the client's address. The cache then served one client's reply options to other clients. `upstreamQuery` builds a new message from the question (with the client's letter case, for dns-0x20), the RD, CD, and AD bits, a random ID (`dns.Id`, from `crypto/rand`), and s-hole's own OPT record: UDP size 1232 (DNS Flag Day 2020, no fragmentation on any path) and the client's DO bit. AD is copied because a stub sets it to ask for the AD bit in the reply (RFC 6840); it identifies nothing. A query with another opcode (NOTIFY, UPDATE) gets NOTIMP, and a query with more than one question gets SERVFAIL, because the fresh query can carry neither.

On the way back, `stripOPT` removes the upstream's OPT record before the cache stores the reply, so the cache holds no options, and `send` builds each client's OPT record. Extended DNS Errors from the upstream are dropped with the rest. miekg/dns folds the extended RCODE bits into `Msg.Rcode`, so an extended RCODE reaches an EDNS client; a client with no OPT record gets SERVFAIL instead, because the RCODE cannot be packed without one.

**No DNS cookies (RFC 7873).** s-hole drops the client's cookie and sends none of its own. A cookie is an identifier: s-hole behind NAT cannot see a change of the household's public address, so it could not rotate its cookie when the address changes, and the upstream could link the queries across the change. Cookies would also add per-upstream state and BADCOOKIE handling. Their benefit is protection against off-path spoofing on plain DNS, which is a fallback by default, and they do nothing against an on-path attacker; only DoH does. The plain path keeps a random query ID and a random source port per exchange (miekg/dns dials a new UDP socket each time), about 32 bits against off-path spoofing. An operator who wants no plain path deletes the plain entries.

**Padding (RFC 8467).** A DoH query is padded to a multiple of 128 bytes (`packDoH`), so the length of the encrypted request does not hint at the name. A DoT reply is padded to a multiple of 468 bytes only when the client's query carried a Padding option, as RFC 7830 asks; a reply over plain UDP or TCP is never padded, because padding hides nothing there.

**Local-only names.** `classify` sorts each name into one of four classes. `localhost` and names under it get 127.0.0.1 or ::1 (RFC 6761). Names under `.invalid`, `.onion` (RFC 7686), and `.alt` (RFC 9476) get NXDOMAIN and go nowhere, not even to the router, because no DNS server can resolve them. A LAN-only name goes only to an upstream on the LAN: names under `.local`, `home.arpa`, `.internal`, `.test`, `.intranet`, `.private`, `.corp`, `.home`, `.lan`, `.localdomain`, `fritz.box` (CL 101; AVM owns the domain, so nothing public is under it), and the `dns.local_domains` entries, plus single-label names. An upstream is on the LAN by the same rule as a client (`lanACL`), so the router, a resolver on loopback, and a DoH server on the LAN all count; with none, s-hole answers NXDOMAIN and `main` logs `no upstream on the LAN` at startup. A single-label query of type SOA, NS, DS, DNSKEY, RRSIG, NSEC, NSEC3, NSEC3PARAM, CDS, or CDNSKEY is public: a validating stub asks `com. DS`. dnsmasq's `domain-needed` draws the same line from the other side (A and AAAA only). `dns.local_domains` exists because routers use their own suffixes; a single label is a valid entry there, unlike an allowlist entry. At startup `main` reads the `search` and `domain` lines of the host's resolver files (`searchDomains`) and logs an INFO for each one that `Handler.KeepsLocal` does not cover (CL 101). It does not add them: a search domain can be a public domain that the router cannot answer, and its names would then get NXDOMAIN. There is no switch to send local names upstream: a router upstream keeps resolving them, and a public resolver could only answer NXDOMAIN after it had seen the name. A localhost name is checked before the blocklist and the blocklist parser skips localhost names, because hosts lists start with lines such as `127.0.0.1 localhost.localdomain`.

### Blocklist Store (`internal/blocklist/`)

The store is an in-memory `map[string]struct{}` (hash set) keyed on normalised domain names (lowercase, no trailing dot). Incoming queries are normalised the same way before lookup (DNS names arrive with a trailing dot and arbitrary casing), so both sides of the comparison share one key space.

Lookup is a **suffix walk** (CL 30): `IsBlocked` tests the queried name and each of its parent domains in turn (`a.b.example.com → b.example.com → example.com → com`), so a single list entry of `example.com` blocks every domain in its subtree. This closes the subdomain-rotation gap that exact-match blocking left open: trackers that rotate `x1.ads.example.com`, `x2.ads.example.com`, … are all caught by one `ads.example.com` entry. The walk reslices the name in place (no allocation) and costs O(labels) hash-set probes, effectively constant for real domain names, and `BenchmarkStore_IsBlocked` (plus its `_Miss` companion, the allowed-query worst case that walks every label) guards the hot path against regression. No new data structure is introduced: it is still two flat hash sets. There is deliberately **no config knob** to restore exact-match blocking; the allowlist (below) is the per-domain escape hatch for an over-broad block entry, so a global switch would only preserve the gap the change exists to close.

Multiple blocklists are merged by construction rather than by an explicit dedup pass: `Update` concatenates the parsed lists and `Replace` inserts them all into the set, where entries appearing in several lists (or differing only in case/trailing dot) collapse to a single key. The `total` reported at startup is the deduplicated set size, which is why it is smaller than the sum of the per-list counts.

Blocklists are downloaded from configurable URLs on startup and periodically thereafter (configurable via `refresh_interval`). The hosts-file format (`0.0.0.0 ads.example.com`), the plain-domain-per-line format, and wildcard lines (`*.ads.example.com`, as in oisd's "domains (wildcards)" lists) are supported. A wildcard line means the domain and every subdomain, which the suffix walk already gives a plain entry, so the parser drops the `*.` (CL 95). The parser counts the non-blank, non-comment lines that give no domain. When a list is empty, or when it skips more lines than it reads, `Update` logs a WARN (`blocklist has no domains`, `blocklist lines skipped` with `read` and `skipped`): the usual cause is a format s-hole does not read, such as an Adblock list. A zero-only check is not enough, because a stray Adblock rule can pass `ValidDomain` (EasyList gave one match, `-728.90.`, before CL 95 made `ValidDomain` stricter). Downloaded files are cached on disk so a restart does not require a network round-trip: at startup, a cache file less than 24 hours old is used without a fetch. A reload always tries the download first. Before b/060, a reload one `refresh_interval` after the last download found a cache just under 24 hours old, so the default 24h refresh downloaded only every 48 hours. Each source logs one `loaded` line whose `from` attribute is `download`, `cache`, or `stale_cache` (CL 88). If a download fails (also after the 200 status, b/068), the server returns a non-200 status, or the list is over the size cap, the stale cache is used (the error response body is never written to disk).

If every configured URL fails on a refresh (typically: total network outage), `blocklist.Update` preserves the existing block set rather than replacing it with an empty slice. This prevents a transient outage from silently unblocking every ad until the next successful refresh. The function returns a wrapped error reporting the last failure; the caller logs it but continues to run.

Whenever an update leaves the block set empty, `Update` raises a loud `WARN` (`warnIfEmpty`) so an operator notices s-hole is answering queries while blocking nothing. This covers two cases the ordinary logs would otherwise hide: a fresh first run that could reach no source and had no cache to fall back on, and a source that returned HTTP 200 but parsed to zero valid domains (which previously logged `blocklist updated total=0` at `Info`, indistinguishable from a healthy refresh). `/readyz` already reports the empty state as 503, but that signal is easy to miss on a headless box. An embedded fallback blocklist was considered and rejected for this role (see `docs/ROADMAP.md` #6) because it would mask the failure with stale, license-encumbered data rather than surface it.

Downloads use a dedicated `http.Client` with a 60-second timeout. The response body is wrapped in `io.LimitReader` capped at 256 MiB to bound disk and memory use if a server misbehaves.

An allowlist is checked with the same suffix walk and takes precedence at every level: if the queried name or any of its parents is allowlisted, the query is allowed regardless of blocklist membership, even when a more specific parent is on the block set. Allowlisting `safe.doubleclick.net` lets that name and its subtree through while `ads.doubleclick.net` stays blocked; allowlisting `example.com` exempts everything beneath it. Because allowlist precedence is global (not most-specific-wins), the walk cannot stop at the first blocked parent; it continues until it either finds an allowlisted suffix or exhausts the labels. The allowlist can be extended at runtime via the REST API; runtime additions take effect immediately but do not persist across restarts. The allowlist keeps at most 1,000 entries that the API added (the store counts them in a separate `runtime` set, and a DELETE frees a place; the config allowlist does not count and has no limit), and it refuses a two-label entry that starts with `co`, `com`, `org`, `net`, `gov`, `ac`, or `edu` (such as `co.uk`), which would exempt a whole public suffix. This is a small built-in rule, not the Public Suffix List, so `github.io` still passes.

Both entry paths validate entries with `blocklist.ValidDomain`, so a bare label such as a TLD (which, being suffix-matched, would otherwise exempt its whole subtree) cannot reach the store. The two paths differ only in how they refuse: the REST handler rejects an invalid addition outright (`400`), while at startup `config.Load` drops any invalid `allowlist` entry and reports it as a config problem (a WARN at startup; `-check-config` fails) rather than aborting. A config typo must not take DNS down for the whole LAN, and a dropped entry fails safe: the domain simply stays blockable (CL 31).

Blocklist replacement is atomic from the perspective of DNS handlers: `Store.Replace` swaps the internal map pointer under a write lock, so handlers either see the old list or the new list, never a partial update.

The store's memory grows linearly with the number of unique domains, while lookup time does not grow with it at all. The blocked set is a `map[string]struct{}`, so each entry costs the Go map overhead plus the domain bytes, and the empty-struct value adds nothing. Measured, that is roughly 70 to 100 bytes per entry. It works out to about 5 MB for an 80k list, 20 MB for a 250k list, and 200 MB for a 2.26M-entry list such as HaGeZi's full threat-intelligence feed. Lookup cost stays flat because the suffix walk does O(labels) probes regardless of how many domains the map holds; a larger map only adds a small constant CPU-cache penalty per probe, never more probes. Two effects sit above this resting footprint. First, `Store.Replace` builds the whole new map before it swaps the pointer, so a refresh holds the old and new sets at once and briefly doubles the set's memory (plus the transient download and parse buffers). Second, because the in-memory set deduplicates, overlapping lists cost only their union, so stacking lists is cheaper than the sum of their sizes suggests. At the tiers the sample config recommends (up to about 250k domains) both figures are small on home hardware. The full threat-intelligence feed is the one to watch on a small Raspberry Pi, and for memory, not for lookup speed.

For operator sizing, the figure to budget is the whole process, not the set alone. Measured resident memory (RSS) on a 64-bit Linux build was about 28 MB for an 80k list, 45 MB for a 320k list, and 79 MB for a 440k list: the set from the paragraph above, plus the Go runtime baseline (a few MB) and the response cache. These are idle figures just after startup. A blocklist refresh adds the reload transient on top (`Store.Replace` holds the old and new sets at once, and the parse allocates about 250 bytes of short-lived memory per domain; see `docs/ROADMAP.md` #32). The Go runtime keeps freed heap for reuse, so before CL 93 RSS stayed near double the idle figure for minutes after each reload: 105 to 125 MB against 65 MB at 405 000 domains on a Raspberry Pi 5 (b/083). `main` now calls `debug.FreeOSMemory` after each blocklist load, which returns the freed pages at once for a few tens of milliseconds of CPU, off the DNS path. All of these fit comfortably on a Raspberry Pi. Method: `VmRSS` from `/proc/<pid>/status` with the sample config on Go 1.26.x. Treat the numbers as order-of-magnitude guidance, not a contract; they move with the Go version and the exact lists.

The on-disk cache file is also written atomically: `fetchList` streams to a sibling `.tmp` file and `os.Rename`s on success. A network drop or `kill -9` mid-download leaves only the `.tmp` and the prior cache file in place; the next start still sees a usable cache. The cache only saves a download at the next start, so a cache file that cannot be created or renamed (for example a data directory owned by another user after a Docker image upgrade) is a WARN, and the downloaded list is still used. Downloads send `User-Agent: s-hole`, and every URL in a log line or a returned error (including the HTTP client's own error, which prints the full URL) goes through `redact.URL`, which hides user info and the query string. `PurgeCache` deletes the cache files (only `blocklist_*.txt` and their `.tmp` files) for a purge.

Cache files are deliberately per-URL, verbatim copies of what each server sent, never merged or deduplicated on disk. The stale-fallback contract is per-list (a failing URL falls back to *its own* last good snapshot, independent of the other lists), and an untransformed copy is inspectable evidence when a source misbehaves (see b/007). Deduplication happens for free in the in-memory set.

Entries in a parsed list that fail `ValidDomain` (empty, no dot, over 253 chars, containing characters illegal in a DNS label, an empty label, or a label that starts or ends with a hyphen) are silently dropped (each counts as a skipped line) so one malformed blocklist line cannot pollute the store. The same validator gates user-supplied allowlist entries via `POST /api/allowlist`.

### DNS Response Cache (`internal/cache/`)

The cache is a size-bounded, TTL-respecting in-memory store for upstream DNS responses. Its purpose is to avoid redundant upstream round-trips for frequently queried domains, which is especially valuable on low-power hardware where upstream latency is comparatively high.

Key design decisions:

- **Key:** `<qname>\x00<qtype>\x00<qclass>\x00<CD and DO bits>`, the full question identity plus the two query bits that change the upstream's answer. `Get` and `Set` take the client's query and build the key from it, so a caller cannot leave the bits out. `Qclass` is included so cross-class queries (e.g. `ClassCHAOS` for `version.bind`) cannot collide with the dominant `ClassINET` traffic. CD (checking disabled) makes a validating upstream return data that failed DNSSEC validation, and DO (DNSSEC OK) adds the RRSIG records; without the bits in the key, one CD=1 query turned off validation for every client until the entry expired, and a DO=1 client got a reply without signatures (CL 97, b/096). AD is not in the key: it only asks the upstream to report the AD bit.
- **Value:** a cloned `dns.Msg` with the time it was cached and the minimum TTL across all answer records. The handler removes the OPT record before `Set` (CL 94), so a cached reply holds no EDNS options and each client gets its own OPT record on a hit.
- **Lifetime cap:** an entry lives at most one day (`maxTTL`, 86,400 s, Unbound's default `cache-max-ttl`), and `Set` lowers each stored record's TTL to that cap, so a bad answer or a huge upstream TTL cannot stay longer and a client is not told to keep the answer longer than s-hole does (CL 97). There is no setting for the cap.
- **TTL adjustment:** on retrieval, elapsed seconds are subtracted from each record's TTL so clients receive accurate expiry times. An EDNS0 OPT record is skipped: its TTL field holds the extended rcode, the EDNS version, and the DO flag, and decrementing it cleared DO after a few seconds (b/072). Since CL 94 the handler stores no OPT record; the skip keeps the cache correct for any caller.
- **Eviction:** when the cache reaches `dns.cache_entries` entries, `Set` first tries to reclaim a slot from an expired entry (a bounded scan of at most `reclaimScanLimit` entries). `Get` marks expired entries as misses but leaves them in the map until the once-a-minute sweep, so without on-insert reclaim a cache full of not-yet-swept corpses would refuse every insert for up to a minute. If the bounded scan finds no expired entry, the cache is full of live entries: the new entry is dropped and counted, and `shole_cache_dropped_total` surfaces the rate so a sustained non-zero value is the signal to raise `dns.cache_entries`. LRU is deliberately not used: it requires a move-to-front on every `Get`, a write on the read path. `Get` is a bare `RLock` read today (the hit/miss counters are atomic), so LRU would turn every cache hit into an exclusive `Lock` and serialize readers, the contention `BenchmarkCache_Get_Parallel` exists to catch. For a read-dominated cache at home-DNS scale that is the wrong trade; if recency ever mattered, a scheme that keeps `Get` read-only (CLOCK or SIEVE: an atomic visited-bit, no reorder on hit) is the way in, not LRU.
- **Only NOERROR responses with at least one answer are cached.** NXDOMAIN, SERVFAIL, empty-answer, and truncated (TC bit) responses are not stored, because a truncated message carries an incomplete answer section that would otherwise be replayed for its full TTL.
- **Cleanup:** a background goroutine sweeps expired entries every minute. It exits cleanly on `Cache.Close()`, which is invoked from the shutdown path so the goroutine never outlives the process. `Flush` empties the cache for a purge: the cache is a short history of the names the network looked up.
- **Cache hit rate** is tracked in `stats.Counter` and reported in `GET /api/stats` and `/metrics` (`shole_cache_hits_total`). The periodic `msg=stats` log line holds the uptime only (b/098).

### Sinkhole Responses

Two modes are supported via `blocking.reply` in config:

| Mode | A query reply | AAAA query reply | Other types |
|------|--------------|-----------------|-------------|
| `zero_ip` (default) | `0.0.0.0` | `::` | NOERROR, empty answer |
| `nxdomain` | NXDOMAIN | NXDOMAIN | NXDOMAIN |

`zero_ip` is the default because `NXDOMAIN` causes some clients to aggressively retry, log errors, or display alarming UI. Returning a routable-but-unroutable address fails silently at the TCP connect layer, which is the behaviour most consistent with "nothing happened."

The TTL on sinkhole replies is configurable (`blocking.reply_ttl_seconds`, default 300 seconds). A short TTL means an allowlisted domain becomes reachable within TTL seconds after being added to the allowlist, without requiring a client cache flush. An explicit `reply_ttl_seconds: 0` is honored: it tells clients not to cache sinkhole replies at all, trading query volume for instant allowlist effect.

### Query Logging (`internal/querylog/`)

Query logging is off by default (`query_log.mode: "none"`, CL 93). When the operator turns it on, it is split into two independent backends behind a `Multi` fan-out, and both are off until configured: `query_log.database` (SQLite) and `query_log.file` (text lines). Both respect `query_log.mode` (`"none"`, `"blocked"`, `"all"`) independently, and neither ever blocks a DNS goroutine.

**FileLogger** writes one line per recorded query to standard output (`query_log.file: "stdout"`) or to a file:
```
2026-06-23T10:04:05Z BLOCK 192.168.1.42 ads.example.com.
2026-06-23T10:04:06Z ALLOW 192.168.1.42 cdn.example.com. CACHED
2026-06-23T10:04:07Z ALLOW 192.168.1.42 dead.example.com. FAILED
2026-06-23T10:04:08Z BLOCK 192.168.1.42 metrics.shop.example. CNAME
```
An ALLOW line carries an optional trailing marker: ` CACHED` for a reply served from the response cache, or ` FAILED` for a failed query (s-hole synthesized a SERVFAIL, or relayed a SERVFAIL/REFUSED from an upstream). The two markers are mutually exclusive. A BLOCK line carries neither (a blocked query is never served as an allowed answer, and its rcode is not a failure); it carries ` CNAME` when a CNAME target in the reply matched, not the queried name (CL 117). Times are UTC. `Log` hands each line to a writer goroutine through a buffered channel and drops it, counting it (`shole_query_log_file_dropped_total`), when the writer falls behind. Before CL 93 the line was written directly, so a slow reader (journald) blocked queries, and the stream to standard output was on by default, so the system journal held a second, unmanaged copy of every query, outside retention and purge (b/075). A file is created with mode `0600` (an existing one is tightened). An open failure turns the output off with a WARN; it never falls back to standard output (b/079). s-hole never shortens the file, except in a purge: the purge overwrites it with zeros through a second handle (the log is open for append, which writes only at the end), syncs it, and then empties it (CL 105). It overwrites only the file it has open: if another file took the path (a log rotation), the purge only empties the open file and returns `ErrNotOverwritten`. On Windows, Go opens an append handle without the right to write data, so `Truncate` on it fails; the purge then empties the file through a new handle, after it checks that the path still names the open file (b/105). Windows refuses to rename a file that s-hole holds open, so the rotation case does not arise there.

**DBLogger** writes to a SQLite database (`modernc.org/sqlite`, pure Go, no CGO). It runs an internal goroutine that batches inserts: entries accumulate for up to `query_log.flush_interval` (default 30 seconds) or 100 entries, then are committed in a single transaction. This decouples DNS handler latency from disk I/O. If the channel buffer (capacity 1000) is full, entries are dropped rather than blocking a DNS goroutine, since logging completeness is subordinate to DNS availability.

The database file is owner-only: `NewDBLogger` creates a missing file with mode `0600` before SQLite opens it (SQLite gives its `-wal` and `-shm` files the database file's mode) and tightens an existing database and its `-wal` and `-shm` files to `0600`, so an upgraded install stops exposing the history an older build wrote with mode `0644` (b/076). Rows store `ts` in UTC; a one-time migration rewrites older rows, which held local time with an offset, and lowercases their domains.

On shutdown, `DBLogger.Close()` blocks on a `sync.WaitGroup` until the writer goroutine has drained the channel and committed the final batch. Only then is the underlying `*sql.DB` closed. This guarantees the last batch of queries is never lost on a clean exit.

`Recent` and `TopBlocked` accept a `context.Context` and pass it through to `db.QueryContext`, so a client-disconnect on the admin server cancels the underlying SQL query rather than letting it run to completion.

A retention prune goroutine runs every hour when `query_log.retention_days > 0` (default 7), issuing `DELETE FROM queries WHERE ts < ?` against the UTC cutoff. A plain DELETE only marks SQLite space free and the WAL keeps old page images, so a pruned query stayed readable in the files (b/077). The database therefore runs with `secure_delete=ON`, which overwrites deleted rows with zeros, and after a prune that deleted rows `wipeWAL` copies the zeroed pages into the database file and empties the WAL. `Purge` deletes every row, resets the row counter (the next row id would otherwise tell how many queries were ever recorded), runs `VACUUM`, and runs `wipeWAL` before and after the `VACUUM`; it runs in the writer goroutine, so no batch in flight is written after it.

SQLite frees the WAL without overwriting it: a TRUNCATE checkpoint cuts it to zero bytes, `journal_size_limit` cuts it after a commit, and the close of the last connection deletes it. The freed blocks keep older page images, with domains, clients, and times (PRIV-16). So `wipeWAL` overwrites the WAL with zeros at each point where it is freed: at startup (after the migration and a crash recovery), after a prune that deleted rows, twice in a purge, and in `Close` (CL 110). It holds the one connection for the whole sequence: `wal_checkpoint(RESTART)`, which must copy every frame into the database file; `BEGIN IMMEDIATE`, with an unchanged `PRAGMA data_version`, so no other process wrote after the checkpoint; `ZeroFile` on the `-wal` file; `ROLLBACK`; and `wal_checkpoint(TRUNCATE)`. After a complete checkpoint SQLite reads no frame from the WAL, and it writes the next transaction from the start of the WAL with a new header. `ZeroFile` writes and syncs the 32-byte WAL header before the rest: after a power loss during the overwrite, a valid header with only part of the frames zeroed would make recovery replay older frames over newer database pages (a test copy silently lost the last update of 1,600 rows), and SQLite ignores a WAL whose header is not valid. `wipeWAL` opens only the `-wal` file, because SQLite holds POSIX locks on the database and `-shm` files, and closing another descriptor of those files would drop those locks. `journal_size_limit=-1` keeps SQLite from shortening the WAL on its own. When a check fails (another program reads or writes the database at that moment, or the `-wal` file is a link), `wipeWAL` neither overwrites nor truncates, so the data stays in the file for the next try, and s-hole logs `query log WAL overwrite failed`; an online purge then fails, and at a stop the WAL stays until the last connection closes, which deletes it without the overwrite.

When s-hole is stopped, `s-hole -purge` overwrites the database, `-wal`, and `-shm` files with zeros (`querylog.ZeroFile`) and deletes them (CL 105). The zeros cover every byte that the purge steps above would change, and also the free pages and a `-wal` file that a crash left. The offline purge does not open the database with SQLite: it can run as root in the data directory that the `s-hole` user owns, and SQLite writes through a hard link at the `-wal` or `-shm` path. For the same reason `ZeroFile` refuses a symbolic link, a file that is not a regular file, and a file with more than one hard link (`ErrRefused`); the step fails, and the purge keeps the file. On flash storage only disk encryption guarantees that a deleted block cannot be recovered from the medium.

`StaleRows` reports the stored rows that hold more than the current settings would write: any row under mode `"none"`, an allowed row under `"blocked"`, a row with a client address under clients `"drop"`, a full address, or a value it cannot parse, under `"subnet"`. It only reads: s-hole never rewrites the operator's history on its own. `main` runs it at startup and hourly and reports the result as a privacy warning with the date retention removes the last such row.

The `querylog.Logger` interface (`Log(rec Record)`) is implemented by `FileLogger`, `DBLogger`, and `Multi`, with compile-time assertions in the package so a future signature drift is caught at build time rather than at the call site. `Record` is a struct rather than positional arguments, so a new per-query field does not churn every implementation. It carries the client, domain, and blocked flag, plus `CacheHit` (CL 76) and the outcome pair `Rcode`/`Synthesized` (CL 77): `Synthesized` is true when s-hole built the reply itself (a block, a local PTR answer, or a synthesized SERVFAIL) and false when it relayed an upstream or cached message, so the `Failed`/`Unresolved`/`UpstreamError` helpers derive the outcome without a separate stored enum.

**SQLite pragmas applied on open:**
```sql
PRAGMA busy_timeout=5000;            -- wait for a held lock instead of failing with SQLITE_BUSY
PRAGMA journal_mode=WAL;             -- write-ahead log: reads don't block writes
PRAGMA synchronous=NORMAL;           -- no fsync per commit; WAL checkpoint is still safe
PRAGMA secure_delete=ON;             -- a DELETE overwrites the deleted rows
PRAGMA journal_size_limit=-1;        -- SQLite never shortens the WAL; wipeWAL zeroes it first
PRAGMA cache_size=-8000;             -- 8 MB page cache
PRAGMA temp_store=MEMORY;            -- keep temp tables off disk
```
WAL mode combined with `synchronous=NORMAL` reduces write amplification by roughly 10× compared to SQLite's default rollback journal. This is the primary mitigation for SD card wear on Raspberry Pi deployments. `secure_delete` adds writes only when rows are deleted (the hourly prune), `wipeWAL` writes the size of the WAL in zeros at startup, at each prune that deletes rows, in a purge, and at a stop (at most a few MiB at home-network volume), and the private defaults cut the insert volume (on a Raspberry Pi 5 at 20 queries per second, `"blocked"` wrote 637 bytes per query against 1.8 KB under `"all"`).

The `*sql.DB` pool is pinned to a **single connection** (`SetMaxOpenConns(1)`). SQLite permits only one writer at a time; with the default multi-connection pool the async batch writer and the retention prune (both writers) could land on separate connections and collide with `SQLITE_BUSY`, silently skipping a prune (b/038). One connection makes `database/sql` queue callers instead, and ensures the per-connection pragmas above apply to the connection that serves every query. `busy_timeout` remains as defence against an external process holding the lock. At home-network query volume the lost read concurrency is immaterial.

The SQLite schema:
```sql
CREATE TABLE queries (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    ts          TEXT    NOT NULL,                -- RFC 3339, UTC
    client_ip   TEXT    NOT NULL,                -- as query_log.clients allows; "" under drop
    domain      TEXT    NOT NULL,                -- lowercase, with the trailing dot
    blocked     INTEGER NOT NULL,
    cache_hit   INTEGER NOT NULL DEFAULT 0,  -- CL 76
    rcode       INTEGER NOT NULL DEFAULT 0,  -- CL 77: reply rcode (0 = NOERROR)
    synthesized INTEGER NOT NULL DEFAULT 0,  -- CL 77: 1 if s-hole built the reply itself
    block_source INTEGER NOT NULL DEFAULT 0  -- CL 117: what matched a blocked row (0 = name, 1 = CNAME target)
);
```
The columns after `blocked` were added by later CLs. SQLite has no `ADD COLUMN IF NOT EXISTS`, so `migrate` adds each on startup only when a `PRAGMA table_info` probe shows it absent (the `ensureColumn` helper); a fresh database already has them. Older rows take the column `DEFAULT`, so a query written before the upgrade reads `cache_hit=0`, `rcode=0, synthesized=0` (never a failure), and `block_source=0` (a block on the name, the only kind before CL 117). This forward-only behavior is why the cached and failure lines of the 7-day stored graph under-report for buckets predating each feature.

### Statistics (`internal/stats/`)

`Counter` maintains atomic counters for total queries and cache hits. The blocked count is deliberately *not* atomic: `RecordQuery` already takes the mutex to update the top-domain tally, so `blocked` is guarded by that same mutex; promoting it to an atomic would be redundant and misleading. Per-domain block counts and per-client query counts are tracked in the mutex-protected maps. Top-N extraction copies the map entries under the lock (resolving the map pointer *inside* the lock, since the prune reassigns it, R31) and sorts the copy outside it to minimise contention.

`RecordQuery` skips the tally for an empty client or domain: the handler passes `""` when `query_log.clients` drops the client or `query_log.mode` does not record the query (CL 93), and `ResetTallies` empties both lists for a purge. The counters (total, blocked, blocked through a CNAME, cache hits, failures) are not reset by a purge: they are counts, and resetting them while queries are in flight could break the load-order invariant below. The Counter also keeps the per-minute timeline behind the dashboard graph (`timeline.go`): 1440 buckets of total, blocked, cached, unresolved, and upstream-error counts for the last 24 hours, never a domain or a client, never on disk. The counts over time show when the household is active, so the timeline follows `query_log.mode` (`SetQueryLogMode`, CL 99): nothing under `"none"` (and before the mode is set), blocked queries only under `"blocked"`. Each bucket's fields are atomic, and the first event of a new minute claims the bucket with a compare-and-swap, so the timeline adds no lock to the query path. `Timeline(window, bucket, now)` aggregates it into a dense series, and `ResetTimeline` empties it for a purge.

`Snapshot(topN int)` returns a `Summary` struct with json tags, making it directly serialisable by the REST API without coupling the stats package to any HTTP library. Fields include uptime, totals, block percentage, local-PTR count (`local_ptr_count`, queries answered locally per RFC 6303), local-name count (`local_name_count`, local-only names answered here, CL 94), cache hit count and percentage, the two failure counters (`forward_failures`, queries s-hole could not resolve; `upstream_errors`, failure rcodes relayed from a live upstream), the queries blocked through a CNAME target (`cname_blocked_count`, a subset of the blocked count, CL 117), blocklist size (`blocklist_size`, set by the API handler after calling `Snapshot`, since the stats package does not depend on the blocklist package), and top-N entry lists. The two failure counters obey the same load-order invariant as the other per-query counters (read before `total` in `Snapshot`, since the handler bumps them after `RecordQuery`). The per-source blocklist health (`sources`, an array of `{url, count, last_refresh, stale}`) is added the same way: the api handler wraps `Summary` in a `statsResponse` and fills `sources` from `blocklist.Store.Sources()`, so the stats package still takes no blocklist dependency. `count` is the pre-dedup domain count each source contributed, so the sum exceeds `blocklist_size`; `stale` is true while a source is served from its on-disk cache after a failed fetch, or has never loaded. A `privacy` object (`mode`, `clients`, `database`, `file`, `retention_days`) and the `warnings` in effect ride on the same `statsResponse` wrapper, so the dashboard can say what s-hole records; they are display metadata only, since the client IP is already masked in the DNS handler. The same `mode` and `clients` values decide what the allowlist audit line keeps of the requester. The DNS-over-TLS state rides on the same wrapper as a `dot` object (`{"enabled": false}` while DoT is off). `main` fills it from `dnsserver.CertReloader.Status` through `api.Server.SetDoTStatus`, so the api package does not import dnsserver; the state (`ok`, `expiring`, `expired`, `reload_failed`) is computed in dnsserver, where the 14-day window is defined. Each top-client entry also carries an optional `label` from the `client_names` map (CL 73), resolved in the handler against the masked client value; `/api/queries` rows carry the same `label`, plus a computed `outcome` label (`allowed`/`blocked`/`unresolved`/`upstream_error`) derived once server-side by `QueryRow.Outcome` from the stored rcode and synthesized flag, so the dashboard and any export read a name instead of decoding the rcode. Both are added in the api layer, so the `stats` and `querylog` packages are untouched.

`Snapshot` loads `cnameBlocked`, `blocked`, `localPTR`, `localName`, `cacheHit`, `forwardFailures`, and `upstreamErrors` all *before* `total`, and `cnameBlocked` before `blocked`: it is a subset of `blocked`, because the handler calls `RecordCNAMEBlocked` after `RecordQuery` counted the query as blocked (CL 117). This load order matters: `RecordQuery` increments `total` atomically *before* taking the mutex and incrementing `blocked`, so reading `total` first allows concurrent queries to inflate `blocked` past the snapshotted `total` and yield a block percentage greater than 100. Reading `blocked` first guarantees the invariant `blocked ≤ total`. `localPTR`, `localName`, `cacheHit`, and the two failure counters are also incremented after `total` (by `RecordLocalPTR`, `RecordLocalName`, the cache-hit path, and the forward path, all after `RecordQuery`), so each must be read before `total` for the same reason. The cache-hit-rate denominator is `total − blocked − localPTR − localName` because none of these queries is served as an allowed answer. A query blocked by its name, a local-PTR query, and a local-name query never reach the cache or the upstream. A query blocked by a CNAME target reads the cache or goes upstream, but it counts as blocked, never as a cache hit.

The per-domain and per-client tally maps are capped at 4 096 entries each. When the cap is exceeded, the bottom half by count is dropped, preserving the high-traffic entries that the top-N report cares about and keeping memory bounded against a long-running process that sees millions of unique keys.

### Admin Interface (`internal/api/`)

An HTTP server (default `127.0.0.1:8080`, localhost only) serves two things:

1. **REST API.** JSON endpoints backed by `stats.Snapshot`, `querylog.DBLogger.Recent`, and `blocklist.Store` methods.
2. **Web UI.** A single-page dashboard embedded in the binary via `//go:embed`: the page (`static/index.html`) and its script (`static/app.js`, a separate file so the CSP allows no inline script). It polls `/api/stats` and `/api/queries` every 3 seconds and renders stat cards, a "Queries over time" graph, top domain/client tables, a per-source blocklist health panel (URL, domain count, last refresh, and an OK/STALE badge), an actions panel (reload, allowlist add, a "why is this blocked?" domain check that shows the decision and the full suffix walk, and **Delete history**, which runs the purge), and a recent query log.

The header says what s-hole records: the `query_log.mode` ("nothing", "blocked queries", "all queries"), the client mode, and the stored-history retention ("off", "7 days", "forever"), with a red PER-DEVICE HISTORY ON badge when `clients` is `"full"` (amber SUBNETS RECORDED for `"subnet"`) and the mode records queries. A warnings panel lists the same privacy and security warnings the log repeats with every stats line (`/api/stats` `warnings`); it is hidden when there are none.

The "Queries over time" graph draws total (violet), blocked (red), cached (teal), unresolved (amber), and upstream error (orange) per bucket from `/api/history`. The 24h view reads the in-memory per-minute counts, which follow `query_log.mode` like the Top lists: under `"none"` they record nothing and the panel shows a note instead of a graph; under `"blocked"` they record blocked queries only, so the graph shows one labeled blocked line. The 7d view reads the stored history and appears only when the database is on and the mode records queries; under `"blocked"` that history holds blocked rows only, so the 7d graph shows one labeled blocked line. The failure lines are amber and orange (not red, which means blocked) so a spike reads as trouble; each is a subset of the forwarded remainder, so both scale under the total envelope. The cached line is the subset of total served from the response cache.

The Top Blocked Domains panel has a "Since start / Stored" toggle: "Since start" reads the in-memory `top_domains` tally from `/api/stats` (resets on restart, caps at `topNMaxEntries`, empty under mode `"none"`), while "Stored" (shown only with a stored history) polls `/api/top-blocked`. The Top Clients panel describes itself from the settings: under mode `"none"` or clients `"drop"` it shows why no client is listed, and under `"subnet"` it notes that the entries are masked. When a `client_names` label resolves for a client, the Top Clients panel and the recent-query log show the label with the masked IP beneath it. Every empty panel names the setting that explains it.

A line under the Blocked card shows how many queries s-hole blocked through a CNAME target (`cname_blocked_count`), and a row blocked that way shows a `BLOCK · CNAME` badge in the recent-query log (CL 117). The recent-query log has filter controls in its header: a domain substring box, an All/Blocked/Allowed/Unresolved/Upstream-error toggle, and a client picker seeded from the Top Clients list (hidden when no client is stored). The filter runs server-side in SQL, so it matches only the stored (masked) columns. The filter lives in `sessionStorage`: a typed domain search is query data and must not stay in the browser profile after the tab closes. Export CSV and Export JSON links download the current filter through `/api/queries/export`; they grey out without a stored history. When DNS over TLS is on, the header also shows a certificate badge from the `/api/stats` `dot` object: OK (green) with the days left, EXPIRES SOON (amber) inside 14 days, EXPIRED or RELOAD FAILED (red); the server computes the state and the days left, so the browser clock does not matter. The three panels that fetch their own data are collapsible; a collapsed panel skips its poll, and the choice (no query data) persists in `localStorage`. Every value from a query is passed through `esc()`, which escapes `&`, `<`, `>`, and both quotes.

The web UI has no external dependencies (no CDN, no framework). It is pure HTML/CSS/JS and works without an internet connection.

The HTTP server is held in an `atomic.Pointer[http.Server]` so it can be gracefully shut down. `Serve` stores it from the background serve goroutine and `Shutdown` reads it from the signal goroutine, so the field is atomic to keep those two accesses race-free (b/053). `doStop` in `cmd/s-hole/main.go` calls `apiServer.Shutdown(ctx)` with a 5-second context before terminating the process, which drains in-flight admin requests. A Shutdown that runs before `Serve` has stored the server records the stop request (a second atomic); `Serve` checks that flag right after it stores the server and stops instead of blocking in Accept, so the stop is never lost even in that startup window (b/054). `http.ErrServerClosed` is suppressed inside `Serve` so a clean shutdown does not log a spurious error.

main binds `admin.listen` synchronously (`net.Listen`, then `apiServer.Serve(ln)`) so a bad address or a port conflict is caught at startup, not inside a goroutine. A failed admin bind is fail-open: main logs a WARN, keeps serving DNS, and the startup banner reports the admin UI as unavailable rather than advertising a URL that refuses connections. DNS is the critical service, so it must not die because the optional dashboard could not bind (b/052). `ListenAndServe(addr)` remains as the one-call bind-and-serve form.

Every route goes through `secure` (`security.go`, CL 93). Binding to localhost does not stop a web page in the operator's own browser from reaching the server, and these attacks worked against earlier releases (the first two until CL 93, the third until CL 104):

- **DNS rebinding (b/073).** A page points its own name at the admin address and then reads the whole query history as a same-origin page. The browser still sends the attacker's name in the `Host` header, so the server answers only when `Host` (port ignored) is empty, an IP literal, `localhost`, or one of the machine's own names (the OS hostname, its first label, and that label with `.local`), and answers anything else with `421` and a hint. Allowing the machine's own names is safe because an attacker's page can only send its own name; a prefix rule such as `raspberrypi.*` would not be. The rule covers every route, `/metrics` and the probes included: Prometheus, Docker, and Kubernetes reach s-hole by IP.
- **Cross-site requests (b/074).** A `text/plain` POST needs no CORS preflight, so any page could add an allowlist entry. `http.CrossOriginProtection` refuses a state-changing request that the browser marks as cross-site (`Sec-Fetch-Site`, or an `Origin` that does not match `Host`); `curl` and scripts send neither and pass. JSON endpoints also require `Content-Type: application/json`, which a cross-site form cannot send.
- **Cross-site reads (CL 104).** A page cannot read a GET reply from another origin, but it can send the GET and time the reply (`/api/queries?domain=` answers faster for a name that is not in the history), and it can start exports that hold the two export slots. `fetchAllowed` is a Fetch Metadata resource isolation policy: a request with `Sec-Fetch-Site: cross-site` or `same-site` gets `403` on every route and method, except a top-level navigation to the dashboard (`GET /` with `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document`), so a link from another page still opens it. `same-site` is refused too, because another port on the same address (a second web app on the host) is the same site. `same-origin` (the dashboard itself), `none` (a typed URL or a bookmark), and no header (`curl`, Prometheus, the healthcheck, an old browser) pass; an unknown value is refused. Browsers send `Sec-Fetch-Site` only to a potentially trustworthy origin (HTTPS, `localhost`, a loopback address), so the check protects the default `127.0.0.1:8080` bind. A dashboard opened by its LAN address over plain HTTP gets no header, and only the Host check and `CrossOriginProtection` apply there; TLS for a non-loopback admin listener is part of ROADMAP #42.

`secure` also sets `Cache-Control: no-store` (query data stays out of the browser's disk cache), a Content-Security-Policy (script, connections, frames, base URI, and forms limited to the page's own origin; no inline script or inline event handler runs, so an injected `<script>` or `onerror` attribute does nothing; inline styles are still allowed because the page uses them), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `Cross-Origin-Resource-Policy: same-origin`. None of this is authentication.

`POST /api/purge` (`purge.go`) is the most destructive request, so it is accepted only from the s-hole host itself (a loopback address or one of the host's interface addresses), only as JSON, and only with `{"confirm": true}`. A device on the LAN cannot wipe the history, which keeps the history useful as a record. `main` builds the purge function, because it owns every store a purge reaches.

Explicit timeouts are configured on the server (`ReadHeaderTimeout=5s`, `ReadTimeout=15s`, `WriteTimeout=30s`, `IdleTimeout=60s`) to defend the unauthenticated LAN-facing endpoint from slowloris-style attacks. POST handlers that accept JSON bodies wrap `r.Body` in `http.MaxBytesReader` (64 KiB) so an attacker cannot exhaust memory by streaming an unbounded payload.

Reloads are single-flighted by a closure in `cmd/s-hole/main.go` that the periodic refresh timer, the API, and SIGHUP share. A reload re-reads the DoT certificate (when DoT is on), then refreshes the blocklists; a certificate that fails to load does not skip the blocklist refresh. The closure returns `true` synchronously if no reload was running and it started one (work proceeds asynchronously in a goroutine), or `false` if a reload is already running or shutdown has started. A request that gets `false` during a pass is queued: the running reload does one more pass when it finishes, and any number of requests during one pass queue a single follow-up. Without the queue, a `systemctl reload` from a certbot deploy hook that arrived during a blocklist download was dropped, so the new certificate waited for the next timer reload (b/061). Once shutdown has started, a queued pass is dropped and a new request starts no pass; the closure logs `reload refused during shutdown`. Shutdown closes the gate under the closure's mutex before it waits, so the bounded reload wait covers at most the pass in flight (b/070). `POST /api/reload` surfaces the boolean as `"reload triggered"` vs `"reload queued"`. Centralising the gate in the closure rather than in `api.Server` ensures the periodic timer cannot bypass it.

State-changing admin requests leave an audit line in the application log. An allowlist add or remove logs the domain at `Info`. It logs the requester address only while `query_log.mode` records queries, masked by `query_log.clients` (`querylog.MaskClientIP`), so the defaults log no address: under `"none"` the `clients` setting gives no warning, so it must not record more. It is the one place the application log names a domain. A purge logs that it ran. Each reload logs its trigger source: `via API`, `via timer`, or the existing SIGHUP `reload signal received` line. The admin API is unauthenticated on the LAN, so an allowlist change un-blocks a domain for the whole network. The log is the record of who changed what and when. slog writes it to stdout (journald captures it under systemd, and the Windows Event Log captures it under the SCM), and s-hole keeps no separate audit store.

Each metric also carries a `# HELP` line on the endpoint itself; this table is the canonical prose reference. Counters only rise; gauges rise and fall. Some metrics appear only when the relevant feature is enabled (noted below).

|---|---|---|

| `shole_blocked_total` | counter | Queries that matched the block set and got a sinkhole reply. |
| `shole_cname_blocked_total` | counter | Queries whose name is on no list but whose reply has a CNAME target on the block set, so they got a sinkhole reply (CL 117). A subset of `shole_blocked_total`. |

| `shole_cache_hits_total` | counter | Responses served from the in-memory cache. |
| `shole_forward_failures_total` | counter | Queries s-hole could not resolve: no upstream gave a usable reply, or the forward limit was reached, so s-hole synthesized SERVFAIL. Points at the environment or config (upstreams down, a bad address, a broken network path, too tight a deadline). |

| `shole_cache_misses_total` | counter | Cache misses: the query went on to the forward step (sent upstream, or SERVFAIL at the forward limit). Present only when caching is enabled. |

| `shole_blocklist_source_size{url}` | gauge | Domains one source contributed, before dedup, so the per-source samples sum to more than `shole_blocklist_size`. One sample per configured source. |
| `shole_blocklist_source_stale{url}` | gauge | 1 while a source is served from its on-disk cache after a failed fetch (or has never loaded), else 0. |
| `shole_allowlist_size` | gauge | Domains in the runtime allowlist. |
| `shole_dot_certificate_expiry_timestamp_seconds` | gauge | Unix time when the DNS-over-TLS certificate being served expires, so an alert can compare it with `time()`. Present only when `dns.dot_listen` is set. |
| `shole_dot_certificate_reload_failures_total` | counter | Reloads whose DoT certificate files did not load; s-hole kept serving the previous certificate. Present only when `dns.dot_listen` is set. |

The three runtime gauges are read from the sampled `runtime/metrics` API, once per scrape, so a scrape never triggers a stop-the-world pause. They are read at scrape time only, never on the query path.

How the query counters relate (read them together, not as one number):

- `shole_queries_total` = `shole_blocked_total` + `shole_local_ptr_total` + `shole_local_names_total` + `shole_cache_hits_total` + forwarded, where forwarded is the remainder (it has no counter of its own; it includes the queries that got SERVFAIL at the forward limit, which were not sent upstream). A query blocked through a CNAME target is in `shole_blocked_total`, not in the cache hits or the remainder, although it read the cache or went upstream.
- `shole_cname_blocked_total` is a subset of `shole_blocked_total`.
- `shole_cache_hits_total` + `shole_cache_misses_total` covers only the queries that reached the cache; a query blocked by its name, a local-PTR query, or a local-name query never does. A query that a cached reply's CNAME target blocks is in neither. A query that the CNAME target of an upstream reply blocks is in `shole_cache_misses_total` only.
- `shole_forward_failures_total` and `shole_upstream_errors_total` are subsets of the forwarded remainder, and `shole_forward_limited_total` is a subset of `shole_forward_failures_total`.
- The `shole_upstream_transport_failures_total` samples sum to at least `shole_forward_failures_total` (equal only with a single configured upstream): a transport failure bumps the per-upstream counter but becomes a forward failure only when failover to every other upstream also fails, so with two or more upstreams a failure that failover recovers adds to the per-upstream sum without adding a forward failure. `shole_upstream_errors_total` (a relayed error response) and `shole_upstream_transport_failures_total` (could not reach the upstream) are named apart on purpose so they do not read as synonyms.

### Observability and Logging

Logging is structured via `log/slog`. Each package-level logger comes from `logging.For("<name>")`, which tags every record with `pkg=<name>` (`main` builds its `pkg=main` logger with `slog.With` after `setupLogger`), so a search on the log stream separates the `main`, `blocklist`, `dns`, `api`, `querylog`, and `stats` messages (the `config` package does not log; `main` logs its problems). A `For` logger looks up `slog.Default()` for each record. A package-level `slog.With` would bind slog's initial handler at package init, before `main` installs its own; the record then went through the `log` package into the new handler, formatted twice and always at level INFO (b/062). The default handler is text on stdout (`time=… level=… msg=… key=value`); `S_HOLE_LOG_FORMAT=json` switches to JSON, which is what most container/log-aggregation pipelines expect. Under systemd, stdout is the journal: `logging.StdoutIsJournal` compares `JOURNAL_STREAM` with the device and inode of stdout, as systemd.exec(5) advises, because a terminal started from a systemd user session can inherit the variable. In the journal, each line starts with its syslog priority (`<3>` to `<7>`), which journald removes and stores, so `journalctl -p warning` shows only warnings and errors. Text lines there drop the `time=` field, because journald records the time; JSON lines keep it. A message says what happened (`config load failed`, not `config`). A `hint` field says what to check, when s-hole knows. Every `stats_interval`, `stats.Counter.Log` writes one `msg=stats` line with the uptime only; the counters and the top-N lists stay on the dashboard, `/api/stats`, and `/metrics`. `docs/TROUBLESHOOTING.md` maps the common problems to the lines they produce. A Windows service process has no console, so a stdout handler would discard every line. When `service.IsWindowsService()` reports the process was launched by the SCM, `setupLogger` routes slog to the Windows Event Log instead (source `s-hole`, mapping `Info`/`Warn`/`Error` to the three Event Log severities); if opening the source fails it falls back to the stdout handler, so the process is never left with no logger. The event-log handler drops the time and level from the message text because the Event Log records both itself. This is the application log only; the per-query `ALLOW`/`BLOCK` stream is the separate `FileLogger` (`query_log.file`).

The application log carries no more than the query log (CL 93, b/078, CL 99): a record from the DNS path never names a domain or a client, under every `query_log.mode`. Unresolved queries and failed reply writes are summarized once a minute (`queries could not be resolved`, `replies could not be sent`; see DNS Server), and an error from a client connection is logged through `redact.NetError`, which removes the socket addresses. net/http's own lines from the admin server (a handler panic) go through `newErrorLog` (`errorlog.go`), which logs them through the `api` logger at ERROR as `admin HTTP server error` and replaces every IP address with `client` (b/103). The periodic stats line holds the uptime only: the difference between two lines with query counts would give an activity timeline in the journal, which purge cannot reach (b/098). Every setting that is less private or less secure than its default (`config.Warnings`) gives a `privacy warning` line at `-check-config` and at startup, and `main`'s `privacyReport` repeats them, with the stale-row check, plaintext fallbacks, and refused queries since the last line, as one `privacy and security warnings in effect` line after every stats line. These warnings cannot be turned off. At startup and hourly, `runResolverCheck` checks whether the host uses s-hole as its own resolver (`/etc/resolv.conf`, or systemd-resolved's server list behind its stub), and warns when that starts: while s-hole is down such a host cannot resolve, download blocklists, or reach its time server.

Operational diagnostics ship over two surfaces:

- **`/healthz`**: a tiny endpoint that returns 200 as long as the HTTP server is responsive. Liveness only; it deliberately makes no downstream call so a flaky upstream cannot cause the container orchestrator to restart the process.
- **`/readyz`**: a readiness probe that returns 200 once `store.Len() > 0` (the blocklist has loaded at least one entry) and 503 otherwise. Pairs with `/healthz` to give a Kubernetes-style probe split: don't restart, but do route traffic away while the initial blocklist download is in flight.
- **`/metrics`**: Prometheus text exposition (format `0.0.4`) covering query counts, refused queries, forward-limit rejections, cache activity and back-pressure, blocklist size and per-source health (URL labels redacted), allowlist size, upstream failures and plaintext fallbacks, query-log back-pressure, the DoT certificate (when DoT is on), and Go runtime gauges (goroutines and heap, read from the sampled `runtime/metrics` API for process leak and heap-growth watching). The Metrics reference table above lists every metric with its type and meaning. We hand-roll the exposition rather than pulling in `prometheus/client_golang` to keep the dependency graph small.
- **`/debug/pprof/*`**: the six standard `net/http/pprof` handlers (index, cmdline, profile, symbol, trace, plus the typed profiles under the index). Registered only when `admin.pprof: true` is set in config (or `S_HOLE_ADMIN_PPROF=1`). Off by default; required for live CPU/heap profiling during incident response. Enabling it also turns on mutex and block profiling (`runtime.SetMutexProfileFraction` / `SetBlockProfileRate`, CL 53), which stay off in the Go runtime by default, so `/debug/pprof/mutex` and `/debug/pprof/block` report the lock contention on the RWMutex-guarded hot path; both sample rather than record every event, so the cost is paid only while pprof is on. It is one of the privacy and security warnings, logged at startup and with every stats line while it is on.

Periodic `runTicker` goroutines (stats print, blocklist refresh) are wrapped in `recover()`. A panic inside the ticker function is logged with its goroutine stack and the next tick still fires, so a transient parser failure no longer silently freezes the refresh loop. `runTicker` also honors an application-wide `context.Context` that `doStop` cancels first, so the tickers unwind cleanly rather than depending on `os.Exit` to reclaim them.

### Startup Network Hint

On startup, `cmd/s-hole/main.go` calls `printNetworkHint`, which enumerates the local interfaces via `net.Interfaces()`, keeps IPv4 addresses on interfaces that are up and are not loopback, link-local, or a container, VM, or VPN interface (Docker, libvirt, VirtualBox and VMware host-only networks, LXC/LXD/Incus, Podman, Kubernetes network plugins, WireGuard, Tailscale, ZeroTier, tun/tap; matched by name, because their addresses are ordinary private ones, b/059), and prints a bordered box listing the DNS server address for each remaining address. When `dns.listen` names one address, the box shows only that address, with "(this machine only)" for a loopback address or `localhost` (b/088). The Admin UI line honors where the API is actually bound (T4): with the localhost-only default it prints a single `http://127.0.0.1:<port> (this machine only)` line rather than advertising LAN URLs that would refuse connections. With DoT on, one more line names the DoT port and not an address, because a DoT client connects by the hostname in the certificate, not by IP. This removes the need for the operator to manually discover the machine's IP when configuring the router's DHCP DNS field. `deploy/install-linux.sh` prints the same banner at the end of installation from `ip -4 -o addr show up scope global` with the same interface-name filter (falling back to `hostname -I`), and the same `admin.listen`-aware Admin UI logic. The script reads `admin.listen` from the `config OK` line of `-check-config`, so the binary's own parser reads the config. After the banner it prints a reminder to keep the s-hole host off s-hole, with a warning when the host already uses itself as its resolver.

### Configuration (`internal/config/`)

All configuration lives in a single YAML file with four sections (`dns`, `blocking`, `query_log`, `admin`) and a top-level `stats_interval` (format 2.0, CL 93). Every setting has a default, so the minimal valid config is an empty file, and every default is the most private choice. The config is read once at startup; the running service does not re-read the file, so a config change takes effect on the next restart.

`Load` decodes the file into a `yaml.Node` tree and walks it against one table of settings (`settings()`): each entry names its key path, a parser that stores a value only when it is valid, and a printer for messages. That gives four properties a struct decode could not:

- **A mistake never stops startup or weakens privacy.** An unknown key, a key renamed since 1.x (each named with its 2.0 key), a 1.x environment variable, an unknown `S_HOLE_*` variable, a duplicate key, and an invalid value are each a `Problem`, and the setting keeps its default (or its YAML value when only the environment variable was wrong). Because every default is the most private value, a typo such as `query_privcy: drop` can only fall back to the private behavior, never to a less private one (b/079). Startup logs each problem as a WARN and runs; `-check-config` fails on any problem, so the operator catches it before a restart.
- **Only three mistakes are fatal**, because nothing can work without the setting: a malformed `dns.listen`, an upstream list in which every entry is malformed, and a DoT certificate pair that does not load while DoT is on. A malformed `dns.dot_listen` turns DoT off with a problem.
- **An explicit zero is honored.** Absent keys keep their defaults and present keys are parsed, so `dns.cache_entries: 0` and `blocking.reply_ttl_seconds: 0` work without the pre-decode seeding that the 1.x loader needed (T1).
- **The environment uses the same parsers.** A scalar setting's variable is `S_HOLE_` plus its key path in upper case with dots as underscores (`S_HOLE_QUERY_LOG_MODE`). Lists and maps have none.

`dns.local_domains` entries are normalized (a leading `.` or `*.`, a trailing dot, and the letter case are removed), and a single label (`fritz`) is valid. Unlike the other list settings, an empty or null entry is a problem: it is most likely a domain the operator meant to add (CL 94).

The upstream check is shape only (`net.SplitHostPort`, or `url.Parse` for a DoH URL): it resolves no name and dials nothing, so it adds no network call and does not probe an operator-supplied address (which, wired to the unauthenticated admin API, would be an SSRF and LAN-scanning primitive). A DoH URL is stored in normalized form, so an uppercase `HTTPS://` reaches the forwarder as the `https://` prefix it matches (b/067). A malformed entry is shown through `redact.URL`. `UpstreamNotes` returns INFO notes for a single upstream, a DoH-only list (no fallback when TLS fails, for example on a wrong clock), and a mixed list (plain is a fallback). When `dns.dot_listen` is set, `Load` also loads the certificate pair with `tls.LoadX509KeyPair`, which reads two local files and makes no network call.

`Warnings` returns one `Warning` (key, detail, hint) for each setting that is less private or less secure than its default: `query_log.mode` other than `"none"`; while the mode records queries, `clients` other than `"drop"`, a `file` output, and with a database a retention of 0 or more than 7 days; a non-loopback `admin.listen`; `admin.pprof`; `dns.local_ptr` off; an upstream list with no DoH entry; `blocking.cname_inspection` off; and an `http://` blocklist. These are choices, not mistakes, so `-check-config` prints them without failing.

### Packaging and Deployment (`internal/service/`, `deploy/`, `Dockerfile`)

s-hole supports these deployment targets:

**Windows Service.** `internal/service/svc_windows.go` (build tag `windows`) integrates with the Windows Service Control Manager via `golang.org/x/sys/windows/svc`. The binary accepts `-service install|uninstall|start|stop` flags. When launched by the SCM, `svc.IsWindowsService()` is detected and the process enters the SCM event loop; a stop control from the SCM calls the same `doStop` function as a Ctrl+C in interactive mode. The SCM starts every service in `C:\Windows\System32`, so before it loads the config, main changes to the config file's directory (`chdirToConfigDir`), then loads the config through the absolute path that it returns (b/069); the sample config's relative paths then resolve next to `config.yaml`, not in the system folder (b/066). `Execute` also watches the DNS server: if `Start` returns without a stop request, the service answers no queries, so `Execute` runs `doStop` and returns a service-specific exit code instead of reporting Running (b/065). `-service install` sets three restart actions 5 s apart and `SetRecoveryActionsOnNonCrashFailures(true)`, because the SCM otherwise applies recovery actions only to a crash, not to a stop with a non-zero exit code. The service runs as its own virtual account, `NT SERVICE\s-hole`, with an unrestricted service SID; before CL 93 it ran as LocalSystem (b/086). Install gives the config folder (the service's working directory, where its data files land) a protected access list: SYSTEM and Administrators full control; the service account read and execute on everything, plus "add file" and "add subfolder" on the folder itself; and CREATOR OWNER full control, so the service can change and delete only the files and folders that it creates (CL 107, b/104). Before CL 107 the service account had "modify" on the whole folder, binary and `config.yaml` included, so a compromised service could replace the binary that an administrator runs later. A Go file mode such as `0600` does not restrict access on Windows (it only sets the read-only attribute), and a new folder under `C:\` inherits modify rights for every signed-in user, so the folder access list is what protects the history there. Install checks before it changes anything: it refuses when the service account could change or replace the binary (the access lists of the binary, its folder, and every folder above it, evaluated for the service SID and the groups that `whoami /groups` shows for the service account), when the binary is in the config folder, when `config.yaml` is missing, and when the config folder is a shared folder (a drive root, the Windows folder or a folder in it, Program Files, ProgramData, the user's profile folder, or the folder that holds the profiles). After it sets the access list, it also refuses when the config folder holds a link or an item that an account other than SYSTEM, the Administrators group, the service, or the installing account owns: before the install, every user can add files to a new folder in ProgramData, and a file's owner can still change its access list. The documented layout is `C:\Program Files\s-hole` for the binary and `C:\ProgramData\s-hole` for the config and the data. The service SID is computed from the service name (`S-1-5-80-` and the SHA-1 of the upper-case name), so the folder gets its access list before the service exists, and a failure stops the install. The access-list rules (`internal/service/acl.go`) have no build tag and are unit-tested on Linux; only reading and writing real access lists is Windows-only. `internal/service/svc_other.go` (build tag `!windows`) provides no-op stubs with the same function signatures so `cmd/s-hole/main.go` requires no platform conditionals of its own.

Because a service has no console, `-service install` also registers a Windows Event Log source (`eventlog.InstallAsEventCreate`) and `-service uninstall` removes it, and `setupLogger` routes slog to that source when the SCM launches the process (see the logging note above). The handler logic lives in `internal/service/eventlog.go` behind a small `eventWriter` interface with no build tag, so it compiles and is unit-tested on Linux with a fake writer; only the `eventlog.Open` constructor (`eventlog_windows.go`, with a `!windows` stub in `eventlog_other.go`) is platform-specific.

**Linux systemd.** `deploy/s-hole.service` runs as a dedicated `s-hole` system user. `AmbientCapabilities=CAP_NET_BIND_SERVICE` allows binding port 53 (and 853 for DoT) without root. `ExecReload` sends SIGHUP, so `systemctl reload s-hole` re-reads the DoT certificate and the blocklists. `ProtectSystem=strict` and `NoNewPrivileges` limit the blast radius of any exploit, and `UMask=0077` makes every file s-hole creates owner-only (s-hole also sets a `077` umask itself on Unix, for a run from a terminal or in Docker). The unit also sets a sandbox (CL 106): a private `/dev`, and a private `/tmp` that is read-only (`ReadOnlyPaths=/tmp /var/tmp`), so a query path under `/tmp` fails to write as before; no access to kernel tunables, modules, logs, cgroups, the clock, or the hostname; a `/proc` that shows only s-hole's own process; the `@system-service` system-call filter without `@privileged` and `@resources`; and `RestrictAddressFamilies` limited to Unix, IPv4, IPv6, and netlink. `AF_NETLINK` stays because `net.InterfaceAddrs` reads the interface subnets for the LAN check through it. Without it, the check refuses the devices on a public IPv6 LAN prefix, and `lan.go` logs the failed read. The installer makes `/var/lib/s-hole` `0700` and gives it and its files to the `s-hole` user (`chown -R`), so a reinstall can use data that an uninstall kept (b/092). `deploy/install-linux.sh` automates the full installation; the systemd unit is embedded as a heredoc inside the script, so only the script itself (plus the binary and config) needs to be copied to the target machine. A companion `deploy/uninstall-linux.sh` reverses it (service, unit, binary, config, and system user/group). It keeps the data directory, owned by root with mode `0700` (the deleted user's numeric ID could go to a later system user), unless `--purge` is given; `--purge` first runs `s-hole -purge`, so data outside `/var/lib/s-hole` goes too. It restores the `systemd-resolved` stub (removing the `DNSStubListener=no` drop-in) only under `--restore-resolved`, and prints, but does not run, the command that clears the system journal.

**Docker.** A multi-stage `Dockerfile` builds a statically linked binary (`CGO_ENABLED=0`, `-trimpath`) in a `golang:1.26.X-alpine` builder stage pinned by digest to one patch of the go.mod release (an unpinned `golang:alpine` built the v1.0.0 image with a different Go release than the archives, b/087; the `alpine` runtime image is pinned by digest too, CL 108). That `golang` tag is the one Go pin of the project: CI, the weekly scan, and the release archives read it through `.github/go-version.sh`, so the archives and the image build with the same Go release, and a Go patch arrives as a Dependabot `docker` pull request (while the `golang` image still publishes the pinned Alpine variant; the Dockerfile header covers the move to a new one). `actions/setup-go` alone would follow GitHub's version list, which can lag a Go security release by weeks. The builder cross-compiles from `$BUILDPLATFORM`, so a multi-arch build runs no compiler under QEMU. The `Dockerfile` copies the binary into an `alpine` runtime image for SSL certificate access (needed for HTTPS blocklist downloads and DoH). The process runs as UID 65532, not root; a file capability (`setcap cap_net_bind_service`) lets it bind port 53 (and 853 for DoT), also under `--network host`. The capability is set in the build stage, and BuildKit's `COPY` keeps it. In the runtime stage, `setcap` would change the file that the `COPY` layer added, and the image would store the binary twice (CL 103). A `HEALTHCHECK` runs `s-hole -healthcheck`, which asks `/readyz` on the admin address. Host networking is the recommended Linux setup: s-hole sees real client addresses (for Top Clients and the LAN-only check) and the localhost `admin.listen` default works unchanged. The binary lives on `PATH` (`/usr/local/bin/s-hole`), deliberately outside the `/app` directory, which is declared a `VOLUME` for config and database persistence, since a bind mount over `/app` would otherwise shadow a binary placed there (b/039). The README's `docker run` examples add `--read-only`, `--security-opt no-new-privileges:true`, and `--cap-drop ALL --cap-add NET_BIND_SERVICE` (CL 106). `--cap-drop ALL` alone fails at exec, because the binary's file capability cannot be granted. The bridge example publishes port 53 on an explicit IPv4 address: published without an address, Docker's proxy relays IPv6 queries into the IPv4-only bridge with the gateway (`172.17.0.1`) as the source, and the LAN check admits that private address.

**Cross-compilation.** A `Makefile` provides `make pi` (arm64, for a 64-bit OS), `make pi32` (armv7, for a 32-bit OS), and `make linux` (amd64) targets; a 64-bit ARM kernel also runs the armv7 build, and the installer accepts it there (b/084). All produce stripped binaries (~10–17 MB) with no host toolchain requirements beyond the Go compiler. The Makefile also exposes the standard development targets (`make check`, `test`, `test-race`, `bench`, `lint`, `fmt`, `vet`, `install`, `version`); `make help` lists the full set.

**Build identity.** `internal/version` holds three vars (`Version`, `Commit`, `BuildDate`) written at link time via `-X` ldflags. The Makefile populates them from `git describe`, `git rev-parse`, and the current UTC timestamp; the Dockerfile accepts them as `--build-arg`; CI fills them from the GitHub Actions context. Source builds without those flags fall back to placeholder values (`dev` / `unknown` / `unknown`), which is acceptable for `go install` use. `s-hole -version` prints the full identity at any time.

## Alternatives Considered

### Use Pi-Hole directly

Pi-Hole solves this problem well for Raspberry Pi / Debian deployments. We ruled it out because: it requires a full Linux install, cannot be deployed as a single binary on Windows or macOS, and the codebase (a PHP web UI + a C DNS daemon fork) is not easily auditable or modified.

### Use CoreDNS with a blocklist plugin

CoreDNS is production-grade and has a plugin ecosystem. The `ads` plugin does DNS sinkholing. We ruled this out because the goal is also to learn by building: using CoreDNS would replace the implementation with configuration. CoreDNS also pulls in a large dependency tree.

### Use `NXDOMAIN` as the default sinkhole response

`NXDOMAIN` is semantically correct ("this domain does not exist") and is what Pi-Hole uses in some modes. We chose `0.0.0.0` as the default because some client applications (notably Windows Update, certain game launchers) interpret `NXDOMAIN` as a network error and surface it to the user, while a connection to `0.0.0.0` fails silently at the socket layer. Both modes are available via `blocking.reply`.

### In-process blocklist update via a signal

Linux is the primary deployment target: the Raspberry Pi optimisations, the hardened systemd unit, and the Docker image are all built around it; Windows is supported (`-service install` and SCM integration) but is not the design's centre of gravity. Accordingly, `SIGHUP` is wired up as the conventional reload gesture on every non-Windows build: `kill -HUP $(pidof s-hole)` (or `systemctl reload s-hole`) triggers the same single-flight reload as `POST /api/reload`. That reload re-reads the DoT certificate when DoT is on and re-downloads the blocklists from the URLs read at startup; it does not re-read `config.yaml`, so a config change takes effect on the next restart. Operators get the muscle-memory behaviour even when the admin API is disabled or firewalled.

The implementation lives in two tiny build-tagged files (`cmd/s-hole/signals_unix.go` and `cmd/s-hole/signals_windows.go`) so `cmd/s-hole/main.go` itself contains no platform-specific code. On Windows, `reloadSignals()` returns nil and the only signals notified are SIGINT/SIGTERM. The SCM is the canonical lifecycle control there, and POST /api/reload remains available for an on-demand reload.

### LRU eviction for the DNS cache

LRU eviction would make better use of cache capacity by removing the least-recently-used entries when full. We chose drop-on-full (with expired-slot reclaim on a full insert) because: (a) home DNS traffic is dominated by a small hot set of domains that will be re-cached quickly, (b) the cache is sized generously (default 2000 entries) relative to typical household domain diversity, and (c) LRU requires a move-to-front on every `Get`, a write on the read path. `Get` is a bare `RLock` read today, so LRU would turn every cache hit into an exclusive `Lock` and serialize readers, the contention `BenchmarkCache_Get_Parallel` exists to catch; for a read-dominated cache that is the wrong trade. If recency ever mattered, a scheme that keeps `Get` read-only (CLOCK or SIEVE) would be the way in, not LRU. Whether even that is needed is now measurable: `shole_cache_dropped_total` counts inserts refused because the cache was full of live entries, so the decision to add a smarter eviction policy is gated on that metric showing sustained pressure (see the pending decision in `docs/ROADMAP.md`), not on speculation about thrashing.

### `kardianos/service` for cross-platform service management

`kardianos/service` provides a unified API for Windows, systemd, and launchd service registration. We chose to implement only Windows SCM integration (using `golang.org/x/sys/windows/svc`) and provide a static systemd unit file for Linux, because: the library adds a dependency, the systemd unit gives more control over hardening flags, and launchd (macOS) is not a target deployment platform.

## Security Considerations

- **DNS amplification and open resolution:** s-hole answers LAN sources only (see DNS Server, step 0) and refuses everything else, which also keeps outsiders from probing the cache. There is no rate limit for each client. Global limits apply (512 queries waiting for an upstream, 256 plain-TCP and 256 DoT connections; see DNS Server). Do not expose port 53 on a public address.
- **Blocklist URLs:** URLs come from operator-controlled config, not from user input. s-hole warns about an `http://` URL, because anyone on the network path can change a list fetched over plain HTTP and unblock trackers. That warning checks only the configured URL, so the downloader also refuses a redirect from an HTTPS request to a URL that is not HTTPS, at any hop (`checkRedirect`, b/097). The refused request is not sent; the download fails, logs `blocklist redirect refused` with both URLs through `redact.URL`, and takes the stale-cache fallback (with no cached copy, the list fails). A redirect to another HTTPS host is followed (a GitHub release download redirects to a CDN host), with Go's limit of 10 requests (9 redirects).
- **Stored data permissions:** s-hole creates the query database, its `-wal` and `-shm` files, the query log file, and the blocklist cache with mode `0600` (umask `077`, `UMask=0077` in the unit), tightens existing files, and the installer makes the data directory `0700` (b/076). On Windows the config folder gets an access list at service install that allows only SYSTEM, the Administrators group, and the service, which can write only the files that it creates. The Docker image runs as UID 65532.
- **Port 53 binding:** Binding to port 53 requires elevated privileges (root / Administrator) or `CAP_NET_BIND_SERVICE`. The systemd unit grants the capability without running as root. The same capability covers port 853 for the opt-in DoT listener. On Windows, the service runs as its own virtual account; binding port 53 needs no special right there. Port 53 is non-negotiable for deployment: DHCP options, `resolv.conf`, and OS network settings identify DNS servers by IP address only (there is no port field anywhere in that chain), so every client on the LAN sends to `<ip>:53` unconditionally. High ports (e.g. 5354 in the CONTRIBUTING smoke test) are strictly a development convenience for queries addressed to the server explicitly.
- **Admin UI:** The HTTP server has no authentication. The default `admin.listen` is `127.0.0.1:8080`, and s-hole warns while it listens on another address. Loopback does not separate the local accounts: every account and process on the host can read the history, purge it, and change the allowlist through the API. So the owner-only file mode protects the database only while s-hole is stopped. The server uses plain HTTP, so on a LAN address the history crosses the network in clear text. ROADMAP #42 requires authentication on loopback for the data routes and TLS for a listener that is not loopback. The server refuses requests addressed to a foreign hostname (DNS rebinding) and requests from another site (except a link that opens the dashboard; on the default loopback bind, because browsers send Fetch Metadata only to trustworthy origins), requires JSON on JSON endpoints, sends `no-store` and a CSP that allows no inline script, enforces conservative timeouts (`ReadHeaderTimeout=5s`, `ReadTimeout=15s`, `WriteTimeout=30s`, `IdleTimeout=60s`), and caps POST bodies at 64 KiB. A purge is accepted only from the s-hole host.
- **`/healthz`, `/readyz`, and `/metrics`** are unauthenticated alongside the rest of the API. They hold aggregate numbers only (no domain or client label; URL labels are redacted), and are intended for local Prometheus / probe access; do not expose them to the public internet. A Prometheus server that scrapes them keeps the counters over time, which show when the household is active; s-hole cannot delete that history (`PRIVACY.md`).
- **`/debug/pprof/*`** when enabled (`admin.pprof: true`) reveals goroutine stacks, heap layouts, and binary symbols, which are useful for incident response and dangerous if exposed to the LAN. Enabling it also activates mutex and block profiling, which add per-lock bookkeeping to every goroutine while on. It is one of the repeating warnings while it is on.
- **`client_names` labels** (CL 73) add device-identity PII to the unauthenticated admin API: an IP that a reader had to correlate becomes a named device. This opens no new hole (there is no new endpoint and no wire-parsed input; the map is parsed once at config load), and it cannot exceed the active `query_log.clients` granularity, because the label is resolved from the stored (already masked) client value: under `subnet` only a CIDR or network-address key resolves, and under `drop` nothing does. Labels are HTML-escaped in the UI, so an operator-supplied label cannot inject markup.
- **Secrets in URLs:** user info and query strings in blocklist and upstream URLs are hidden wherever s-hole shows a URL (`redact.URL`): log lines, errors, `/metrics` labels, and `/api/stats`.

## Privacy Considerations

s-hole sees every DNS query on the LAN, so a query log is the browsing history of every person in the household, with times that show when each person is home and awake. Privacy is the first design rule (CL 93); `PRIVACY.md` is the user-facing inventory of every place s-hole keeps or sends data.

The threat model covers: devices and guests on the LAN that can reach the admin API; other local accounts and services on the s-hole host; web pages in the operator's own browser (rebinding, cross-site requests, framing); the network path to the upstreams and the upstream operators; stores that outlive s-hole's retention (journald, container logs, Prometheus, backups, browser caches and downloads); and forensic access to the SD card or a backup image. Root on the host and a deliberately hostile operator config are out of scope.

The rules that follow from it:

- **Collect the minimum by default.** `query_log.mode: "none"`, `clients: "drop"`, `database` and `file` off, retention 7 days. Each opt-in gives a repeating warning.
- **The application log carries no more than the query log** (b/078), and query lines never go to standard output unless the operator asks (b/075), because s-hole cannot delete what the journal keeps.
- **Retention and purge erase.** `secure_delete` and the TRUNCATE checkpoint remove deleted rows from the files (b/077); s-hole overwrites the WAL with zeros before SQLite truncates or deletes it (CL 110); the purge reaches every store s-hole writes, overwrites the query log file with zeros before it empties or deletes it and, when s-hole is stopped, the database files before it deletes them (CL 105), and the report names what it cannot reach (standard output). On flash storage and a copy-on-write file system the zeros can go to new blocks.
- **Fail closed.** A config mistake falls back to the most private value; an unknown client mode drops the client; a failed log-file open turns the output off (b/079).
- **Keep LAN data on the LAN.** Private reverse lookups are answered locally, and the upstream hop is encrypted by default. The upstream gets a fresh query with only the question and a few flags, never the client's EDNS options (cookie, Client Subnet) or query ID, and names that are local by definition (`printer`, `nas.lan`) go only to LAN upstreams (CL 94, see "Minimal upstream query and local names").
- **Respect the device's own privacy choices.** A device that uses its own encrypted DNS bypasses s-hole; s-hole does not try to stop it.
- **Show what is stored.** The dashboard header, the warnings panel, and the startup log state what is recorded and for how long.

The `query_log.clients` setting (CL 72) controls how much of the client IP is stored: `full`, `subnet` (host bits masked), or `drop` (no client). The `client_names` map (CL 73) is a read-only display label resolved against that stored value, so it tracks the privacy level rather than defeating it: a host label resolves only under `full`, a subnet/CIDR label under `subnet`, and nothing under `drop`. A change to a stricter setting applies to new rows only; s-hole reports the older rows (`StaleRows`) and never rewrites them on its own.

## Testing Strategy

- **Unit tests:** Every implementation package under `internal/` ships a `*_test.go` file. Coverage targets (checked in review, not a strict CI gate): `stats`, `config`, `version`, and `redact` 100 %; `logging` ≥ 95 %; `cache` ≥ 94 %; `api`, `blocklist`, `dnsserver`, and `querylog` ≥ 85 %. The `cmd/s-hole` bootstrap (the `main()` wiring and signal-dispatch goroutine) and the platform-specific `internal/service` glue run below these targets because they need a running binary or Windows; both are exercised by manual smoke tests. Run `go test -cover ./...` for the current numbers.
- **What the unit tests exercise:** `blocklist.Store` lookup, suffix (subdomain) blocking and allowlist suffix precedence, `IsAllowlisted` (suffix walk, runtime changes, no allocation), atomic `Replace`, the `Explain` diagnostic walk (decision plus matched block/allowlist entries), `parseHostsFormat` against the hosts, plain-domain, and wildcard (`*.example.com`) formats and its skipped-line count, the localhost-name skip in every format, the unread-list WARN (`blocklist has no domains`, `blocklist lines skipped`: the skipped > read threshold, every load path, never for a - **Regression traceability:** many of these are regression tests pinned to specific bug numbers (b/005, b/007, b/010, b/017, b/018, b/021, b/022, b/024, b/026, b/028, b/029, b/032, b/033, b/034, b/035, b/036, b/038) or staff-review IDs (R3, R4, R5, R6, R8, R9, R12, R13, R14, R15, R16, R17, R18, R19, R26, R27, R31, R32, R33, R34, R35, R36, R37, R38, T1–T6). The `b/NNN` and `R/S/T NN` identifiers appear in the relevant test comments and, for bugs, in `docs/BUGS.md`.
- **DNS handler unit tests** use a `fakeWriter` implementing `dns.ResponseWriter`; the cache-hit path is exercised by pre-populating the in-memory cache, bypassing the upstream resolver entirely. The forwarder tests use a real in-process miekg/dns server on `127.0.0.1:0` so the production code path (including `dns.Client.ExchangeContext`) is exercised end-to-end.
- **Server lifecycle test** binds the production `dnsserver.Server` to a free port (UDP + TCP), confirms a real `dns.Client.Exchange` round-trips through the handler, and verifies `Shutdown` causes `Start` to return. Further tests pin that `Shutdown` frees every port even when it runs before or races `Start` (b/063), and that a listener that fails at runtime makes `Start` return its error while the others keep serving. The DoT tests (`dot_test.go`) also bind real listeners: a full UDP, TCP, and DoT server on free ports, queried over TLS.
- **Fuzz tests:** `internal/blocklist/fuzz_test.go` fuzzes `ValidDomain`, `parseHostsFormat`, and `cacheFilename`. The `ValidDomain` fuzz asserts that every accepted name has a valid shape (at most 253 characters; two or more non-empty labels of letters, digits, `-`, and `_`; no `-` at a label edge). The parser fuzz asserts that every emitted domain passes `ValidDomain`, and that the skipped count of an input equals the sum of its lines' counts; the filename fuzz asserts the result is platform-safe (no `/`, `\`, or `:`). Run with `go test -fuzz=FuzzValidDomain -fuzztime=30s ./internal/blocklist/`.
- **Integration test:** `internal/dnsserver/integration_test.go` wires the full stack (`blocklist.Store` + `cache.Cache` + `querylog.DBLogger` on a real SQLite file + `dnsserver.Handler` + `dnsserver.Server` on a free UDP port + a mock upstream) and exercises three real DNS queries (blocked, forwarded-and-cached, cache-hit). Catches wiring bugs (constructor arg order, nil dependencies, fan-out misconfig) that unit tests miss.
- **Benchmarks:** `BenchmarkStore_IsAllowlisted` and `BenchmarkHandler_ChainBlocked` (CL 117) cover the allowlist walk and the CNAME check that run for each served answer with a CNAME. The set covers the in-process request cycle (blocklist decision → cache lookup → reply construction) plus the stats record path and the periodic parse path. `BenchmarkStore_IsBlocked` and `BenchmarkStore_IsBlocked_Miss` run against a 100 000-entry store and guard against accidental O(n) regressions; the `_Miss` variant walks a deep, not-blocked name to the TLD (the suffix walk's worst case and the common allowed-query path). `BenchmarkCache_Get` (CL 32) measures the cache-hit path, whose cost and per-op allocations are dominated by the defensive `msg.Copy` and `decrementTTLs` walk. `BenchmarkHandler_ServeDNS` (CL 32) drives `Handler.ServeDNS` through the stub `ResponseWriter` on its `Blocked` and `Cached` sub-paths; all three CL-32 benchmarks call `ReportAllocs`. `BenchmarkCounter_RecordQuery` (CL 52) covers the per-query stats update; its `ManyDomains` sub-benchmark drives the top-N map past its cap so the prune path runs, which the handler benchmark never reaches because it reuses one domain. `BenchmarkCache_Set` (CL 52) covers the cache write path taken on a miss, the counterpart to `BenchmarkCache_Get`. `BenchmarkParseHostsFormat` (CL 52) covers blocklist parse throughput over a 100 000-line list, the startup and refresh path. `BenchmarkStore_IsBlocked_Parallel`, `BenchmarkCache_Get_Parallel`, and `BenchmarkHandler_ServeDNS_Parallel` (CL 53) run those read paths under `b.RunParallel`, the one-goroutine-per-query concurrency the handler runs in, so a lock-contention regression a serial benchmark cannot see (an exclusive `Lock` on a read path, or work moved under a mutex) shows up. `BenchmarkStore_Replace` (CL 53) measures the reload swap that rebuilds the blocked set under the write lock. `BenchmarkCache_Set_DropOnFull` and `BenchmarkCache_CleanupExpired` (CL 53) cover the two cache-maintenance paths the write benchmark skips: the copy-then-drop cost on a full cache, and the once-a-minute O(n) sweep held under the write lock. `BenchmarkDBLogger_Flush` (CL 53) measures the query-log batch commit, the single-connection drain budget (b/038) that bounds how fast the async writer clears its channel before `Log` starts dropping; `BenchmarkDBLogger_Log_Parallel` confirms the enqueue stays non-blocking under concurrent callers. The upstream-forwarding path is left unbenchmarked on purpose, because it is bounded by the network round-trip, not handler code. `make bench` runs each once as a regression smoke, not a measurement. The measurement and profiling workflow (benchstat, pprof, live `/debug/pprof`) is documented in `CONTRIBUTING.md`.
- **Goroutine-leak detection:** the `cache`, `querylog`, and `dnsserver` packages (the three that own long-lived goroutines: cache cleanup sweep; DBLogger batch-writer and retention-prune; UDP/TCP listeners and the optional DoT listener) run their suites under `go.uber.org/goleak` via a `TestMain` (`leak_test.go`). If any test leaves a goroutine running after it returns, the package fails. `blocklist` is deliberately excluded: its `httptest`-based tests can register transient keep-alive goroutines that would flake the check. goleak is a test-only dependency and is not linked into the shipped binary.
- **CI:** `.github/workflows/ci.yml` runs a `golangci-lint` job (the v2 release pinned by `GOLANGCI_LINT_VERSION` in the `Makefile`, with `gosec` and `nolintlint`, once for the Linux build and once with `GOOS=windows`), then `go mod verify`, `go build`, `go vet`, `go test -race`, single-iteration benchmarks, a `govulncheck` job (fails on any known CVE reachable from our code; also available locally via `make vuln`), and a cross-compile matrix (linux/amd64, linux/arm64, linux/armv7, windows/amd64) on every push and PR, with the Go release that the Dockerfile's `golang` image pins, a read-only token, and every action pinned to a commit SHA. Branch protection on `master` requires all checks to pass (`govulncheck` and `shellcheck` included) and PR branches to be up to date before merging. `.github/workflows/vulncheck.yml` runs `govulncheck` every week on `master` and, in binary mode, on the binaries of the latest release, so an advisory published after a release fails a visible run. `.github/workflows/release.yml` signs a build provenance attestation for each archive, the binary in it, and the container image, and the image carries an SBOM. GitHub CodeQL (default setup, a repository setting with no workflow file) analyzes the Go code, the workflows, and the dashboard script on each push to `master`, each pull request, and once a week. CodeQL is not a required check: its findings are code scanning alerts and do not block a merge.
- **CL 93 privacy tests:** a cold sub-agent wrote the privacy-hardening tests from the requirements (see `docs/cls/CL-93.md`): the config problems and warnings, owner-only file modes, erasure after prune and purge, the LAN-only check, the Host and cross-origin checks and security headers, log hygiene, the failure summary, the in-memory timeline, and the purge and health-check commands.
- **Manual smoke test:** `CONTRIBUTING.md` documents the full 8-step pre-release pass (probes → DNS behaviour → dashboard → allowlist round-trip → reload single-flight → stats/metrics cross-check → persistence + shutdown → purge). The network-level variant: configure a single device's DNS to the running instance, browse an ad-heavy site, verify blocked domains resolve to `0.0.0.0` and ads do not render, and on Linux verify `kill -HUP $(pidof s-hole)` triggers a refresh.
