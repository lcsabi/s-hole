# CL 117: Block trackers behind a CNAME (CNAME inspection)

## Description

s-hole now checks the CNAME targets in each answer that it serves. When the
queried name is on no list, but a CNAME target in the answer is, s-hole sends
the normal sinkhole reply for the queried name. This closes ROADMAP #14.

- `internal/dnsserver/cname.go` (new): `chainBlocked` checks the target of each
  CNAME record in the Answer section with `blocklist.Store.IsBlocked`. It does
  not check when inspection is off, when the reply is not NOERROR, or when the
  queried name is allowlisted.
- `ServeDNS` runs the check on a cache hit and after a forward. It records a
  query in the stats when the outcome is known, after the check, not before
  the cache. A CNAME block and a name block share one path (`writeBlocked`):
  the same reply, the same stats, and the same query-log row, with the block
  source.
- `blocklist.Store.IsAllowlisted` (new): the allowlist half of the
  `IsBlocked` suffix walk.
- `stats.Counter` has a new counter, `cnameBlocked`
  (`Summary.CNAMEBlockedCount`, `cname_blocked_count`).
- The query log records why a query was blocked: `querylog.BlockSource`
  (`BlockedByName`, `BlockedByCNAME`), a `block_source` column in the
  database (with a migration), `blocked_by` in `/api/queries` and in the
  exports, and a ` CNAME` marker on a BLOCK line of the query log file.
- `/metrics` has `shole_cname_blocked_total`. The dashboard shows the count
  under the Blocked card and a `BLOCK · CNAME` badge in the recent queries.
- New setting `blocking.cname_inspection`, default `true`. While it is
  `false`, `config.Warnings` reports it.

## Motivation

A tracker can hide behind a subdomain of the site that uses it. The site adds
`metrics.shop.example CNAME shop.example.tracker.example` and loads the
tracker from `metrics.shop.example`. The browser sees a first-party name, so
its third-party protections do not apply, and cookies for `.shop.example` go
to the tracker. No list can name every such subdomain, because each customer
of the tracker has its own. This is "CNAME cloaking". Dimova et al., "The
CNAME of the Game: Large-scale Analysis of DNS-based Tracking Evasion"
(PETS 2021), measured it on a large scale.

Before this CL, s-hole decided on the queried name only, before the cache and
the forward. The cloaked name is on no list, so s-hole forwarded it, cached
the chain, and relayed it. The upstream answer already holds the whole chain,
so s-hole can check the targets without a further lookup.

## Design decisions

- **Check the chain on every serve; cache the raw answer.** The upstream
  answer goes into the cache as before. The check runs after a forward and on
  each cache hit. A blocklist reload or an allowlist change then applies to
  the next query, also for a name in the cache. A repeated query for a
  cloaked name does not go upstream again, so the upstream sees it once per
  TTL, not once per query. Caching the sinkhole reply was the alternative; with
  it, a list change waits for the TTL.
- **Record the query when its outcome is known.** Before this CL,
  `RecordQuery` ran before the cache and the forward. A query that the chain
  blocks counts as blocked, not as a cache hit or a forward, so the call moved
  to each outcome. Every path still calls `RecordQuery` before the counter for
  its outcome (the LOAD-ORDER INVARIANT). `cnameBlocked` is a subset of
  `blocked`, so `Snapshot` reads it before `blocked`.
- **The allowlist wins.** If the queried name or a parent is allowlisted,
  the chain is not checked. This is the fix for a site that breaks: allowlist
  the name that the device asks for. A target that is allowlisted does not
  count, because `IsBlocked` applies the allowlist to it.
- **Only CNAME targets.** s-hole does not check the final A or AAAA address:
  it has no address lists, and a tracker on a shared CDN shares its addresses
  with other sites. A DNAME needs no check of its own: the resolver also
  returns the CNAME that it makes from the DNAME. The target of an HTTPS or
  SVCB record needs none: the client looks that name up through s-hole, which
  checks the name.
- **Default on, with a warning when off.** This follows the rule that every
  default is the most private option. Turning inspection off makes s-hole
  block less, so it is a `config.Warnings` case, like `dns.local_ptr: false`.
  The handler's own default (before `SetCNAMEInspection`) is on too.
- **Record the block source, never the target.** The maintainer decided that
  a blocked row says what matched (`block_source`). The row helps an operator
  find the cause when a site breaks. The column is an integer, so a later kind
  of block (pattern blocking, #25; Adblock lists, #43) adds a value and needs no
  new column. The default 0 means "the queried name", which is right for every
  row from an older build. The CNAME target is not recorded in the query
  history, logged, or shown.
- **No new outbound connection.** The check uses the answer that s-hole
  already has. Data from a third party, such as Tracker Radar, is not bundled
  or downloaded; an operator can add any list URL as before.

## Limits

- The upstream resolver sees the cloaked name, because s-hole needs the
  answer to check it. Inspection stops the connection to the tracker and the
  cookies that it gets, not the DNS lookup.
- s-hole cannot see a chain that the site's DNS provider resolves itself and
  returns as A records only (CNAME flattening).
- s-hole cannot see a site server that sends the data to the tracker
  (server-side forwarding).
- A device that uses its own encrypted DNS does not ask s-hole.

## Requirements

The tests cite these as "CL 117 req N".

1. A blocked CNAME target in the Answer section (at any hop, or a parent of a
   target) blocks the query, for every query type and upstream.
2. The reply is the same sinkhole reply as a name block, in both reply modes.
3. An allowlisted queried name skips the check. An allowlisted target does not
   count.
4. (a) The raw answer is cached and checked on each cache hit. (b) A block set
   or allowlist change applies to the next query, also from the cache.
5. The query counts once in the total and as blocked, not as a cache hit. The
   tallies and the per-minute graph follow `query_log.mode`.
6. `cname_blocked_count` <= `blocked_count` <= `total_queries`, also under
   load.
7. The query-log record holds the queried name and the block source
   (`BlockSource`; `String` gives name, cname, or unknown).
8. The `block_source` column, its migration, and `blocked_by` in JSON.
9. The ` CNAME` marker on a BLOCK line of the query log file.
10. `blocked_by` in `/api/queries` and the exports (the last CSV column),
    `cname_blocked_count`, and `shole_cname_blocked_total`.
11. `blocking.cname_inspection`, default true (also in the handler), with a
    warning when false.
12. `Store.IsAllowlisted`: suffix walk, runtime changes, no allocation.
13. No check outside the Answer section or on a failure rcode.
14. `chainBlocked` does not allocate.

## Privacy impact

- **Collects:** nothing new from the network. s-hole reads the CNAME records
  in the answer that it already received.
- **Keeps:** one more value in each blocked row of the query history, the
  block source ("name" or "cname"), under the same `query_log.mode`,
  retention, and purge as the row. One more since-start counter (a count, no
  domain or client). The CNAME target is not kept in the query history, the
  log, or the stats; the response cache keeps the raw answer until its TTL, as
  before.
- **Who can read:** the same as for the query history and the counters
  (`PRIVACY.md`).
- **Sends:** nothing new. The counter on `/metrics` has no label.

## Testing

A separate agent wrote the tests from the requirements, without the diff.

- `internal/dnsserver/cname_test.go`: a blocked target at each hop (first,
  middle, last) and a blocked parent of a target; the reply for A, AAAA,
  HTTPS, TXT, and MX in both reply modes, compared byte for byte with a name
  block; an answer from a LAN upstream; an allowlisted queried name and an
  allowlisted target; a second query served from the cache and still blocked;
  a block set change and an allowlist change applied to a cached answer; the
  query-log record of a CNAME block and of a name block; the tallies and the
  per-minute graph under each `query_log.mode`; inspection off and the
  handler's default; no check of the Authority and Additional sections or of
  a failure rcode. `TestServeDNS_CNAMETargetIsNeverStored` runs the real
  `DBLogger` and `FileLogger` and scans the database and WAL bytes, the log
  file, the stats JSON, and the slog output for the target, with the queried
  name as a positive control. `TestServeDNS_CNAMEBlockModeNoneLeavesNoTrace`
  covers `query_log.mode: "none"`. A `-race` load test checks
  `cname_blocked_count` <= `blocked_count` <= `total_queries` through the
  handler. A benchmark and a zero-allocation test cover `chainBlocked`.
- `internal/stats/cname_test.go`: the counter, its JSON field, a purge that
  keeps it, and `TestCounter_CNAMEBlockedNeverExceedsBlockedUnderLoad`.
- `internal/querylog/cname_test.go`: `BlockSource.String`, the
  `block_source` round trip through `Recent`, `Search`, and `Export`,
  `blocked_by` in JSON, the migration from the CL 77 schema and from the
  first schema (an old blocked row reads `name`), and the ` CNAME` file

- `internal/api/cname_test.go`: `blocked_by` in `/api/queries` and the JSON
  export, the CSV header with nine columns, `cname_blocked_count` in
  `/api/stats`, and `shole_cname_blocked_total` (HELP, TYPE counter, no

- `internal/config`: the default, YAML, environment variable, precedence,

- `internal/blocklist`: `IsAllowlisted` (suffix walk, case, trailing dot,
  runtime changes), a zero-allocation test, and a benchmark.

Mutation testing: 28 mutations, each caught (for example: no check on a cache
hit, no allowlist skip, the target logged, a CNAME block counted as a cache
hit, `RecordCNAMEBlocked` before `RecordQuery`, `Snapshot` reads the new
counter after `total`, the migration skipped, the default off). Two were
caught only after the tester added a case: a check of the Authority and
Additional sections, and the order of the two counter calls in the handler.

`make check` passes (lint for Linux and Windows), and `go test -race ./...`
passes. Coverage: `stats` 100%, `config` 100%, `blocklist` 99.6%,
`dnsserver` 97.0%, `querylog` 87.4%, `api` 94.5%.

Live check on the Raspberry Pi 5 (arm64) and the Debian 13 VM (amd64), with
no install, the same steps and results on both: the master build
wrote a blocked row, then this build opened the same database. The old row
read `blocked_by: name`. `analytics.neworleanssaints.com` (a CNAME to
`s5498061.t.eloqua.com`) got `0.0.0.0` for A and `::` for AAAA, also from the
cache. It counted as blocked and in `shole_cname_blocked_total`, not as a
cache hit. The CSV export, `/api/queries`, and the query log file showed the
block source. The target name was in none of the database, the query log,
or the application log. With the setting off, `-check-config` printed the
warning, and the chain was relayed.

Measurement (outside the repository; the data is not committed). Tracker
Radar (US, CC BY-NC-SA 4.0) lists the subdomains that point to each tracker
domain (`cnames`). We took the domains in a tracking category and not in the
CDN category: 943 subdomains for 25 tracker domains, 937 of which resolved on
2026-10-10. We queried each through two instances of this build, with the
inspection off and on, and the same lists:

| Lists | Inspection off | Inspection on |
|---|---|---|
| The sample config (StevenBlack, AdAway) | 135 (14.4%) | 614 (65.5%) |
| HaGeZi PRO | 360 (38.4%) | 406 (43.3%) |

HaGeZi PRO names many cloaked subdomains itself, but it does not list
`eloqua.com`; the sample lists do. The rest (for example `tinypass.com`,
`pardot.com`, `klaviyo.com`) is on neither list, so inspection cannot block
it. Inspection makes a list's tracker entries reach every subdomain that
points to them; the list still decides what is a tracker.
