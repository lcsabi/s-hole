# CL 88: blocklist `loaded` log line says where the list came from

## Description

`blocklist.Update` logged the same line for every source that produced a
list: `loaded url=… domains=…`. The line did not say whether s-hole had just
downloaded the list or read it from the on-disk cache. A cache file younger
than 24 hours is used without any fetch, so after a restart the journal looked
the same as after a real download.

This CL adds a `from` attribute to that line:

- `download`: fetched from the URL in this update and written to the cache.
- `cache`: the cache file was less than 24 hours old, so no fetch was tried.
- `stale_cache`: a fetch was needed but failed (network error, non-200 status,
  or a body over the size cap), so an older cache file was served.

The CL also adds a testing rule to `CLAUDE.md`: the agent that writes the code
does not write its tests.

## Motivation

During the CL 86 VM tests, the question "did s-hole download its lists at
startup, or use the cache?" could not be answered from the journal. The answer
decided the wording of a README note. The same `loaded` line appeared in both
cases, and the only other hint (the source's `last_refresh` in `/api/stats`
compared with the process start time) is indirect. One attribute answers it
directly.

The testing rule comes from the maintainer. Tests that the implementing agent
writes after its own code tend to follow that code, so they can pass without
checking the requirement (decorative tests), and they share the implementer's
reading of the requirement. A cold agent that gets only the requirements, not
the diff, tests the behavior the requirement describes.

## What it does

- **`internal/blocklist/loader.go`.** Three constants (`fromDownload`,
  `fromCache`, `fromStaleCache`) name the origins. `sourceMeta` carries a
  `from` field in place of its `stale` flag, and `Update` derives
  `SourceStatus.Stale` from it (`from == fromStaleCache`), so the log attribute
  and the stale flag in `/api/stats` and `/metrics` cannot disagree. Each
  return path of `fetchList` sets `from`. The `loaded` line gains `"from",
  meta.from`.
- **`CLAUDE.md`.** A new process rule under "Process conventions": a separate
  cold `general-purpose` sub-agent writes the tests for a change from the
  requirements (spec, CL description, or bug report), without the diff or the
  implementer's reasoning. It lists its own cases before it reads the existing
  tests, and runs mutation testing when it judges that worth it. It runs before
  the documentation sweep, so the CL can record its results. A new test that
  fails is treated as a possible bug in the code; the test is not changed to
  pass without the maintainer's agreement. The implementer may use
  red-to-green TDD while it builds, but those tests do not replace the cold
  agent's tests.

## Design decisions

- **The attribute is `from`, not `source`.** In this package "source" already
  means a blocklist URL (`SourceStatus`, `sources`), so `source=cache` would
  read as a URL. `loaded url=… from=cache` reads as intended.
- **Three values, not two.** A stale-cache fallback already logs its own WARN,
  but the `loaded` line is the one an operator searches for, so it names the
  fallback too.
- **One field instead of two.** Replacing `stale` with `from` keeps a single
  source of truth for the log line and the health record.
- **Log only.** `/api/stats` and `/metrics` keep their existing `stale` field
  and gauge. Adding the origin there was not needed to answer the journal
  question.
- **TDD is allowed but not enough.** Red-to-green by the implementer shows
  each of its tests can fail, which rules out decorative tests. It does not
  remove the shared reading of the requirement, so the cold tester still
  writes the tests.

## Files changed

- `internal/blocklist/loader.go`: the `from*` constants, `sourceMeta.from`,
  the `from` attribute, and `Stale` derived from it.
- `internal/blocklist/loader_test.go`: three existing assertions renamed from
  `meta.stale` to the `from` field (mechanical, by the implementer); new tests
  from the cold tester (see Testing).
- `CLAUDE.md`: the testing rule.
- Docs: `docs/CHANGELOG.md`, `docs/CL.md`, this file.

## Testing

- **Tests from a cold agent.** Following the new rule, a separate
  `general-purpose` sub-agent got the requirements above (the three `from`
  values, the unchanged failure and `Stale` behavior, and where the code
  lives) but not the diff. It listed nine cases before it read the existing
  tests, and noted that no existing test checked the `loaded` line: the
  existing `swapLogger` helper filters at WARN, below which that line sits.
  It added `captureLogs` (an INFO-level JSON capture) and five tests:
  `TestUpdate_LoadedFromDownload`,
  `TestUpdate_LoadedFromFreshCacheMakesNoRequest` (a 23-hour cache, zero
  server hits), `TestUpdate_OldCacheRefetchedLogsDownload` (a 48-hour cache
  and a working server), `TestUpdate_LoadedFromStaleCache` (connection error,
  503, and over the size cap, each with its WARN line), and
  `TestUpdate_MixedOriginsOneLoadedLinePerSource` (four URLs in one update,
  one of them failing with no cache).
- **Mutation testing: 16 of 16 caught.** The mutations covered dropping or
  renaming the attribute, wrong constant values, each return path reporting
  the wrong origin, `Stale` computed wrongly, a shorter cache age, a disabled
  fresh-cache check, and a `loaded` line for a failed source. `loader.go` was
  restored after each one and checked byte-identical.
- **Open edges, not tested:** the exact 24-hour boundary (the tests use 23 and
  48 hours to stay stable), and an old cache file that exists but cannot be
  read (it returns an error, so no `loaded` line is written).
- `make check` clean. `internal/blocklist` coverage 95.8%.
