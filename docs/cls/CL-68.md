# CL 68: Guard the remaining non-positive durations and name the URL in fetch errors (b/055)

## Description

The two-axis code review of the CL 59-67 range left two follow-ups. This CL
closes both. One is a real defect (b/055); the other is an error-message parity
cleanup. No public API change.

- **b/055** (config): `refresh_interval` and `stats_interval` accept a
  well-formed but non-positive duration, which panics `time.NewTicker` in
  `runTicker` at startup. Only `db_flush_interval` was guarded (b/046), so
  `-check-config` reports these two as valid and the service then crashes.
- **Cleanup** (blocklist): the non-200 and over-cap `fetchList` errors named
  the cap but not the source URL. CL 62 intended a truncation error "naming the
  URL and the cap"; the code named only the cap.

## Motivation

**b/055.** b/046 fixed exactly this crash for `db_flush_interval`: a non-positive
value is well-formed, so it passes `time.ParseDuration`, then panics
`time.NewTicker` in a background goroutine after the service is up. The fix
guarded `ParsedDBFlushInterval` only. The other two duration fields feed the same
`time.NewTicker` call (`runTicker`, launched for both the stats printer and the
periodic refresh), and neither parser rejects a non-positive value. `Validate()`
checks only the two enums, so `config.LoadAndValidate` accepts `refresh_interval:
0s` or `stats_interval: -5s`.

CL 66 then added `-check-config` on the promise that a config the installer's
dry-run accepts is one the service will start on. For these two fields the
promise is broken: the dry-run prints `config OK` and exits `0`, then the service
panics a ticker goroutine at startup. The panic is unrecovered, because
`runTickerOnce`'s `recover` runs only inside the loop, after `time.NewTicker` has
returned. So the guarded/unguarded split also undercut b/046's own goal of one
consistent behavior for a bad duration value.

**Cleanup.** When a source returns a non-200 or exceeds the 256 MiB cap and no
stale cache exists, `fetchList` returns an error that names the cap but not the
URL. The caller `Update` logs the URL alongside the error, so no operator loses
it today, but the error read alone did not identify the source, and CL 62's own
description said the truncation error should name the URL.

## What it does

**b/055.** Reject a non-positive value in `ParsedRefreshInterval` and
`ParsedStatsInterval`, the same `d <= 0` check `ParsedDBFlushInterval` already
has. All three duration fields now fail `-check-config` and startup cleanly, the
same way a malformed duration string already does, instead of crashing a ticker
goroutine after the service is up.

**Cleanup.** Prefix both `fetchList` failure errors with the quoted URL:
`"%q: HTTP %d"` and `"%q: response exceeded %d-byte cap"`. The two sibling paths
now match each other and the WARN log lines, so the error identifies the source
on its own.

## Design decisions

- **Guard at the parser, not in `runTicker`.** The other malformed-config values
  fail at the config gate with a clean log-and-exit. A non-positive interval now
  fails there too, so `-check-config` and startup stay in lockstep. Guarding
  `time.NewTicker` in `runTicker` instead would move the check away from the
  gate the dry-run runs, which is the opposite of what CL 66 set up.
- **A zero interval is not a "disabled" value here.** Neither ticker treats `0`
  as off; both would panic. So rejecting non-positive loses no valid
  configuration. If a disabled stats printer is ever wanted, that is a separate
  feature with its own sentinel, not a reinterpretation of `0s`.
- **Name the URL, keep the non-200 and over-cap paths parallel.** Both are the
  no-cache hard-failure branch, so both get the same URL prefix rather than only
  the truncation one, which keeps the two siblings reading alike.
