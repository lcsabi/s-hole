# CL 105: Purge overwrites the query files with zeros

## Description

A purge now overwrites the query files with zeros before it empties or
deletes them:

- **Text log, online and offline.** The purge overwrites the query log file
  with zeros up to its size and syncs it, then empties it (s-hole running)
  or deletes it (s-hole stopped).
- **Database, offline.** When s-hole is stopped, `s-hole -purge` overwrites
  the database, `-wal`, and `-shm` files with zeros, syncs them, and deletes
  them. When s-hole runs, the purge is unchanged: `secure_delete`, `VACUUM`,
  and the TRUNCATE checkpoints.
- **Links.** The overwrite refuses a symbolic link, a file that is not a
  regular file, and (on Unix) a file with more than one hard link. The step
  fails. When s-hole is stopped, the purge keeps that file; when s-hole runs,
  it still empties the log file (`ErrNotOverwritten`).

Review finding: PRIV-08. Target release: v2.1.0.

## Motivation

- **PRIV-08.** The online database purge zeroes the rows (`secure_delete`)
  and runs `VACUUM`. The offline purge, which `uninstall-linux.sh --purge`
  uses, only deleted the files, and the online text-log purge only truncated
  the file. Both free the disk blocks without changing them, so the history
  stayed on the disk until the file system reused the blocks.

## What it does

- `internal/querylog/zero.go` (new): `ZeroFile(path)` checks the path with
  `Lstat`, opens it for writing (on Unix with `O_NOFOLLOW` and `O_NONBLOCK`),
  checks that the open file is the same regular file and has one link, writes
  zeros in 64 KiB chunks up to its size, and syncs it. It does not truncate
  or delete the file, and it never creates one. A refusal matches
  `ErrRefused`. `zero_unix.go` and `zero_windows.go` hold the open flags and
  the link count; Windows has neither and relies on the `Lstat` and
  `os.SameFile` checks.
- `internal/querylog/logger.go`: `FileLogger` keeps the file path. The purge
  in the writer goroutine overwrites the file through a second handle (the
  log is open for append, which writes only at the end), then truncates it.
  It overwrites only the file the logger has open (`os.SameFile`): if another
  file took the path, the purge empties the open file and returns an error
  that matches `ErrNotOverwritten` ("emptied, but not overwritten with
  zeros").
- `cmd/s-hole/purge.go`: `purgeOffline` replaces `os.Remove` with `wipe`:
  `ZeroFile`, then `os.Remove`, for each of the database, `-wal`, `-shm`, and
  log files that exists. A refused file is not deleted, the step fails with
  `delete failed:`, and the other files are still wiped. `joinErrs` keeps a
  step result on one line. The running-s-hole report gives the query log
  file step the `ErrNotOverwritten` text instead of `empty failed:`. The other
  report texts do not change.
- `internal/querylog/db.go`: a comment only (the blocks that a WAL truncate
  frees can keep old pages).

## Design decisions

- **The offline purge does not open SQLite** (decided with the maintainer).
  PRIV-08 first proposed to run the online purge steps on the database file
  before the delete. But `uninstall-linux.sh --purge` runs `s-hole -purge` as
  root in `/var/lib/s-hole`, which the `s-hole` user owns. SQLite refuses a
  symbolic link at the `-wal` or `-shm` path, but it writes through a hard
  link there: in a test, the other name was truncated (`-wal`) or overwritten
  (`-shm`). The kernel blocks such links by default
  (`fs.protected_hardlinks=1`), and a check before the open leaves a race.
  The zeros cover every byte that the SQLite steps would change, and also the
  free pages and a `-wal` file that a crash left (SQLite's own checkpoint
  would truncate that file without overwriting it). So the offline purge
  writes zeros only.
- **Refuse links.** For the same reason, `ZeroFile` checks the path before it
  opens it and the open file after it, and refuses a file with more than one
  hard link. Deleting such a link would leave the data under the other name,
  so the purge keeps the file and fails the step.
- **Empty the log even when the overwrite fails.** The purge must not keep a
  history that it can delete. It reports the missing overwrite as a failed
  step, so the operator can act (for example, on files that a log rotation
  made).
- **Best effort.** On flash storage and on a copy-on-write file system, the
  zeros can go to new blocks. SQLite frees its WAL without overwriting it: it
  truncates the WAL at each checkpoint and deletes it when the database
  closes, so when s-hole stops, the WAL is gone before an offline purge runs.
  Older page copies from the WAL can stay in free disk blocks. `PRIVACY.md`
  says so; an overwrite of the WAL before SQLite frees it is a separate
  follow-up (decided with the maintainer).

## Privacy impact

- **Collects:** nothing new.
- **Keeps:** less. The query log file, and the database files of a stopped
  s-hole, no longer leave the history in the disk blocks they free. Free
  blocks from SQLite's WAL can still hold older page copies (see Design
  decisions).
- **Who can read:** reading free disk blocks needs raw disk access (root, or
  the disk itself); this CL reduces what such a reader finds.
- **Sends:** nothing new.

## Testing

A separate sub-agent wrote the tests from the requirements, without the
diff. It listed its cases first, then wrote:

- `internal/querylog/zero_test.go`, `zero_unix_test.go`: `ZeroFile` zeroes
  the whole file and keeps its size (0, 1, 100 bytes, one chunk minus one,
  one chunk, one chunk plus one, two chunks, and an odd size over three
  chunks). A missing file gives `fs.ErrNotExist` and is not created. A
  symbolic link (also a dangling one), a directory, a named pipe (without
  blocking), and a hard-linked file are refused with `ErrRefused`, and no
  name changes. A missing file and a read-only file do not match
  `ErrRefused`.
- `internal/querylog/logger_purge_test.go`: after the online purge the file
  is empty, and a later line is its only content. When another file took the
  log's path, the purge leaves that file as it is, empties the open file, and
  returns an error that matches `ErrNotOverwritten` and `ErrRefused`.
  Standard output still gives `ErrStdoutNotPurgeable`.
- `cmd/s-hole/purge_overwrite_test.go`, `purge_overwrite_unix_test.go`: the
  acceptance test. A real database and a real log file with the test domain
  are read, after the offline purge, through descriptors opened before it:
  at deletion each file has its old size and holds only zeros. The same for
  a crash state (the rows only in the `-wal` file): the database, `-wal`, and
  `-shm` files are zeroed in full. A corrupt database and a non-SQLite file
  are zeroed and deleted, and the step does not fail. A symbolic link or a
  hard link at the database, `-wal`, `-shm`, or log path (alone and in sets)
  is refused and kept, the other name keeps its exact bytes, each refused
  path is named once in a one-line result that starts with `delete failed:`,
  and the other files are still zeroed and deleted. A hard-linked `-wal` or
  `-shm` in the crash state (the case that SQLite wrote through) keeps both
  names unchanged. A named pipe at the log path is refused without blocking.
  The running-s-hole report shows the `ErrNotOverwritten` text, one line,
  and a failed step.

The tester found one bug in a first version, which ran the SQLite purge
steps offline: that step checked only for a regular file, so a hard link at
the database path let a purge run as root delete the rows of another SQLite
database. The follow-up check found that SQLite also writes through a hard
link at the `-wal` or `-shm` path, which led to the zeros-only design (see
Design decisions). The tests of the removed SQLite step were removed.

Mutation tests by the tester, each caught by at least one test: `ZeroFile`
writes nothing or skips the last part chunk; no hard-link check;
`refusedError.Is` always false; the wipe removes a refused file, stops at
the first error, removes without `ZeroFile`, or truncates the `-wal` first;
`errors.Join` instead of `joinErrs`; no `ErrNotOverwritten` case in the
report; no overwrite or no same-file check in the online purge. Removing the
first `Lstat` check in `ZeroFile` breaks no test: the `O_NOFOLLOW` open and
the same-file check after it refuse the same paths. A file-level test cannot
see that the log held zeros at the moment of the online truncate; the
renamed-path test pins the overwrite through its error, and the live check
below shows it.

`make check` passes. Coverage: `querylog` 87.3%.

Live on the Debian 13 VM, each case on a new 64 MiB ext4 file system in a
loop device: s-hole with `mode: all`, a database, and a log file answered
300 queries for a test domain, then stopped; then `s-hole -purge` ran. Each
file was read after the purge through a descriptor opened before it.

| Case | master | this CL |
|---|---|---|
| Offline after a clean stop: test domain in `queries.db` / `queries.log` at deletion | 600 / 300 | 0 / 0 (only zeros) |
| Offline after `kill -9`: test domain in `queries.db` / `-wal` / `-shm` / `queries.log` at deletion | 0 / 2262 / 0 / 300 | 0 / 0 / 0 / 0 (only zeros, sizes kept) |
| Offline after `kill -9`: test domain in the raw file system image after the purge | 2561 | 0 |
| Offline after a clean stop: test domain in the raw image after the purge | 3066 | 2352 |
| Online purge (log file only): test domain in the raw image after the purge | 300 | 0 |

After a clean stop, the raw image still holds the test domain. An earlier
run mapped each such block with `filefrag` on the `-wal` file while s-hole
ran: every one was a block of the WAL that SQLite deleted when s-hole
stopped, before the purge (see Design decisions). In every case, the purge
added no block that holds the test domain.
