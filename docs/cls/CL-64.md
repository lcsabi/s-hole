# CL 64: Make the admin http.Server field race-free (b/053)

## Description

**b/053** (api): `api.Server.httpServer` is written by `Serve` and read by
`Shutdown` from two different goroutines with no synchronization. `main` runs
`Serve` in a background goroutine, and `doStop` calls `Shutdown` from the signal
goroutine, so the assignment `s.httpServer = hs` in one goroutine races the read
in the other. A plain `*http.Server` field makes this a data race that `-race`
flags. The finding came from the CL 59-63 ultrareview follow-up.

The race predates the CL 59-63 series (the old `ListenAndServe` set the field the
same way inside the same background goroutine), so this is a pre-existing defect,
not a regression from that series.

## Motivation

Two goroutines touch `s.httpServer`:

- `Serve` (background, started by `go apiServer.Serve(apiLn)` in `main`) writes
  the field after building the `http.Server`.
- `Shutdown` (signal goroutine, via `doStop`) reads the field to drain the
  server.

The write and the read are unsynchronized, which is a data race under the Go
memory model. Beyond the `-race` failure, the nil-check in `Shutdown` had a
second-order effect: if a stop arrived before `Serve` stored the server, the read
saw the zero value and `Shutdown` no-oped, so in-flight admin requests would not
be drained. The synchronous bind added in CL 63 makes that window tiny, but the
data race on the field itself is real regardless of timing.

## What it does

Change the field to `atomic.Pointer[http.Server]`.

- `Serve` calls `s.httpServer.Store(hs)` instead of a plain assignment.
- `Shutdown` calls `s.httpServer.Load()`; a nil result means the server was
  never started, so it returns nil (unchanged behavior, now race-free).

This makes `Server` safe regardless of how the caller sequences `Serve` and
`Shutdown`, so a future edit to `main`'s startup order cannot reintroduce the
race. The public API (`Serve`, `ListenAndServe`, `Shutdown`) is unchanged.

## Design decisions

- **An atomic field, not a lock or a call-order rule.** The two accesses are a
  single-pointer write and read, which `atomic.Pointer` covers exactly with no
  mutex and no new dependency (`sync/atomic` is stdlib). Guarding the type
  itself keeps it correct for any caller, which is stronger than relying on
  `main` to store the pointer before it backgrounds the serve loop (an ordering
  a later edit could drop, the same failure class CL 59 removed by construction).
- **Nil-load stays a no-op.** `Shutdown` before `Serve` has stored the server is
  still a no-op, matching the prior nil-check. `TestShutdown_BeforeListenIsNoOp`
  pins that path.

## Testing

- `TestServe_ConcurrentShutdownIsRaceFree`: starts `Serve` on a bound listener in
  a goroutine and drives `Shutdown` concurrently until `Serve` returns. It is a
  `-race` guard: the pre-fix plain-pointer field races here under `-race`, the
  atomic field is clean. It is deterministic without `-race` because it retries
  `Shutdown` until the store is visible and `Serve` returns.
- `TestShutdown_BeforeListenIsNoOp`, `TestServe_OnBoundListener`,
  `TestListenAndServe_LifecycleAndShutdown`, and
  `TestListenAndServe_BindFailureSurfaces` stay green.
