# CL 30 — Wildcard / subdomain blocking (suffix match)

## Description

`blocklist.Store.IsBlocked` now matches a domain against the block set by
walking its parent labels most-specific-first
(`a.b.example.com → b.example.com → example.com → com`) instead of requiring
an exact match. A single list entry therefore blocks its whole subtree:
`ads.example.com` now also blocks `x.ads.example.com`. The whitelist is
matched by the same suffix walk and keeps global precedence — if the queried
name or any parent is whitelisted, the query is allowed even past a more
specific blocked parent.

Roadmap item #3.

## Motivation

Exact-match blocking was the biggest real filtering gap. Trackers rotate
subdomains (`x1.ads.example.com`, `x2.ads.example.com`, …) precisely to slip
past exact-match blockers: one blocklist entry could not cover them. Every
other DNS sinkhole (Pi-hole, AdGuard Home, unbound) blocks the subtree. The
old behaviour was documented as a non-goal only because it was unimplemented,
not because exact-match was desirable.

## Design decisions

**Suffix walk, no new data structure.** `IsBlocked` reslices the normalised
name in place on each `.` boundary and probes the two existing flat hash
sets — O(labels) lookups, no per-query allocation. A trie/radix structure
would buy nothing at these set sizes and would cost the "auditable in an
afternoon" identity a data structure to reason about. The walk stops at the
last label; neither set can contain a bare TLD (`ValidDomain` requires a
dot), so probing `com` is harmless.

**Whitelist wins at every level (global, not most-specific-wins).** The
walk cannot early-return on the first blocked parent, because a *broader*
parent might still be whitelisted. Instead it records a block match and
keeps walking; the first whitelisted suffix it meets returns "allowed"
immediately. Semantics:

- whitelist `safe.doubleclick.net` + block `doubleclick.net` →
  `safe.doubleclick.net` and its subtree pass, `ads.doubleclick.net` stays
  blocked.
- whitelist `example.com` + block `ads.example.com` → the whole
  `example.com` subtree passes (a parent whitelist is an intentional
  "trust everything under here").

This is the roadmap's "whitelist-wins at every level" and makes the
whitelist the surgical escape hatch for an over-broad block entry.

**No config knob to restore exact-match.** Exact-match was a gap, not a
feature; a global `block_subdomains: false` switch would only let trackers
back in via subdomain rotation, and its one legitimate use (a blocklist that
over-blocks a domain whose subdomains you need) is already served by the
now-suffix-aware whitelist. Skipping the knob also avoids touching
`config.yaml` (which is `--skip-worktree`) and keeps the config surface flat.

**Behaviour change is unconditional and pre-release.** No tagged release
exists yet (`docs/ROADMAP.md` #2), so there are no external users with an
exact-match expectation to preserve. The old test that pinned
"subdomain not auto-blocked" is flipped, not kept.
