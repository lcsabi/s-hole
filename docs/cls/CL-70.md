# CL 70: query-volume-over-time graph on the dashboard

## Description

Add `GET /api/history`, a read-only endpoint that aggregates the SQLite query log
into per-bucket total and blocked counts over a time window, and a two-line graph
panel on the dashboard that draws the series with a native `<canvas>` (no chart
library). Make the three fetch-backed panels (the new graph, Recent Queries, Top
Blocked) collapsible so hiding one also skips its poll. Implements ROADMAP #20.

## Motivation

The dashboard showed current totals but not the shape of the day. Comparable
sinkholes lead with a queries-over-time graph, and the data already sat in the
query DB with per-row timestamps. A short history turns "current numbers" into
"what happened today". The graph needs no new dependency: the aggregation is one
grouped SQL query, and the drawing is hand-written canvas.

## What it does

- **`DBLogger.History(ctx, window, bucket)`** (`db.go`): groups the `queries`
  rows into buckets and returns a dense, zero-filled series (oldest first) so the
  graph draws a continuous line even across idle periods. `ts` is RFC3339 text
  with a timezone offset, so the bucket key is computed from the UTC epoch
  (`CAST(strftime('%s', ts) AS INTEGER)`), not from the text; the `WHERE` cutoff
  stays an RFC3339 string to reuse `idx_queries_ts` and match the prune path. The
  dense series is built in Go so the handler stays thin. `Bucket` carries
  `Start` (unix seconds), `Total`, and `Blocked`.
- **`GET /api/history`** (`api.go`): parses `?window=` and `?bucket=` durations
  (`parseHistoryParams`), defaulting to 24h/1h and clamping the bucket *count* so
  a crafted `window=7d&bucket=1s` cannot ask for 600k buckets (`maxHistoryBuckets`
  = 1000, mirroring `maxQueriesLimit`). A small `parseFlexDuration` accepts a
  whole-day `d` suffix (`time.ParseDuration` stops at hours), so `window=7d`
  works. The response echoes the effective `window`/`bucket` in seconds. When
  query logging is disabled (`s.db == nil`) it returns an empty series and 200,
  the same degrade-not-fail contract as `/api/queries` and `/api/top-blocked`.
- **Dashboard** (`static/index.html`): a full-width "Queries over time" panel
  leads the dashboard below the stat cards. It draws two filled lines (Total in
  the accent color, Blocked in red) on a devicePixelRatio-scaled canvas, with a
  0/max y axis, thinned time labels, a legend, and a hover tooltip that reads the
  exact bucket time, total, and blocked. A 24h / 7d segmented toggle (constant 1h
  bucket) reuses the existing `.seg` pattern.
- **Collapsible panels** (`static/index.html`): the three panels that own a
  dedicated `/api/*` fetch (Queries-over-time, Recent Queries, Top Blocked) gain a
  disclosure arrow. Collapsing a panel hides its body via the `[hidden]`
  attribute and skips its poll; expanding it refetches immediately. The state
  persists per panel in `localStorage`. The stat cards, Top Clients, Sources, and
  Actions stay always-open because they ride the single shared `/api/stats` call,
  so collapsing them would save no request.

## Design decisions

- **Bucket in SQL, densify in Go.** Grouping in SQL keeps the payload to one row
  per non-empty bucket; the handler stays thin, and `History` fills the gaps so
  the UI never special-cases a missing bucket.
- **Clamp the bucket count, not just the window.** The `?limit=` clamp already
  guards row endpoints; the history endpoint's analogous risk is an enormous
  bucket count, so `parseHistoryParams` widens the bucket until the count fits.
- **Aggregate counts only.** The series has no client field, so the ROADMAP #21
  privacy work does not couple to it.
- **No new metric.** Prometheus derives rates from the existing counters, so the
  history is API-and-UI only.
- **Collapse scope = fetch-backed panels.** Tracing the fetches, only three
  panels own a dedicated call; the rest share `/api/stats`. Scoping collapse to
  the three makes "hide it" also mean "stop polling it", which is the point.

## Testing

- `make check` clean.
- `TestDBLogger_History` seeds rows with controlled timestamps into known hour
  buckets and asserts the dense series buckets them correctly (current and
  previous hour counts, zero-filled gaps, ascending order, out-of-window
  exclusion). `TestDBLogger_HistoryEmptyDBIsZeroFilled` covers the idle DB.
- `TestParseHistoryParams` covers defaults, garbage, the `d` day suffix, and each
  clamp; `TestParseHistoryParams_BucketCountCapped` pins the count guard.
- `TestHistoryEndpoint_WithRealDB` drives the endpoint end-to-end through a real
  DBLogger; `TestHistoryEndpoint_NoDBReturnsEmpty` pins the db-disabled contract.
- Manual smoke: with the DB on, generated mixed allow/block traffic and confirmed
  a dense 24-bucket series with the current bucket populated (total 52, blocked
  20), `window=7d` returning 168 buckets, and `window=7d&bucket=1s` clamped to a
  605s bucket (999 buckets). With `query_db` off the endpoint returned
  `{"series":[]}` and the panel showed its empty state.
