# CL 116: Publish the October 2026 privacy and security review

## Description

Add `docs/SECURITY-REVIEW-2026-10.md`, the public summary of the privacy and
security review of s-hole 2.0.0, and link it from `SECURITY.md` (a new
"Reviews" section), the README project tree, and the CHANGELOG. No code
changes.

## Motivation

In October 2026 an external staff-level review of s-hole 2.0.0, a check of
its claims, the maintainer's own audit, and the fix work found 37 issues (21
security, 16 privacy; 5 Medium, 22 Low, 10 Info, no High). They were tracked
in private working notes, because the repository is public and the issues
were not fixed yet. The maintainer decided to publish a summary after the
final verification. The fixes shipped in 2.0.1, 2.1.0, and 2.1.1, except two
issues that only device pairing (ROADMAP #42) can fix; for those the docs now
state the limit. The final verification passed on 2026-10-09, and the
release checks ran on 2.1.0 and 2.1.1. The maintainer approved the text.

## What it does

- `docs/SECURITY-REVIEW-2026-10.md`: the scope of the review and the test
  systems; the result counts by severity; the five Medium issues with their
  fix and bug ID; the other changes by area; the recommendations that needed
  no change, with the reason; what is still open (device pairing, ROADMAP
  #42); the known limits that `PRIVACY.md` and `SECURITY.md` document; and a
  table of the releases and CLs that hold the fixes.
- `SECURITY.md`: a "Reviews" section that links the page.
- `README.md`: the project tree names the review page under `docs/`.
- `docs/CHANGELOG.md`: a bullet under `[Unreleased]` (Added).

## Design decisions

- **A summary, not the working notes.** The page says what was found and
  what changed, at the level a user or a reviewer needs, and points to the
  CL files and `docs/BUGS.md` for detail.
- **No working-note IDs in the page.** The public record already has the bug
  IDs (b/096 to b/105) and the CL numbers; the `SEC-NN` and `PRIV-NN` IDs
  appear only in CL notes.
- **The two issues without a code fix are named as such.** The page and
  `SECURITY.md` say that dashboard access by every account on the host and
  plain HTTP on the LAN wait for device pairing, so no reader takes "fixed"
  to cover them.
- **The known limits stay in the page.** A reader of a review summary needs
  to know what s-hole still cannot protect, not only what it fixed.
- **A page in `docs/`, not release notes.** The 2.1.0 and 2.1.1 release
  notes are immutable, and the review spans three releases.

## Testing

- `make check` passes; no code changed.
- The page is based on the final verification of 2026-10-09 (tests, code,
  documentation, and live runs on a Debian 13 VM, a Raspberry Pi 5, Windows
  10, and Android 13) and on the 2.1.0 and 2.1.1 release checks.
- A cold documentation sweep checked every claim in the page against the
  code, CL 97 to CL 115, `docs/BUGS.md`, the other docs, the git tags, and
  the release flags. It found 6 must-fix items, all fixed: "each issue is
  fixed" left out the two issues that wait for #42; "after a purge or a
  stop" (a stop alone keeps the history); "never names a domain or a client"
  (true for the DNS path; the allowlist audit line can name the requester);
  the 403 for another site (browsers mark only loopback and HTTPS); "releases
  are immutable" (only from 2.1.0); and an overstated Testing line in this
  file. Its wording suggestions are applied too.

## Privacy impact

None. The page describes s-hole's behavior. It names no person, host name,
network address, or working document, and s-hole collects, stores, and sends
no new data.
