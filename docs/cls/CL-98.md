# CL 98: Blocklist redirect policy

## Description

An HTTPS blocklist download no longer follows a redirect to a URL that is not
HTTPS (b/097). The download fails instead, s-hole logs a warning with both
URLs, and the stale-cache fallback applies. A redirect to another HTTPS host
still works.

Review finding: SEC-02 (b/097). Target release: v2.0.1.

## Motivation

The blocklist HTTP client used Go's default redirect policy: up to 10
redirects, with no check on the scheme. An `https://` list that redirected to
`http://` was downloaded in plain text with no warning. The config warning
for a plain HTTP list (`config.Warnings`) checks only the configured URL, so
it did not fire. An attacker on the network path could then change the list:

- remove tracker domains, which unblocks them for the whole LAN;
- add domains, which blocks banking or software updates for every device;
- send a list near the 256 MiB cap, which can use up the memory of a
  Raspberry Pi.

A redirect also makes s-hole connect to a host that is not in the config.
`PRIVACY.md` and the "no other outbound connections" rule named only the
blocklist hosts.

A scratch Go program with the same client shape confirmed the issue: an
HTTPS test server that redirected to an HTTP server gave status 200, the
final scheme `http`, and the HTTP server's body.

## What it does

- **Redirect policy** (`internal/blocklist/loader.go`, `checkRedirect`): the
  blocklist `httpClient` gets a `CheckRedirect` function. It returns an error
  for the 10th redirect, when 10 requests are already made (the limit of
  Go's default policy stays). When the first
  request of the chain was HTTPS and the next target is not HTTPS, it logs
  `blocklist redirect refused` at WARN with `url` (the first URL) and `to`
  (the target), both through `redact.URL`, and returns
  `errInsecureRedirect`. The client does not send the refused request.
- **Fallback:** the HTTP client returns the error as a `*url.Error` with the
  target URL, which `redactURLError` already redacts. `fetchList` treats it
  like any connection error: the stale cached copy is used when it can be
  read (`download failed, using stale cache`, `from=stale_cache`, STALE on
  the dashboard), and otherwise the source fails (`blocklist load failed`).
  If every source fails, `Update` keeps the existing block set, as before.
- **Not refused:** a redirect from HTTPS to HTTPS on another host (a GitHub
  release download redirects to a CDN host), and any redirect of a list that
  is configured as `http://`, which already gets a config warning.
- **Docs:** PRIVACY (the blocklist hosts row names the HTTPS hosts they
  redirect to), SECURITY (the blocklist downloads bullet), DESIGN (the
  blocklist URLs consideration, which said that the downloader followed every
  redirect), README (Security Notes), TROUBLESHOOTING (the new WARN in the
  empty block set table, the `grep` pattern, and the stale-cache reasons),
  CLAUDE.md (the outbound connections rule and the package test seams),
  CONTRIBUTING (the `trustTLS` test seam), CHANGELOG, and b/097.

## Design decisions

- **Check the first request, at every hop.** The rule compares the target
  with the first request of the chain (`via[0]`), so an HTTPS, HTTPS, HTTP
  chain is refused at the last hop. A list configured as `http://` is not
  checked: its config warning already says that the list can be changed in
  transit.
- **Refuse, do not rewrite.** s-hole does not change an `http://` target to
  `https://`. The target host may not serve HTTPS, and a silent rewrite would
  hide a broken list URL from the operator.
- **Allow cross-host HTTPS redirects.** Real lists use them. TLS still checks
  the certificate of the new host. The PRIVACY row names these hosts.
- **A dedicated WARN.** The fallback WARN that follows (`download failed,
  using stale cache`, or `blocklist load failed`) shows the error, but the
  dedicated line says what happened and gives a hint, and
  `TROUBLESHOOTING.md` can quote it.
- **No setting.** There is no setting to allow a downgrade. An operator who
  wants a plain HTTP list can configure its `http://` URL and get the
  warning for it.

## Privacy impact

- **Collects:** nothing new.
- **Sends:** s-hole no longer sends a blocklist request in plain text after a
  redirect, so a host on the network path cannot read or change it. A
  redirect to another HTTPS host still makes s-hole connect to that host,
  with `User-Agent: s-hole` and no other data. `PRIVACY.md` now lists these
  hosts.
- **Log:** the new WARN holds two blocklist URLs, with user info and the
  query string redacted. It holds no query data.

## Testing

- `make check` passed. `go test -cover ./internal/blocklist/`: 99.6% (floor
  85%). `CGO_ENABLED=1 go test -race ./internal/blocklist/` passed.
- **Cold sub-agent tests:** a `general-purpose` sub-agent with the
  requirements only (no diff) wrote `internal/blocklist/redirect_test.go`
  (7 tests, 5 subtests). A helper, `trustTLS`, swaps only
  `httpClient.Transport` to trust the `httptest` certificates and to dial a
  second host name (`example.com`) on 127.0.0.1, so the tests run the
  production redirect policy and timeout.
  - HTTPS to HTTP, with `DownloadFirst` and with `CacheFirst` and an old copy:
    the plain HTTP server gets no request, the store holds only the cached
    domains, the source is stale with the cache file's time, and one WARN
    holds both URLs in their `redact.URL` form.
  - The same with no cache: `Update` fails and keeps the existing block set,
    and the source shows as failed. A second HTTPS list still loads.
  - A chain HTTPS, HTTPS on another host, HTTP: the middle hop gets one
    request, the plain HTTP server gets none, and the WARN names the
    configured URL and the HTTP target.
  - HTTPS to HTTPS on another host: followed, `from=download`, no WARN.
  - A list configured as `http://` that redirects to `http://`: followed.
  - The limit: 9 redirects work, the 10th fails after 10 requests, and a
    redirect loop stops after 10 requests.
  - Negative checks: no user info or query string of either URL in any log
    record or in the returned error.
  - Mutation testing: 13 mutations of `loader.go` (no policy, no scheme
    check, no limit, an off-by-one limit, refuse every non-HTTPS target,
    refuse cross-host redirects, check the first hop only, both WARN URLs
    unredacted, the WARN target unredacted, the last hop instead of the
    configured URL, WARN at INFO, no target in the WARN, no
    `redactURLError`). Each one failed at least one test. No
    test failed against the code.
- **Live run** (WSL, the built binary on loopback), with one list URL that
  redirects from HTTPS to plain HTTP (with user info and a query string) and
  one GitHub `raw` URL that redirects to `raw.githubusercontent.com`:

  | Case | This branch | master (v2.0.0 code) |
  |---|---|---|
  | HTTPS to HTTP, no cache | `blocklist redirect refused`, then `blocklist load failed`; both URLs redacted | `from=download`: the plain HTTP body was downloaded and parsed |
  | HTTPS to HTTP, a 3-day-old cached copy | `blocklist redirect refused`, then `download failed, using stale cache`, `from=stale_cache` | not run |
  | GitHub `raw` to `raw.githubusercontent.com` | `from=download`, 2,030 domains | `from=download`, 2,030 domains |

  The scratch files were removed afterwards. No VM or Pi run: the change is
  in the download client only, which the local run covers.
