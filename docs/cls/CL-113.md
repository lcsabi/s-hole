# CL 113: Graduate the CHANGELOG to v2.1.0

## Description

Graduate the CHANGELOG's `[Unreleased]` section to `[2.1.0] - 2026-10-09` and
add a fresh empty `[Unreleased]` above it. A `v2.1.0` tag push needs this step:
`.github/workflows/release.yml` draws the GitHub Release notes from the
matching `[2.1.0]` CHANGELOG section, so that section must exist at the tagged
commit. No workflow or Go code changes.

## Motivation

`v2.0.1` shipped on 2026-10-08. Since then the `[Unreleased]` section has
collected the operator-visible work from CL 101 to CL 108 and CL 110 to
CL 112: LAN scope and local names, DNS server limits and DoT TLS 1.3, the
smaller Docker image, admin API hardening, the purge and WAL overwrite, the
systemd sandbox and hardened `docker run` examples, the Windows service access
list, the signed release path, static analysis, and the privacy
documentation. CL 109 changed tests only and has no CHANGELOG bullet.

The config format and the setting names do not change, so the release is a
minor version. Some behavior changes (TLS 1.3 only for DoT, public IPv4
interface subnets are not LAN, the Windows install layout, the Fetch Metadata
check) can need an operator action; the intro lists them.

## What it does

- Rename `## [Unreleased]` to `## [2.1.0] - 2026-10-09`, then insert a fresh
  empty `## [Unreleased]` above it.
- Add a short intro to the section. It says that this is a minor release with
  privacy and security fixes, that the config format does not change, and it
  lists the five changes to check before an upgrade: upgrade with
  `install-linux.sh` for the new unit, move a Windows install out of one
  folder, TLS 1.2-only DoT clients (Android 9) lose DoT, a public or CGNAT
  IPv4 interface subnet is not LAN, and a browser page on another site or
  port gets 403 from the admin API.
- Update three README examples: the archive name and the `docker pull` tag
  from 2.0.1 to 2.1.0, and the `s-hole -version` output to `v2.1.0`,
  `go1.26.9`, and a matching build date.
- Use one prefix for the two README notes on attestations: "From 2.1.0".

## Design decisions

- **Graduation is its own CL, merged before the tag,** as CONTRIBUTING's
  "Cutting a release" requires and as CL 96 and CL 100 did. Otherwise the
  release-notes extractor falls back to a placeholder.
- **The intro lists only the changes that need an action.** The bullets below
  it describe every change. An operator who reads only the first lines of the
  GitHub Release learns what to do before the upgrade.
- **The date is the planned tag date.** If the tag moves to another day, a
  follow-up edit changes the date before the tag.
- **No CHANGELOG bullet of its own.** The graduation changes no runtime
  behavior.

## Files changed

- `docs/CHANGELOG.md`: graduate `[Unreleased]` to `[2.1.0] - 2026-10-09`, add
  a fresh empty `[Unreleased]`, and add the intro.
- `README.md`: the version in three examples, the sample build date, and the
  "From 2.1.0" prefix.
- `docs/CL.md`: index row for CL 113.
- `docs/cls/CL-113.md`: this file.

No Go code changed. `internal/version` reads the ldflags, so a build tagged
`v2.1.0` reports the tag with no source change.

## Testing

- `make check` stays green; no Go code changed.
- Ran the release-notes `awk` extractor from `release.yml` against the
  graduated `docs/CHANGELOG.md` with `version=2.1.0`, and with the rc tag
  `v2.1.0-rc1` reduced the same way. It returns the `[2.1.0]` body from the
  intro to the last Security bullet, and nothing from `[2.0.1]`.
- End-to-end validation follows CONTRIBUTING "Cutting a release" after this CL
  merges: push `v2.1.0-rc1`; check the archives, `SHA256SUMS`, `-version`, the
  `ghcr.io/lcsabi/s-hole:2.1.0-rc1` image, the rendered notes with the "Build"
  section, `gh attestation verify` for each archive, its binary, and the
  image, the image SBOM, and that a published asset cannot be replaced; then
  delete the rc and cut `v2.1.0`. This is the first release with the CL 108
  release path.

## Privacy impact

None. The change edits release notes and documentation only. It collects,
stores, and sends no data.
