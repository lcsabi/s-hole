# CL 36 — Act on ultrareview findings (bug_001–bug_006)

## Description

A cloud multi-agent review (`/ultrareview`) of the branch up to CL 35 returned
six findings — one `normal`, five `nit`. All six were verified against the code
and are addressed here in one CL. None are refactors for their own sake: two are
correctness gaps, one is a documented-invariant regression, two are
consistency-with-existing-code fixes, and one is a banned test pattern. The
finding IDs (`bug_001`–`bug_006`) are referenced in the regression-test comments
so the mapping survives in `git blame`.

Summary of the six:

| ID | Severity | Area | One-line |

## Findings and fixes

### bug_002 (normal) — installer `start` is a no-op on upgrade

**What was wrong.** The installer ended with `systemctl start s-hole`. On a
*re-run* (the upgrade path in ROADMAP #1 — `scp` a new binary, re-run the
installer), `install -m 755` replaces the binary at a new inode but the running
process keeps executing the old one, and `systemctl start` on an
already-active unit is a documented no-op. The service therefore kept running
the **old** build while the new "Installed build" box (added in CL 35) printed
the **new** version. That is worse than the pre-CL-35 silence: it turns the
stale-binary failure mode CL 35 exists to catch into a *false-positive* "you're
up to date" signal.

**Fix.** `systemctl start` → `systemctl restart`. `restart` picks up the new
binary on an active unit and is equivalent to `start` on an inactive one (a
fresh install), so no branching is needed. Comment added explaining why.

### bug_001 (nit) — admin-UI hint misclassifies LAN binds

**What was wrong.** The end-of-install banner decides whether to print a LAN
admin URL with `grep -qE '0\.0\.0\.0'` — it matched only the literal string
`0.0.0.0`. An operator who binds the admin UI to a specific interface
(`api_listen: "192.168.1.10:8080"`), a bare port (`":8080"`), or the IPv6
wildcard (`"[::]:8080"`) got the misleading "this machine only — set
`api_listen: "0.0.0.0:8080"` for LAN access" note even though the UI *is*
LAN-reachable — and for the specific-IP case, following the advice would widen
the bind. The Go side already gets this right in `isLoopbackHost`
(`cmd/s-hole/main.go`), which the shell banner was meant to mirror (T4).

**Fix.** Parse `api_listen` into host and port (stripping the YAML key, quotes,
and IPv6 brackets) and classify with a `case` that mirrors `isLoopbackHost`:
only `127.*` / `::1` / `localhost` are loopback; an empty host, `0.0.0.0`, `::`,
or any specific address is LAN-visible. Verified against all seven forms.

### bug_004 (nit) — case-sensitive private-PTR intercept

**What was wrong.** `isPrivatePTR` compared the query name against the
all-lowercase `privateReverseZones` with `==` / `strings.HasSuffix`. DNS names
are case-insensitive (RFC 1035 §2.3.3) and miekg/dns preserves the wire-format
case verbatim, so a PTR query for `1.1.168.192.IN-ADDR.ARPA.` — as produced by
a dns-0x20 case-randomising forwarder (Unbound `use-caps-for-id`, PowerDNS
Recursor) chained in front of s-hole, or a mixed-case `dig` argument — bypassed
the intercept. It then missed the blocklist and cache and reached `forward()`,
which is exactly the upstream round-trip and LAN-address leak CL 27 was written
to prevent (and the NXDOMAIN answer is not cached, so it leaks on every repeat).

**Fix.** Fold the name with `strings.ToLower` after the qtype guard — the same
normalisation `blocklist.normalize` applies, so the two paths are now
consistent. The fold is placed after the `qtype != PTR` early return, so it only
allocates for actual PTR queries and the non-PTR hot path is untouched.
`TestIsPrivatePTR` gained two mixed-case cases.

### bug_006 (nit) — `Snapshot` load order re-introduces the b/021 race

**What was wrong.** `Snapshot` read `total` before `localPTR`. The handler
records a private PTR as `RecordQuery` (bumps `total`) *then* `RecordLocalPTR`
(bumps `localPTR`), so `localPTR` is the strictly-later counter. Reading it
after `total` means a concurrent PTR query completing between the two atomic
loads can make the observed `localPTR` exceed the observed `total` — the exact
b/021 pattern (`blocked` > `total`), applied to a new counter pair. Consequences:
`/api/stats` could transiently show `local_ptr_count > total_queries`, and
`forwardable = total − blocked − localPTR` could go negative, making the Cache
Hit Rate card flash 0.0 % during PTR bursts (no crash — the `forwardable > 0`
guard prevents the divide).

**Fix.** Read `localPTR` before `total` (as `blocked` is already read before
`total`). The docstring's load-order rationale was rewritten to state the
general rule: every counter incremented *after* `total` in a single query must
be *read before* `total`. Added `TestCounter_LocalPTRNeverExceedsTotalUnderLoad`,
a concurrent regression modelled on the b/021 test, which passes under `-race`.

### bug_003 (nit) — `/debug/pprof/symbol` rejected POST

**What was wrong.** The route was registered as `GET /debug/pprof/symbol`.
`net/http/pprof.Symbol` reads program counters from the URL query on GET and
from the request body on POST, and `go tool pprof` symbolizes by **POST**ing the
PC list (a real profile's list does not fit in a URL). A GET-only pattern makes
the mux answer POST with 405, so remote symbolization — the stated reason CL 20
(R35) exposed pprof at all — silently failed against the stripped binaries the
Makefile ships.

**Fix.** Register `/symbol` for both GET and POST. The obvious "drop the method
prefix" does *not* work: a method-less `/debug/pprof/symbol` conflicts with the
GET-only `/debug/pprof/` prefix under the Go 1.22 mux (more specific path but
more methods — the mux panics at registration), which the added
`TestPprof_SymbolAcceptsPOST` and the existing `TestPprof_OnWhenEnabled` both
caught. Registering the two verbs explicitly is the conflict-free form. `/symbol`
remains behind the `enable_pprof` opt-in, so the security posture is unchanged.

### bug_005 (nit) — banned hardcoded flush sleep in tests

**What was wrong.** `TestTopBlockedEndpoint_WithRealDB` and
`TestQueriesEndpoint_WithRealDB` used `time.Sleep(150 * time.Millisecond)` to
wait for the async SQLite writer to flush — the exact anti-pattern CL 21 (S3)
removed from `internal/dnsserver/integration_test.go` and replaced with a poll
loop. It is both slow on a healthy runner (always waits the worst case) and
flaky under CI contention (a 50 ms flush tick plus the commit can straddle
150 ms, yielding zero rows and a spurious failure).

**Fix.** Added a `waitForRows(t, db, n)` helper that polls `db.Recent` until at
least `n` rows are committed (2 s deadline), mirroring the integration-test
pattern, and used it in both tests. The top-blocked test waits for all four rows
so the per-domain counts it asserts are stable.
