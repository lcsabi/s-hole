# CL 80: code-review fixes (outcome filter round-trip, log wording, upstream-failure test)

## Description

Apply three findings from a `/code-review` pass over the CL 70-79 range. One is
a genuine defect (b/057): the `?outcome=` query filter rejected the same
spelling it reports in each row, so a caller that filtered by the value it read
back silently matched every row. The other two are quality fixes: two operator
log warnings had a comma splice, and the per-upstream transport-failure counter
had no direct test.

## Motivation

The review confirmed the branch was clean on both axes (specification and
standards) with no correctness or spec defects. It surfaced one API-contract
trap and two low-severity quality items worth closing before the work goes out:

- **b/057.** `/api/queries` reports each row's outcome as `upstream_error`
  (underscore), but the `?outcome=` filter accepted only `upstream-error`
  (hyphen). The `parseQueryFilter` switch has no default, so an unrecognized
  value leaves the filter empty and returns all rows. A programmatic consumer
  that round-trips the value it read (`?outcome=upstream_error`) therefore got
  an unfiltered result with no error. The dashboard was unaffected, because it
  sends the hyphen token for filtering and reads the underscore token for the
  row badge, each self-consistent.
- **Log wording.** Two `main.go` warnings joined a state clause and a second
  clause with a comma (a comma splice). CLAUDE.md's STE guidance lists the
  semicolon as an allowed separator, so the branch had moved these the wrong
  way.
- **Test gap.** `upstreamTracker.transportFailures` is cumulative and a later
  success must not reset it. The existing tests covered the cooldown behavior
  only. The invariant was exercised only indirectly through the metrics
  endpoint, so a refactor of `recordSuccess`/`recordFailure` could break it with
  CI still green. This counter feeds `shole_upstream_transport_failures_total`.

## What it does

- **`internal/api/api.go`** (`parseQueryFilter`): the `outcome` switch now also
  accepts the underscore spelling `upstream_error` and normalizes it to the
  `upstream-error` token that `Search` expects. `unresolved` is a single word
  and needs no alias. The behavior for an unknown value is unchanged (it leaves
  the filter unset), which matches the `blocked` filter and the documented
  contract. The function doc records the accepted alias.
- **`cmd/s-hole/main.go`**: the "pprof endpoints enabled" and "admin UI failed
  to bind" warnings use a semicolon between the two clauses instead of a comma.
  Message text only. No structured fields change.
- **Tests**: `TestParseQueryFilter` gains an `outcome=upstream_error` case that
  asserts the underscore form normalizes to `upstream-error`.
  `TestUpstreamTracker_TransportFailureCountsAccumulate` pins that two failures
  count to two, a success does not reset the count, and a second upstream is
  counted independently.

## Design decisions

- **Accept both spellings; do not reject unknown values.** Adding a `default`
  that returns a 400 would change the endpoint from lenient to strict and
  diverge from the `blocked` filter, which also ignores an unrecognized value.
  The round-trip trap is closed by accepting the underscore alias, which is the
  smaller and more consistent change. The canonical query token stays the
  hyphen form.
- **Keep the two vocabularies.** The row label (`upstream_error`) and the query
  token (`upstream-error`) each stay self-consistent end to end (the JSON tag on
  `Bucket.UpstreamError`, `QueryRow.Outcome`, and the dashboard badge use the
  underscore; the dashboard status button, `parseQueryFilter`, and `Search` use
  the hyphen). Renaming either side would churn the dashboard and the stored
  JSON contract for no gain now that the filter accepts both.
- **Semicolon, not a period, in the log warnings.** The slog messages in this
  file are terse phrases with no terminal period, so a semicolon reads better
  than splitting into two sentences and matches the surrounding style.
