# CL 38 — Pin the query-log SQLite pool to one connection (b/038)

## Description

`internal/querylog` opened its SQLite database with `database/sql`'s default
(multi-connection) pool. Two goroutines write to it — the async batch writer
(`run`) and the retention prune (`runPrune`) — and SQLite permits only one
writer at a time. With no `busy_timeout` and more than one pooled connection, a
contending writer failed immediately with `SQLITE_BUSY`; `prune` logs a WARN and
returns on error, so the `DELETE` was silently skipped. This surfaced as an
intermittent CI failure of `TestDBLogger_RetentionPruneDeletesOldRows` under the
race detector ("after prune got 2 rows, want 1").

## Motivation

Two defects, one root cause (a multi-connection pool over a single-writer
embedded database):

1. **Contention → skipped prune / flaky test.** The startup prune, a seed
   transaction, and an explicit `prune()` contended across pooled connections;
   one hit `SQLITE_BUSY`, so the row it was supposed to delete survived. The
   race detector's timing widened the window enough to fail on CI.
2. **Pragmas applied to one connection only.** The per-connection pragmas
   (`synchronous`, `cache_size`, `temp_store`) were run via `db.Exec` on the
   pool, so they stuck only to whichever pooled connection served that call —
   other connections ran without them.

Filed as b/038 (P2).

## Fix

- **`db.SetMaxOpenConns(1)`** in `NewDBLogger`. Pinning the pool to one
  connection makes `database/sql` queue callers instead of letting two writers
  collide, eliminating the internal `SQLITE_BUSY` entirely, and guarantees the
  per-connection pragmas apply to the connection that serves every query. At
  home-network query volume the lost read concurrency is immaterial.
- **`PRAGMA busy_timeout=5000`** added to the pragma block as defence against an
  *external* process (e.g. the `sqlite3` CLI) holding the lock — internal
  contention is already gone via the single connection.

The prune's WARN-and-skip-on-error behaviour is intentionally left as-is: with
contention removed it no longer fires, and a genuinely failed prune stays
best-effort (retried on the next hourly tick).

## Design decisions

**Single connection over a busy_timeout-only fix.** `busy_timeout` alone would
make the writers *wait* for each other, but pinning to one connection is the
standard, robust pattern for an embedded SQLite database behind `database/sql`
in a single process: it removes the contention rather than serialising it after
the fact, and it fixes the pragma-scoping defect for free. WAL is retained for
its write-amplification benefit (SD-card wear on the Pi); it just no longer
needs to support concurrent internal writers.

**Test left unmodified.** `TestDBLogger_RetentionPruneDeletesOldRows` is the
regression guard; the fix makes it deterministic, so only a comment was added
noting the b/038 history. Verified by running it 50× under `-race`, plus the
full race suite.
