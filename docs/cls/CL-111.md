# CL 111: Static analysis gate: gosec in the lint job and CodeQL

## Description

The lint gate now includes security checks:

- `.golangci.yml` enables `gosec`. Each finding is fixed, or its line has a
  `//nolint:gosec // G<NNN>: <reason>` comment. No rule is excluded for the
  whole tree. Test files stay outside gosec, as the config already said.
- `.golangci.yml` enables `nolintlint` with `require-specific`,
  `require-explanation`, and `allow-unused: false`. A `//nolint` comment must
  name its linter and give a reason, and the lint fails when no finding
  needs it.
- `make lint` also lints the Windows build (`lint-windows`, with
  `GOOS=windows`). The CI `lint` job runs golangci-lint a second time with
  `GOOS=windows`. Before, no lint run checked the Windows service code.
- GitHub CodeQL default setup is on for Go, GitHub Actions, and
  JavaScript (the dashboard script), with the default query suite. It is a
  repository setting with no workflow file.
- `SECURITY.md` states both gates.

Review finding: SEC-08. No release change: s-hole itself does not change.

## Motivation

- **SEC-08.** `linters.default: standard` does not include gosec, so the
  `gosec` exclusion for `_test.go` had no effect, and the `//nolint:gosec`
  comments in `internal/blocklist/loader.go` and `internal/service/acl.go`
  were for a linter that did not run. No other static security analysis ran on the code.
- **The Windows build.** The CI lint job and CodeQL's Go build run on
  Linux, so the files that build only for Windows (`internal/service`,
  `cmd/s-hole/*_windows.go`) were never linted. A local lint with
  `GOOS=windows` found 9 old errcheck findings and 1 gosec finding in
  `internal/service/svc_windows.go`. golangci-lint reports one finding for
  each line, so gosec reported 2 more (G104) on the same lines once the
  errcheck entries below were in place.

- The `//nolint:gosec` comment on `http.NewRequest` in
  `internal/blocklist/loader.go` is removed: gosec does not report that
  line, and `nolintlint` refuses an unused directive.
- errcheck: the deferred `(*mgr.Mgr).Disconnect` and `(*mgr.Service).Close`
  calls of the Windows service commands join the `exclude-functions` list,
  with a reason, like the `(*os.File).Close` entries.
- `Makefile`: `lint` runs `lint-windows` (a target-specific
  `export GOOS=windows`) and then the lint for the host.
- `.github/workflows/ci.yml`: a second golangci-lint-action step in the
  `lint` job, with `env: GOOS: windows` and the same pinned version. It
  stays one job, so the required check `lint` covers both builds.

## Design decisions

- **A reason on each line, no rule exclusions.** Most findings are G304
  (a file path from a variable). Every such path comes from the operator's
  config, a fixed list, or a hash. A `filepath.Clean` call would also
  silence G304, but it would not make the code safer; a comment that says
  where the path comes from is more honest and is visible in review. A
  rule-wide exclusion would also hide a new G304 on a path that comes from
  a request.
- **nolintlint.** The SEC-08 acceptance criterion asks for zero unexplained findings. The
  linter enforces it: a bare `//nolint`, a comment with no reason, and a
  stale directive fail the job.
- **One `lint` job for both builds.** A matrix would rename the check
  (`lint (windows)`), and the required check on `master` is `lint`.
- **CodeQL languages.** The SEC-08 decision named Go. GitHub detected
  Actions and JavaScript too, and the maintainer chose all three (no cost
  for a public repository): the Actions queries look for workflow
  injection, and the JavaScript queries look for XSS in the dashboard
  script. Query suite: `default` (high precision).
- **CodeQL is not a required check.** Its results are code scanning alerts.
  Making them block a merge is a separate repository rule; this CL does not
  add it.

## Privacy impact

- **Collects, keeps, sends:** nothing new. s-hole itself does not change;
  the code edits are comments and two discarded `Close` errors in the
  Windows installer.
- **CodeQL** runs on GitHub's runners over the public repository source. It
  sees no data of s-hole users.

## Testing

A separate sub-agent wrote the tests from the requirements, without the
diff. It listed its cases first, then wrote `cmd/s-hole/lintconfig_test.go`
(14 tests), which reuses the workflow helpers of `workflows_test.go`. Each
check is a function that returns a list of problems: the repository tests
run it on the real files, and the negative tests give it broken input.

- `TestLintConfig_GosecAndNolintlint`: gosec and nolintlint are on, with
  the three nolintlint settings; the `_test.go` rule turns off gosec and
  errcheck for test files only; no gosec `excludes` or `includes`, no
  severity or confidence threshold, no preset, no path or text rule that
  reaches a non-test Go file of the repository, no new-issues-only mode.
- `TestGoFiles_NolintSpecificAndExplained`: every `//nolint` in the Go files
  (parsed with `go/parser`) names its linters and gives a reason; a rule ID
  has the `G123:` form; non-test code has no `#nosec` comment and no
  generated-file marker.
- `TestLint_MakeAndCIRunFullConfig`: `make lint` and each
  golangci-lint-action step run the repository config, with no flag that
  turns a linter off or hides findings, no ignored exit status, and no
  `continue-on-error`.
- `TestMakefile_LintWindows`, `TestCI_LintWindows`: `lint` runs
  `lint-windows` with `GOOS=windows`; the one `lint` job (no matrix) has a
  Linux step and a `GOOS: windows` step, with the same pinned action and the
  version from the `Makefile`.
- `TestSecurityMD_StaticAnalysisGates`: the SECURITY.md summary has a gosec
  bullet and a CodeQL bullet with the facts above.
  `TestWorkflows_NoCodeQLWorkflow`: no workflow runs CodeQL.
- A negative test for each check.

Mutation testing: 20 mutations of `.golangci.yml`, the `Makefile`,
`ci.yml`, `SECURITY.md`, and two `//nolint` comments were each caught. The
tester also removed the `//nolint:gosec` in `internal/config/config.go`
(golangci-lint reported G304) and the reason of a `//nolint` in a test file
(nolintlint reported it).

`make check` passes, with `golangci-lint run ./...` at 0 issues for the
Linux and the Windows build (golangci-lint v2.14.0). Coverage is unchanged
(the code edits are comments and two `Close` calls in Windows-only code).
