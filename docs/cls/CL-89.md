# CL 89: reload fixes, correct log levels, and a troubleshooting guide

## Description

Two fixes to the reload path, found in the code review of CL 86 and CL 88,
and a fix and cleanup of the application log, found during the VM test of
the reload fixes.

- **b/060.** With the default `refresh_interval: 24h`, s-hole downloaded its
  blocklists only every 48 hours. `fetchList` served a cache file younger than
  24 hours without a fetch on every call, and the cache written by one timer
  reload was a few seconds under 24 hours old at the next tick. Now
  `blocklist.Update` takes a `Mode`: startup passes `CacheFirst` and keeps the
  fresh-cache shortcut, and every reload passes `DownloadFirst`, which always
  tries the download and falls back to the cache only when the download fails.
- **b/061.** A reload request that arrived while a reload ran was dropped,
  with no log line on the timer and SIGHUP paths. Now `newReloadFn` queues it:
  the running reload does one more pass when it finishes. Any number of
  requests during one pass queue a single follow-up, so passes still never
  overlap. `POST /api/reload` answers `"reload queued"` in place of `"reload
  already in progress"`, and the dashboard's Reload button shows which one
  happened.
- **b/062.** Every line from the `api`, `blocklist`, `config`, `dns`, and
  `querylog` packages was logged at INFO, with the whole record inside `msg`
  (`level=INFO msg="WARN download failed ... pkg=blocklist url=..."`). The
  package loggers were built with `slog.With` at package init, before `main`
  installed its handler. A new package, `internal/logging`, gives `For(pkg)`,
  whose handler looks up `slog.Default()` for each record.
- **Log cleanup.** Under systemd, each line starts with its syslog priority, so
  `journalctl -p warning` works, and text lines drop the `time=` field that
  journald already records. Messages that named only a thing (`msg=config`,
  `msg=service`, `msg="db insert"`) now say what happened, and advice moved
  into a `hint` field. The multi-line `[stats]` block is one `msg=stats` line.
- **`docs/TROUBLESHOOTING.md`.** A new page for operators: for each common
  problem, the command to run, the log lines it can show, and what to do.

## Motivation

The reviewer found that the new Reload tooltip ("Re-downloads the
blocklists") contradicted `fetchList`, which serves a cache under 24 hours old.
Checking the timer against the cache age showed the larger problem: the timer
tick and the cache age are both 24 hours, and the download finishes a few
seconds after the tick, so every second tick loaded from the cache. The CL 88
`from` attribute made it visible (`from=cache` on a timer reload). With the
default config, a list that the maintainer fixes upstream reached s-hole up to
two days later.

The reviewer also found that a dropped reload matters for the CL 86 certbot
deploy hook. The hook installs a renewed certificate and runs `systemctl reload
s-hole`. If a timer reload was downloading at that moment, it had already read
the old certificate files, and the hook's request did nothing. The new
certificate then waited for the next timer reload, and nothing in the log said
so.

The maintainer found b/062 in the journal during the VM test of the two
fixes above: the `blocklist` lines had `level=INFO msg="INFO loaded ...
from=download"`. A small reproduction showed the larger problem: a WARN or
ERROR from these packages also became `level=INFO`, so a search for
problems missed "all sources failed" and "db commit failed, dropping batch".
The same review of the journal showed the other problems that the cleanup
fixes. The time appeared twice on each line. `journalctl -p warning` showed
nothing, because journald stored every line as info. About 15 messages were
a bare noun that did not say what happened. Every 5 minutes, the `[stats]`
block added up to 13 lines with no level. An operator also had no guide to
the lines that matter when something breaks.

## What it does

- **`internal/blocklist/loader.go`.** New type `Mode` with `CacheFirst` and
  `DownloadFirst`. `Update` and `fetchList` take it. The fresh-cache check runs
  only for `CacheFirst`; the stale-cache fallbacks (connection error, non-200,
  truncation at the size cap) are unchanged for both modes.
- **`cmd/s-hole/main.go`.** The startup load passes `CacheFirst`; the reload
  work passes `DownloadFirst`. `newReloadFn` replaces its `TryLock` gate with a
  small state machine under a mutex (`running`, `queued`). A call while a pass
  runs sets `queued` and returns false; the pass checks and clears `queued`
  under the same mutex when it finishes, so a request cannot slip between the
  check and the release. `runCtx` is now created before the reload closure,
  which takes it: once shutdown cancels it, a queued pass is dropped.
- **`internal/api/api.go`.** The reply for a queued request is `"reload
  queued"`.
- **`internal/api/static/index.html`.** The Reload button reads the reply and
  flashes "Reload queued: it runs after the current reload" or "Reload
  triggered".
- **`internal/logging` (new).** `For(pkg)` returns a logger whose handler
  resolves `slog.Default()` for each record and replays `With` and `WithGroup`
  onto it. `NewStdoutHandler(w, json, journal)` builds the stdout handler. In
  journal mode it keeps one inner handler per level, each writing through a
  shared-mutex writer that puts the sd-daemon prefix (`<7>`, `<6>`, `<4>`,
  `<3>`) and the line in one `Write`. Text lines drop `time`; JSON lines keep
  it. `StdoutIsJournal` (unix) compares `JOURNAL_STREAM` with stdout's device
  and inode; on Windows it is false.
- **Package loggers.** `api`, `blocklist`, `config`, `dns`, and `querylog` use
  `logging.For`. `stats` gets a logger too.
- **`internal/stats/stats.go`.** `Counter.Print` becomes `Counter.Log`: one
  INFO record, `msg=stats`, with the counters as fields, including
  `forward_failures` and `upstream_errors`. `main` calls it on the
  `stats_interval` ticker and at shutdown (`shutdownDeps.logStats`, renamed
  from `printStats`).
- **Messages.** About 27 messages renamed to say what happened. The
  CHANGELOG lists each old and new message. `admin UI listening` drops its
  `addr` field, which repeated `url`.
- **Docs.** README (startup-only cache note, the `/api/reload` row), DESIGN
  (blocklist caching, the reload paragraph, the `/api/reload` route row, the
  test-coverage list), CLAUDE.md (the single-flight reload description),
  CONTRIBUTING (smoke-test step 5),
  the `SourceStatus` comment in `store.go`, CHANGELOG, and b/060, b/061, and
  b/062 in BUGS.md. For the logging: the new `docs/TROUBLESHOOTING.md`, the
  DESIGN logging paragraph, the README contents, `S_HOLE_LOG_FORMAT` row,
  service commands, and package table, the CLAUDE.md package-logger rule, and
  the coverage floor for `internal/logging` in CLAUDE.md, README, DESIGN, and
  CONTRIBUTING.

## Design decisions

- **Reloads always download; startup keeps the cache.** The cache has two
  jobs: a fallback when a download fails, and a fast restart that does not
  re-fetch every list. Only the second job caused b/060, and it matters only
  at startup. A smaller fix was to compare the cache age with a margin below
  `refresh_interval`. It was rejected because a manual reload would still
  serve the cache for up to 24 hours, which is not what an operator who
  clicks Reload expects, and the tooltip would stay wrong.
- **Coalesce into one follow-up pass, not one per request.** One pass after
  the last request does all the work any of the queued requests asked for: it
  re-reads the certificate and downloads the lists after they arrived. More
  passes would only repeat the downloads.
- **Log-only was the smaller fix for b/061, and it was not enough.** Logging
  the drop would make it visible, but the renewed certificate would still wait
  for the next timer reload.
- **The gate stays in `main`.** The queue lives in the `newReloadFn` closure,
  the same place as the old mutex, so the timer cannot bypass it (b/022).
- **Drop a queued pass during shutdown.** `shutdown` waits for the in-flight
  reload with a bounded budget. A queued pass could add a full download to
  that wait. The pass in flight still finishes, as before.
- **The API reply text changes.** `"reload already in progress"` would now be
  wrong, because the request is not dropped. A script that matched the old
  text must change; the CHANGELOG says so under Changed.
- **Resolve the handler per record, not at init.** Two other fixes were
  possible. `main` could pass a logger to every package, but that changes
  every constructor for a cross-cutting concern. A package could call
  `slog.Default()` at each log site, but a new log site that forgets it
  brings the bug back. `logging.For` keeps the one-line package var, and the
  CLAUDE.md rule names it. The cost is one `WithAttrs` per record; the DNS
  hot path logs only on failures.
- **Detect the journal the way systemd documents it.** A check for a
  non-empty `JOURNAL_STREAM` is simpler, but a terminal started from a
  systemd user session can inherit the variable. The terminal then showed
  `<6>` prefixes and no time. The device and inode comparison avoids that.
- **Keep `level=` in journal lines.** journald removes the priority prefix, so
  `level=` is the only level text left in `journalctl` output. The same
  `level=WARN` search then works under systemd, in Docker, and in a terminal.
- **Drop the top-5 lists from the stats line.** Five domains and five clients
  in one line make it long, and the dashboard and `/api/stats` show the same
  lists with more context. The failure counters are more useful in the log,
  because they point at an upstream problem.
- **Rename messages now.** A rename breaks a saved search, so the CHANGELOG
  lists every old and new message. The renames go into one CL so that
  operators update their searches once.
- **Remove semicolons and `-ing` verbs from the new messages** (STE rules 8.1
  and 3.5), for example `reload queued until the running reload ends` and
  `queued reload started`. Older messages such as `ignoring malformed
  upstream` and `shutting down` keep their text, because the guide and
  existing searches quote them and they read clearly.

## Testing

A separate cold sub-agent wrote the tests from the requirements (the b/060
and b/061 reports and this CL's behavior list), without the diff. It listed its
cases before it read the existing tests.

- **`internal/blocklist/loader_test.go`.** `TestUpdate_DownloadFirstIgnoresFreshCache`,
  `TestUpdate_ReloadSoonAfterDownloadRefetches` (the b/060 shape: a download,
  then a reload seconds later, makes two requests),
  `TestUpdate_CacheFirstStillServesFreshCacheAfterDownload`,
  `TestUpdate_DownloadFirstFailureServesStaleCache` (connection error, non-200,
  and truncation, each with a 10-second-old and a 48-hour-old cache),
  `TestUpdate_DownloadFirstFailureNoCacheIsHardFailure`, and
  `TestUpdate_DownloadFirstNeverLogsFromCache`. The existing tests pass
  `CacheFirst`, because they test the startup behavior.
- **`cmd/s-hole/main_test.go`.** `TestNewReloadFn_SingleFlight` is rewritten for
  b/061: the second call returns false, no pass overlaps, and exactly one
  follow-up runs. New: `TestNewReloadFn_ManyCallsQueueOnePass`,
  `_CallDuringFollowUpQueuesAgain`, `_WaitGroupCoversFollowUp`,
  `_CancelDropsQueuedPass`, `_LogsQueueOncePerPass`, and
  `_NoOverlapNoLostRequestUnderStress` (200 rounds of 8 goroutines, 20 calls
  each; the last pass must see the last request). Every wait in the helpers is
  bounded, so a closure that runs too many passes fails instead of hanging.
- **`internal/api/api_test.go`.** `TestReload_QueuedWhenReloadRuns` replaces
  `TestReload_AlreadyInProgressDoesNotDispatch`, and
  `TestReload_ConcurrentCallsOneTriggeredRestQueued` replaces
  `TestReload_ConcurrentCallsCollapse`. The new version is deterministic:
  exactly one `"reload triggered"`, and 49 `"reload queued"`.

Mutation testing: 12 mutations, all caught. They were: `DownloadFirst`
behaving as `CacheFirst` and the reverse, a fallback logging `from=cache`,
dropping the queue, ignoring ctx, one follow-up per call, the queue log line on
every call, `wg.Done` after the first pass, a lost-request window (`running`
cleared in a second critical section, caught by the stress test), an
overlapping follow-up, the old API string, and an API that always answers
"triggered".

VM test (Debian 13 VM, systemd service, build `bf157a1`, 2026-09-29):

- **Journal format.** Startup lines are stored at `PRIORITY=6` with no
  `time=` field, and every package line has its own level and separate
  fields (`msg=loaded pkg=blocklist ... from=cache`). With both downloads
  blocked, the two `download failed, using stale cache` lines are
  `level=WARN`, stored at `PRIORITY=4`, and `journalctl -u s-hole -p warning`
  shows exactly those two lines. Over SSH, outside systemd, lines keep `time=`.
- **b/060.** Startup used the fresh cache (`from=cache`). The first timer
  reload, 2 minutes later with `refresh_interval: 2m`, logged `from=download`
  for both lists. A manual reload and `systemctl reload` also downloaded.
- **b/061.** Two quick `POST /api/reload` calls answered `reload triggered`,
  then `reload queued`, and ran two passes. Five calls ran two passes, with one
  queue line and one `queued reload started`. Two `systemctl reload` calls
  exited 0 and ran two passes. A stop right after a queued request took 0.16
  s: the pass in flight finished, and the queued pass did not run.
- **Stale fallback.** With TCP 80 and 443 rejected for IPv4 and IPv6, both
  lists loaded `from=stale_cache`, `/api/stats` showed them stale, and
  `shole_blocklist_source_stale` was 1. A reload after the rules were removed
  downloaded both and cleared the flags. An IPv4-only rule is not enough:
  `raw.githubusercontent.com` is reachable over IPv6, so that list still
  downloaded in the maintainer's first try.
- **CONTRIBUTING smoke test** on port 53: probes, sinkhole and suffix
  blocking, cache hit, whitelist round-trip, `/api/check`, DoT with `dig
  +tls`, stats and metrics agreeing (7 queries, 4 blocked, 1 cache hit), the
  one-line `msg=stats` at shutdown, and the query history kept over a
  restart. `-check-config` on a bad file exits 1 with `config load failed`.
- **Dashboard.** The maintainer clicked Reload twice quickly: the flashes
  were "Reload triggered", then "Reload queued: it runs after the current
  reload".

Manual check for the maintainer: CONTRIBUTING smoke-test step 5 (two quick
