# CL 110: Overwrite the SQLite WAL with zeros before SQLite frees it

## Description

s-hole now overwrites the query database's write-ahead log (the `-wal`
file) with zeros at every point where SQLite frees it:

- at startup, after the migration and any crash recovery;
- after a retention prune that deleted rows;
- in an online purge, after the row deletes and again after the `VACUUM`;
- in `DBLogger.Close`, after the last flush and before the database closes.

`journal_size_limit` is now `-1`, so SQLite no longer shortens the WAL after
a commit on its own. `ZeroFile` writes and syncs the first 32 bytes (the WAL
header) before the rest of the file.

Review finding: PRIV-16. Target release: v2.1.0.

## Motivation

- **PRIV-16.** In WAL mode, each flush appends copies of the changed 4 KiB
  pages, with domains, clients, and times, to `queries.db-wal`. SQLite never
  overwrites the WAL: `wal_checkpoint(TRUNCATE)` cuts it to zero bytes,
  `journal_size_limit` cuts it after a commit, and the close of the last
  connection deletes it. Each of these only frees the disk blocks. So after
  a prune, a purge, or a stop, older page copies stayed in free blocks. The
  offline purge (CL 105) could not reach them, because SQLite deleted the
  WAL when s-hole stopped. The CL 105 live check found 2352 test-domain hits
  in the raw image after a clean stop and an offline purge, all in blocks of
  the deleted WAL (2111 in this CL's own run on master; see Testing).

## What it does

- `internal/querylog/db.go`:
  - `wipeWAL(ctx, conn)` runs on the one connection, which the caller holds
    for the whole sequence:
    1. `PRAGMA wal_checkpoint(RESTART)`. It goes on only when the result is
       busy = 0 and every frame was copied into the database file.
    2. `PRAGMA data_version`, `BEGIN IMMEDIATE`, and `PRAGMA data_version`
       again. The write lock stops any other process from adding a frame,
       and an unchanged data version shows that no other process wrote
       after the checkpoint.
    3. `ZeroFile` on the `-wal` file. A missing file is not an error.
    4. `ROLLBACK` (the transaction is empty), then
       `PRAGMA wal_checkpoint(TRUNCATE)`.

    If a check fails, `wipeWAL` neither overwrites nor truncates the WAL
    and returns an error (`errWALBusy` for the first two checks).
  - `NewDBLogger` runs `wipeWAL` after `migrate`, before the writer starts.
  - `prune` holds the connection for the `DELETE` and the `wipeWAL`, so no
    flush runs between them. The old `checkpoint` function is gone.
  - `purgeAll` holds the connection for every step and runs `wipeWAL` in
    place of each TRUNCATE checkpoint. A failed `wipeWAL` fails the purge
    (`WAL overwrite: ...`).
  - `Close` runs `wipeWAL` after the writer and the prune goroutine stop,
    then closes the database.
  - At start, prune, and stop, a failure is a WARN:
    `query log WAL overwrite failed`, with `at` (`start`, `prune`, `stop`),
    `err`, and a `hint`. It names no domain or client.
  - `journal_size_limit=-1` replaces `4194304`.
  - Two package-level test seams: `walFreeHook` (called with the WAL path
    after the overwrite and before the TRUNCATE checkpoint) and
    `walCheckpointHook` (called after the RESTART checkpoint and before
    `BEGIN IMMEDIATE`). Production never sets them.
- `internal/querylog/zero.go`: `ZeroFile` writes and syncs the first 32
  bytes before it writes the rest, then syncs again.

## Design decisions

Decided with the maintainer before the code was written (2026-10-09).

- **Overwrite the WAL ourselves, with guards.** After a complete checkpoint,
  SQLite reads no frame from the WAL: a reader takes the database pages
  only, and the next writer starts the WAL again from offset 0 with a new
  header and new salts. So the old frames are free to overwrite. The guards
  make sure that this state holds while s-hole writes the zeros: the
  RESTART result proves the complete checkpoint (and SQLite has synced the
  database file), the held connection stops s-hole's own writer, and the
  write lock with an unchanged `data_version` stops another process. If a
  check fails, the WAL keeps its data in the file, where the next wipe can
  reach it, instead of in free blocks that nothing can reach.
- **Header first.** A test copy of a WAL with a valid header and the second
  half of its frames zeroed recovered only the first frames: `integrity_check`
  said `ok`, but 1,600 rows silently lost their last update, because
  recovery replayed older page images over newer pages in the database. A
  copy with only the header zeroed opened with the current data: SQLite
  ignores a WAL whose header is not valid. So `ZeroFile` writes and syncs
  the header before the rest. A power loss during the overwrite then leaves
  a WAL that recovery replays in full (all of it already in the database) or
  ignores. The extra sync costs one `fsync` per call, also for the log file
  and the offline purge.
- **Only the `-wal` file.** SQLite holds POSIX locks on the database and
  `-shm` files. Closing any other descriptor of such a file drops all of the
  process's locks on it. The WAL file has no locks, so a second descriptor
  is safe there only.
- **`journal_size_limit=-1`.** With the old 4 MiB limit, a WAL that grew
  past 4 MiB was cut back at the first commit after a checkpoint, without an
  overwrite (measured: 5,133,552 to 4,194,304 bytes). Now only `wipeWAL` and
  the close after it shorten the WAL. A WAL that grew (a large transaction,
  or another program that holds a read transaction) keeps its size until
  the next wipe; every large transaction in s-hole (prune, purge, migration)
  is followed by one.
- **A failed purge.** If the purge cannot overwrite the WAL, the WAL still
  holds the deleted rows, so the purge reports the step as failed.
- **Alternatives considered:** a transaction that writes a zero-filled blob
  as large as the WAL (no outside write, but the database grows by the WAL
  size, the coverage is approximate, and it adds SD wear);
  `journal_mode=MEMORY` (no WAL, but a crash or power loss during a flush
  can corrupt the database); and documenting the limit (the state after CL
  105). Rollback-journal modes keep old page images in the same way, and a
  persistent WAL without an overwrite keeps deleted rows in the file (b/077).
- **Cost.** Each wipe writes the size of the WAL in zeros (at most a few
  MiB at home-network volume) and syncs twice. The prune holds the
  connection for this time; the DNS path does not wait, because `Log` only
  queues an entry or drops it.

## Privacy impact

- **Collects:** nothing new.
- **Keeps:** less. The blocks that the WAL frees after a prune, a purge, or
  a stop hold zeros, not page images. On flash storage and on a
  copy-on-write file system, the zeros can go to new blocks (best effort, as
  before).
- **Who can read:** reading free disk blocks needs raw disk access (root, or
  the disk itself); this CL reduces what such a reader finds.
- **Sends:** nothing new. The new WARN names no domain or client.

## Testing

A separate agent wrote the tests from the requirements, without the diff.
`walFreeHook` records the WAL bytes at each point where s-hole frees the WAL.

- `TestDBLogger_PruneZeroesWALBeforeItIsFreed`,
  `TestDBLogger_PurgeZeroesWALBeforeItIsFreed`,
  `TestDBLogger_CloseZeroesWALBeforeItIsFreed`: while other goroutines call
  `Log`, the WAL holds only zeros at each free point (one at a prune, two in
  a purge, one at `Close`), with no test domain or client;
  `integrity_check` is ok after each step; after a restart, every row that
  was not deleted is there.
- `TestNewDBLogger_ZeroesLeftoverWALAtStart`: a WAL that a crash left is
  zeroed at startup, and its committed rows are kept.
- `TestDBLogger_WALWipeRefusedWhileAnotherConnectionReads`,
  `TestDBLogger_WALWipeRefusesHardLinkedWAL`, and
  `TestDBLogger_WALWipeRefusedWhenAnotherConnectionWritesAfterCheckpoint`
  (through `walCheckpointHook`): when a guard fails, the WAL is neither
  zeroed nor truncated, the purge returns an error, the prune and `Close`
  log the WARN while the guard fails (with no domain or client), and the
  other connection's rows are kept, also after a restart.
- `TestDBLogger_WALIsNotShortenedAfterCommit`: `journal_size_limit` is -1,
  and a small commit after a large transaction does not shorten the WAL.
- `TestDBLogger_WALWipeKeepsRowsOfAnotherWriter`: rows that another
  connection commits survive each wipe.
- `TestZeroFile_OverwritesAroundTheHeader`: sizes around the 32-byte split
  are zeroed completely and keep their size.

Mutation testing: 19 mutations (no zeroing, no RESTART guard, no
`data_version` guard, a refusal ignored, `journal_size_limit=0`, a missing
wipe at each point, a purge that ignores the error, zeros before the
checkpoint, and others) were each caught. Without the `data_version` guard,
the write test corrupted the database (`database disk image is malformed`).
The header-first order and its sync are not tested (no fault injection);
the Design decisions record the measurement behind them.

`make check` passes, also `go test -race` for `querylog`. Coverage:
`querylog` 87.3%. The `querylog` tests also pass on Windows 10 (the WSL
host, not elevated).

Live on the Debian 13 VM, each case on a new 64 MiB ext4 file system in a
loop device, with `mode: all` and a database; the raw image was searched
after `sync`. "stop" is 300 queries, a clean stop, then `s-hole -purge`.
"prune" is 3,000 rows in the old format (local time, uppercase domains),
which the startup migration rewrites and the startup prune deletes
(retention 1 day). "online" is 300 queries, then `POST /api/purge`.
