# CL 69: Graduate the CHANGELOG to v0.2.1

## Description

Graduate the CHANGELOG's `[Unreleased]` section to `[0.2.1] - 2026-09-03` and add
a fresh empty `[Unreleased]` above it. This is the bookkeeping step that a
`v0.2.1` tag push needs: `.github/workflows/release.yml` draws the GitHub Release
notes from the matching `[0.2.1]` CHANGELOG section, so that section must exist at
the tagged commit. No workflow or Go code changes.

## Motivation

`v0.2.0` shipped on 2026-08-28. Since then the `[Unreleased]` section has
collected the operator-visible work from CL 59-63 and CL 65-68: clean-shutdown
data-loss fix, single-contact upstream failover, config guards for
`db_flush_interval`/`refresh_interval`/`stats_interval`, case-insensitive
fail-safe boolean env overrides, hash-derived cache filenames, over-size source
handling, the admin-server bind-failure banner, the stop-before-store window fix,
the Linux installer hardening, and the new `-check-config` flag. These are
shippable but have never carried a version tag. Cutting `v0.2.1` turns that
running section into a named release so bug reports can name a real build.

The release is mostly fixes. The one new user-facing feature is `-check-config`
(CL 66), plus installer hardening. A patch bump is the maintainer's call for a
pre-1.0 project that loosely tracks SemVer; the work is dominated by robustness
fixes to the `v0.2.0` line.

## What it does

- Rename `## [Unreleased]` to `## [0.2.1] - 2026-09-03`, then insert a fresh empty
  `## [Unreleased]` above it.
- Bump the three illustrative version strings in `README.md` (the release tarball
  name, the `ghcr.io` pull comment, and the `-version` output example) from
  `0.2.0` to `0.2.1`, so the docs show the current release.

The graduated `[0.2.1]` section carries exactly the bullets already written under
`[Unreleased]`: two Added (CL 66), one Changed (CL 67), and eight Fixed (CL 59-63,
CL 68). The internal-perf and doc-sync CLs since `v0.2.0` (CL 64 and the doc-only
merges) have no operator-visible behavior, so they carry no release-notes bullet.

## Design decisions

- **Graduation is its own CL, merged before the tag.** CONTRIBUTING's "Cutting a
  release" requires the tag to point at a commit whose CHANGELOG already carries
  the release section, or the `awk` notes extractor falls back to a placeholder.
  This CL lands that section first.
- **Bookkeeping CL, no CHANGELOG bullet of its own.** The graduation changes no
  runtime behavior, so it adds no entry to the new `[Unreleased]` section. The
  README example bump is documentation-only for the same reason.
- **The roadmap record is deferred to a post-tag commit.** Item 2's row and
  narrative record each release with its real tagged commit and confirmed date
  (as PR #29 did for `v0.2.0`). That commit lands after the `v0.2.1` tag is out,
  not here, so it can name the actual commit hash.

## Files changed

- `docs/CHANGELOG.md`: graduate `[Unreleased]` to `[0.2.1] - 2026-09-03`, add a
  fresh empty `[Unreleased]`.
- `README.md`: bump the three `0.2.0` example strings to `0.2.1`.
- `docs/CL.md`: index row for CL 69.

No Go code changed. `internal/version` already consumes the ldflags, so a build
tagged `v0.2.1` reports the tag with no source change.

## Testing

- `make check` (fmt + vet + lint + test) stays green; no Go code changed.
- Ran the release-notes `awk` extractor from `release.yml` against the graduated
  `docs/CHANGELOG.md` with `version=0.2.1`; it returns exactly the `[0.2.1]` body
  and nothing from `[0.2.0]`.
- End-to-end validation is a maintainer step: push `v0.2.1-rc1`, confirm the four
  archives plus `SHA256SUMS` land on a `--prerelease` Release, that
  `sha256sum -c SHA256SUMS` passes, that a downloaded binary reports
  `s-hole v0.2.1-rc1`, and that `docker pull ghcr.io/lcsabi/s-hole:0.2.1-rc1`
  runs and reports the same version without moving `:latest`. Then delete the rc
  and cut `v0.2.1`.
