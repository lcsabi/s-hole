# CL 51: document the benchmarking and profiling workflow

## Description

Add a "Benchmarking and profiling" subsection to `CONTRIBUTING.md` and a one-line
pointer to it from the `DESIGN.md` benchmark paragraph.

## Motivation

The benchmarks were described (DESIGN says what the four cover and that
`make bench` is a regression smoke), but the workflow for measuring and profiling
was not written down anywhere. A contributor who wanted to prove a change is
faster, or find where a benchmark allocates, had to reconstruct the commands.
This also matches a value the project already holds: the ROADMAP non-goal against
tuning knobs "without a benchmark", and CL 50 shipping with `benchstat` evidence.

## What it does

The new subsection gives copy-pasteable commands for three tasks, all proven
during the CL 50 profiling session:

- Measure one benchmark with `-benchmem -count=N` (versus `make bench`, which runs
  each once as a smoke).
- Compare before and after with `benchstat`, which reports a p-value so a real
  change is distinguishable from noise.
- Profile a benchmark (`-cpuprofile`/`-memprofile` plus `go tool pprof`) or a live
  instance (`enable_pprof`, localhost-bound).

It closes with two honest framings: profiling this codebase usually confirms the
design rather than revealing a problem, so it is a diagnostic reached for on a
symptom; and the numbers depend on the machine, so measure on the target hardware
when the absolute value matters.

The `CONTRIBUTING.md` section is the workflow home (it sits next to the Fuzz tests
and Manual smoke test sections). `DESIGN.md` keeps only a cross-reference, since it
documents rationale rather than procedure.
