# CL 108: CI and release supply chain

## Description

- **Actions pinned to a commit SHA.** Every `uses:` in `ci.yml`,
  `release.yml`, and the new `vulncheck.yml` names a full commit SHA with a
  `# vX.Y.Z` comment. Dependabot (`github-actions`, already configured)
  moves the SHA and the comment together.
- **golangci-lint pinned.** `GOLANGCI_LINT_VERSION ?= v2.14.0` in the
  `Makefile` is the one pin. `make tools-install` installs that release, and
  the CI lint job reads the line and passes it to the action (before:
  `version: latest`).
- **Least-privilege tokens.** `ci.yml` and `vulncheck.yml` declare
  `contents: read` for the workflow. `release.yml` declares `permissions: {}`
  for the workflow, and each job declares its own: `build` reads the
  repository and signs attestations; `release` writes the GitHub Release;
  `docker` pushes the image and signs its attestation. Every
  `actions/checkout` step sets `persist-credentials: false`, because no job
  pushes to git. The govulncheck action gets `repo-checkout: false`, so its
  own checkout does not keep the token either.
- **Build provenance.** The `build` job signs a build provenance attestation
  (`actions/attest`) for its archive and for the binary in it. The `docker`
  job signs one for the image and pushes it to the registry. Users check them
  with `gh attestation verify` (README).
- **Image SBOM.** `docker/build-push-action` runs with `sbom: true` and
  `provenance: mode=max`, so BuildKit stores an SBOM and its own provenance
  next to the image.
- **Clean release builds.** The release `setup-go` step sets `cache: false`.
  A Go cache that a CI run on `master` saved cannot change the published
  binaries.
- **Go version in the release notes.** Each build job records
  `go env GOVERSION`. The release job checks that all four agree and adds a
  "Build" section to the notes with that version and the version of the
  `golang` image that the Dockerfile pins.
- **Base images by digest.** The Dockerfile pins
  `golang:1.26.9-alpine3.24@sha256:…` and `alpine:3.24@sha256:…`.
- **Weekly vulnerability scan.** `.github/workflows/vulncheck.yml` runs every
  Monday and on demand: `govulncheck` on `master`, and
  `govulncheck -mode=binary` on each binary of the latest release (after a
  `SHA256SUMS` check). A finding fails the run.
- **CI step outputs through `env`.** The cross-compile step reads the version
  metadata from environment variables, not from `${{ }}` expressions inside
  the script.

Review findings: SEC-04, SEC-05, SEC-06, SEC-07. No Go code changes; the
image and the binaries are built the same way. Target release: v2.1.0.

## Motivation

- **SEC-04.** A tag such as `@v7` can move. A moved or compromised tag would
  run new code in the release job, which can write releases and push the
  image. `version: latest` changed the lint result whenever golangci-lint
  published a release.
- **SEC-05.** `release.yml` gave `contents: write` and `packages: write` to
  every job, also to the four build jobs that only compile. `ci.yml` relied
  on the repository's default token setting, so a change of that setting
  would widen it without a diff.
- **SEC-06.** `SHA256SUMS` comes from the same place as the archives. It
  shows that a download is complete, not who built it. An attestation is
  signed with a short-lived certificate that names this repository, the
  workflow, and the commit.
- **SEC-07.** A release did not record which Go patch built it, the image
  bases could change under the same tag, and nothing noticed when a new Go
  or module advisory affected a binary that was already published. Example:
  on 2026-10-09, `govulncheck -mode=binary` found 12 standard-library
  advisories in the v2.0.1 binaries (built with go1.26.8; fixed in
  go1.26.9). The CI scan of the source did not show them, because CI already
  used go1.26.9.

## Design decisions

- **`actions/attest`, not `actions/attest-build-provenance`.** Since v4 the
  second action is a wrapper around the first, and its notes ask new users to
  use `actions/attest`. Default mode (no SBOM or predicate input) is SLSA
  build provenance.
- **Attest in the build job.** The archive is signed where it is built,
  before it passes through the workflow's artifact storage. The build job
  gets `id-token: write` and `attestations: write` for that. It runs only
  `go build`, which runs no module code (no cgo, no `go generate`).
- **No storage record.** `actions/attest` can also create an artifact storage
  record for the image. That needs the `artifact-metadata` right and serves
  organization artifact tracking, which this repository does not use, so
  `create-storage-record: false`.
- **The binary is signed too.** The attestation for an archive also names the
  binary in it, so an operator can check an installed `s-hole` without the
  archive.
- **The image can be one Go patch behind the archives.** The archives float
  on Go 1.26 (decided); the image uses the `golang` image that the
  Dockerfile pins, which moves when the Dependabot `docker` update merges.
  The release notes name both, so the difference is visible.
- **SBOM for the image only** (decided with the maintainer). An archive
  holds one static Go binary, and `go version -m` already lists the modules
  in it. The image adds Alpine packages, so it gets the SBOM.
- **One Go version for all archives.** If two build jobs report different Go
  versions (a Go release during the run), the release job fails before it
  creates the release. Run the workflow again.
- **govulncheck stays an action in CI.** `golang/govulncheck-action` pins
  its own steps by SHA, and Dependabot updates it. The weekly binary scan
  cannot use it (the action has no `-mode` input), so that job installs
  `govulncheck@v1.8.0` with `go install`. The advisories come from the live
  database on each run, so the scanner pin does not age the scan.
- **A failed run is the alarm.** A finding fails the scheduled run, and
  GitHub notifies the maintainer. No issue is opened, so the workflow needs
  no `issues: write`. GitHub turns a scheduled workflow off after 60 days
  without repository activity; the Actions page then shows it as disabled.
- **The scheduled scan fails until v2.1.0 ships.** The latest release
  (v2.0.1) has the go1.26.8 advisories above. That is the intended signal.

## Repository settings

These settings are part of this CL. They are applied with `gh api` after
the PR merges, with the maintainer's agreement, and recorded here:

- Immutable releases: on (assets and tag of a published release cannot
  change).
- Tag ruleset for `v*`: no deletion and no update; pre-release tags (`v*-*`)
  excluded, so a dry-run tag can be removed after its release is deleted.
- Required status checks on `master`: `govulncheck` and `shellcheck` added
  to the existing ones.
- Dependabot security updates: on.
- Actions: "require actions to be pinned to a full-length commit SHA" on;
  "allow selected actions": GitHub-owned actions plus
  `golangci/golangci-lint-action`, `golang/govulncheck-action`, and
  `docker/setup-qemu-action`, `docker/setup-buildx-action`,
  `docker/login-action`, `docker/build-push-action`.

## Privacy impact

- **Collects, keeps, sends:** nothing new. s-hole itself does not change.
- **Attestations:** a signed attestation names this repository, the workflow
  file, the commit, and the tag, which are public already. GitHub stores it,
  and, for a public repository, the public Sigstore transparency log records
  the signing certificate. It holds no data about s-hole users.
- **`gh attestation verify`** is a command that an operator runs on their own
  machine. It contacts GitHub, not s-hole. s-hole makes no new outbound
  connection.

## Testing

A separate sub-agent wrote the tests from the requirements, without the
diff. It listed its cases first, then wrote `cmd/s-hole/workflows_test.go`
(23 tests), next to `unit_test.go`, which also reads repository files. Each
check is a function that returns a list of problems: the repository tests
run it on the real files, and the negative tests give it broken input. Every
file in `.github/workflows` is checked, so a new workflow is covered too.

- SEC-04: every `uses:` is `owner/repo[/path]@<40 hex>` with a `# vX.Y.Z`
  comment (tags, short SHAs, local and `docker://` references, and flow
  style are refused); the `Makefile` has one exact v2 pin, `tools-install`
  uses it, and the CI lint step reads it (the test runs the step's `sed`
  through `sh` when a shell is present).
- SEC-05: every workflow has top-level permissions, no `read-all` or
  `write-all`, and no write right at the top level; the exact map of each
  `release.yml` job is pinned; a job has `id-token: write` and
  `attestations: write` if and only if it signs an attestation; every
  checkout sets `persist-credentials: false`; the govulncheck action has
  `repo-checkout: false` after its own checkout.
- SEC-06: the build job attests the archive and the binary before the upload;
  the docker job has `sbom: true`, `provenance: mode=max`, and an attest step
  with `push-to-registry: true` and the digest of the push step; release
  `setup-go` steps set `cache: false`.
- SEC-07: every Dockerfile `FROM` has a digest; there is one
  `golang:X.Y.Z-` builder whose minor release matches `go.mod`; the release
  notes `sed` finds it; every `go-version` is the quoted `go.mod` minor
  release (`"1.26"`); `vulncheck.yml` has a weekly cron, `workflow_dispatch`,
  a source scan of `master`, and a `-mode=binary` scan after
  `gh release download`.

The tester ran 45 mutations on the five files (for example a tag instead of
a SHA, a removed permissions block, `persist-credentials: true`, a removed
digest, `version: latest`, `sbom: false`, `cache: true`, a daily cron). At
least one test caught each mutation, and the files were byte-identical
afterwards. No new test failed against the files. A Dependabot update that
moves the `golang` image to a new minor release (for example 1.27) fails
`TestDockerfile_ImagesPinnedByDigest` on purpose: the `go.mod` minor release
and the image move together, by decision.

`make check` passes.
