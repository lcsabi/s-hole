# CL 85: DNS-over-HTTPS upstream forwarding (ROADMAP #5)

## Description

s-hole forwarded every cache-miss query to its upstreams over plain DNS on port
53. That hop is cleartext, so an ISP that intercepts port 53 can log or rewrite
it, and any on-path observer can read it (DESIGN open question #1).

This CL adds DNS-over-HTTPS (DoH) as a third upstream transport. An `upstreams`
entry can now be a DoH endpoint with an IP host, for example
`https://1.1.1.1/dns-query`. s-hole POSTs the same wire-format query to it over
HTTPS (RFC 8484) and unpacks the wire-format reply, so the upstream hop is
encrypted and carried on port 443. DoH and plain entries share the one ordered
`upstreams` list; s-hole tells them apart by the `https://` prefix.

## Motivation

DoH is the answer to an ISP that intercepts or logs plain port-53 traffic, and
it is DESIGN open question #1 (resolved: yes). It needs no new dependency:
`miekg/dns` already packs a query to wire format and unpacks a reply, and
`net/http` (already used by the admin server and blocklist downloads) carries
it. The forwarder was already transport-agnostic below `exchange`, so DoH slots
in as one more branch there.

## What it does

- **`internal/dnsserver/upstream.go`**:
  - `exchange` gains a branch: an `https://` upstream is handled by the new
    `exchangeDoH`, otherwise the existing UDP-first / TCP-on-truncation path
    runs unchanged.
  - `exchangeDoH` packs the query, POSTs it (`Content-Type` and `Accept`
    `application/dns-message`) under the same 3s per-attempt context deadline the
    UDP/TCP path uses, checks for HTTP 200, reads the body through an
    `io.LimitReader` capped at `dns.MaxMsgSize`, and unpacks it. A transport
    error, a non-200 status, or an unparsable body returns an error, so
    `forwardWith` records a transport failure and fails over to the next
    upstream. There is no TC/TCP retry: an HTTP body is never DNS-truncated.
  - A reused package-level `dohClient` (`*http.Client`) beside `udpClient` and
    `tcpClient`, so its connection pool keeps a DoH upstream's TLS connection
    warm; only the first query after startup or a long idle gap pays the
    handshake. The per-attempt deadline rides on the request context, so no
    `Client.Timeout` is set. Default TLS verification stays on.
- **`internal/config/config.go`**:
  - `filterUpstreams` now routes a URL-shaped entry (one containing `://`)
    through the new `isValidDoHURL` instead of `net.SplitHostPort`. A valid DoH
    upstream is `https://` with an IP host (`url.Parse` plus `net.ParseIP` on the
    hostname); a hostname host, a non-https scheme, or a malformed URL is dropped.
    A plain entry still takes the `host:port` path unchanged.
  - The drop WARN and the empty-list fatal error now name both accepted shapes.

## Design decisions

- **IP-literal DoH URLs only, for this first cut.** The host must be an IP
  (`https://1.1.1.1/dns-query`), so there is no DoH hostname to resolve and no
  risk of the bootstrap lookup looping back into s-hole (often the LAN's own
  resolver). TLS still verifies, because Cloudflare, Google, and Quad9 ship
  certificates with IP SANs. A hostname DoH URL is rejected at config time.
  Hostname support with a bootstrap resolver is a recorded follow-up.
- **One mixed `upstreams` list**, not a separate `doh_upstreams` field. The
  failover loop, the cooldown tracker, and the per-upstream
  `shole_upstream_transport_failures_total{upstream}` metric all key off the
  upstream string, so a DoH URL flows through them unchanged and gets its own
  metric label for free. An operator lists a DoH endpoint first and a plain
  resolver after it to keep a fallback.
- **Reuse the 3s per-attempt / 10s per-query budget.** The TLS tax is RTT-scale
  (about one extra round-trip on a cold connection, and warm via keep-alive),
  well inside 3s; on a link too slow for that, failover to the plain fallback is
  the right response. A `doh_timeout` knob is a recorded follow-up, not built.
- **A non-200 or unparsable reply is a transport failure**, not a relayed
  answer, so it triggers failover exactly as a UDP failure does. A DoH 200 that
  carries a SERVFAIL/REFUSED DNS message is a normal relayed rcode, handled by
  the existing handler path.
- **Validation stays shape-only.** `isValidDoHURL` parses and inspects the URL
  but dials nothing and resolves nothing, preserving the CL 82 (#28) property
  that config validation cannot be turned into an SSRF or LAN-scan primitive via
  the unauthenticated admin API.
