# CL 107: Windows service access list

## Description

- **Standard Windows layout.** The README installs the binary in
  `C:\Program Files\s-hole` and the config and the data in
  `C:\ProgramData\s-hole`, and gives the steps to move an install from
  `C:\s-hole`.
- **The service writes only what it creates.** `-service install` gives the
  config folder a new protected access list (`serviceDirACL` in
  `internal/service/acl.go`): SYSTEM and the Administrators group get full
  control; the service account gets read and execute on everything, plus
  "add file" and "add subfolder" on the folder itself (not inherited);
  CREATOR OWNER gets full control of new files and subfolders. So the
  service can create, change, and delete its data files (the query
  database, the query log file, the blocklist cache), but it cannot change
  `config.yaml` or another file that an administrator puts in the folder.
  Before, the service account had "modify" on everything in the folder.
- **Install checks before it changes anything.** `-service install`
  refuses when:
  - the service account could change or replace the binary. The check reads
    the access lists of the binary, its folder, and every folder above it,
    and evaluates them for the service SID and the groups that
    `whoami /groups` showed for the service account on Windows 10
    (`checkBinary`, `grantedRights`, `binaryPaths`);
  - the binary is in the config folder, where the service can add files;
  - `config.yaml` does not exist or is not a regular file;
  - the config folder is a drive root, the Windows folder or a folder in
    it, `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%ProgramW6432%`,
    `%ProgramData%`, `%USERPROFILE%`, or the folder that holds the user
    profiles (`unsafeConfigDir`).
- **Install checks the owners after it sets the access list.** It refuses
  when the config folder, or anything in it, is owned by an account other
  than SYSTEM, the Administrators group, the service, or the account that
  runs the install, or when it holds a link or a junction (`checkOwners`,
  `foreignItems`).
- **The access list is set before the service exists, and a failure stops
  the install.** s-hole computes the service SID from the service name
  (`serviceSID`), so it no longer looks up the account after
  `CreateService`. Before, a failure to set the access list was a warning.
- **The Windows purge counts hard links.** `querylog.ZeroFile` refused a
  file with more than one hard link only on Unix; on Windows `linkCount`
  returned 1. It now reads the link count through the file handle
  (`GetFileInformationByHandle`).
- **The Windows dashboard purge empties the query log file (b/105).** On
  Windows, Go opens an append handle without the right to write data, so
  `Truncate` on the logger's handle failed with `Access is denied`, and the
  purge reported `empty failed`. When that `Truncate` fails, the purge now
  empties the file through a new handle (`truncateFile`), after it checks
  that the path still names the open file. The live test of this CL found
  the defect; `master` had it too.

Review finding: SEC-03. Bugs: b/104, b/105. Target release: v2.1.0.

## Motivation

The service account had "modify" on the config folder, and the README put
the binary in that folder. A program that took control of the s-hole process
could replace `s-hole.exe`. An administrator who later ran that binary
(`-purge`, `-check-config`, `-service uninstall`) ran the program as
Administrator. The service could also rewrite `config.yaml`, for example to
point `query_log.database` at a system file, which an offline `-purge` run
as Administrator then overwrote with zeros and deleted. On Linux the binary
belongs to root and the config is `640 root:s-hole`, so Linux did not have
this path.

## Design decisions

- **Decided with the maintainer:** the Windows standard layout,
  binary in Program Files and data in ProgramData. Only administrators can
  change files in `C:\Program Files`, so the binary needs no access list of
  its own.
- **CREATOR OWNER, not a separate data folder.** The relative paths of the
  sample config (`queries.db`, `blocking.cache_dir: "."`) resolve in the
  config folder. With CREATOR OWNER the service can write there, and an
  existing config keeps working. A data subfolder would need a config change
  on every install.
- **Refuse, do not warn.** A binary that the service can change is the
  escalation path itself. Like the other privacy and security checks, it
  has no setting to skip it.
- **The check fails closed.** An access list that s-hole cannot read
  refuses the install. The evaluation follows the Windows access check
  (ordered entries, deny before a later allow, inherit-only entries skipped,
  generic rights mapped, implicit owner rights unless OWNER RIGHTS is set).
  It ignores privileges and integrity labels, and it counts an allow entry
  with a condition as if the condition were true. The group list is the
  groups of a service token; an extra group only makes the check stricter.
- **Shared config folders are refused.** The access list replaces the list
  of the folder and of every file in it. A config path such as
  `C:\ProgramData\config.yaml` would have locked every other program out of
  ProgramData. Without `-config`, the path is `config.yaml` in the current
  folder, which in an elevated prompt is often `C:\Windows\System32`.
- **Owners are checked after the access list is set.** A new folder in
  ProgramData lets every user add files until the install. A file that
  another user put there (a blocklist cache file, for example) would stay
  under that user's control, because its owner can change its access list.
  The check runs after `restrictDir`, when no other account can add a file,
  so there is no gap between the check and the change. A refused install
  leaves the folder with its new access list, which is the more private
  state. Links and junctions are refused because they could point the
  service and the purge at files outside the folder.
- **A failed access list stops the install.** The service would otherwise
  run in a folder that inherits the ProgramData list, where every user can
  read the history.
- **Upgrade steps use only the new binary.** The old service account could
  have changed the old binary and the old config. The README tells the
  operator to read the old config before copying it, to purge the old
  folder with the new binary, and not to copy `queries.db` or the cached
  lists: copied files belong to the administrator, so the service cannot
  write them.
- **An installed service is not changed.** The fix applies at install. An
  existing install keeps its old access list until the operator moves it;
  the CHANGELOG says so.

- **b/105 in this CL (decided with the maintainer).** The live test found
  that the Windows dashboard purge failed to empty the query log file, and
  the acceptance of SEC-03 includes a working dashboard purge. The fix
  falls back to a second handle only when `Truncate` fails, so Linux keeps
  the old path.

## Privacy impact

- **Collects, keeps, sends:** nothing new.
- **Who can read the history on Windows:** unchanged (SYSTEM, the
  Administrators group, and the service account).
- **Purge:** an offline purge on Windows no longer overwrites a file that
  a hard link in the config folder points to; it reports the step as failed
  and keeps the file. The Windows dashboard purge now empties the query
  log file after it overwrites it with zeros (b/105); before, the zeroed
  file kept its size.

## Testing

A separate sub-agent wrote the tests from the requirements, without the
diff. It listed its cases first, then wrote:

- `internal/service/acl_test.go` (no build tag, 27 tests): the service SID
  (two values that Windows publishes, case, shape); the exact group list
  (9 SIDs, CONSOLE LOGON included); `foreignItems` (allowed owners, foreign
  owners at any depth, sorted, an empty owner fails closed);
  the SDDL (protected, parses, round trip); the config folder list, entry by
  entry and through a simulated inheritance (on the folder the service gets
  read and execute plus "add file" and "add subfolder"; on a file that an
  administrator creates, read and execute only; on a file that it creates,
  full control; other users nothing; the old "modify" list is caught); the
  access check (deny order, null DACL, inherit-only entries, generic rights,
  owner and OWNER RIGHTS); the right sets and `binaryPaths` (drive root,
  UNC share); realistic Windows access lists (`C:\Program Files\s-hole` is
  safe; a folder under `C:\`, a binary in `C:\`, and a binary in
  `C:\ProgramData\s-hole` are refused); `rightNames`; `unsafeConfigDir`
  (refused folders, allowed subfolders and look-alike names, each variable
  alone, an empty environment).
- `internal/service/svc_windows_test.go` (Windows only): `readACL` and
  `checkBinary` on temp files with access lists the test sets (a writable
  file, Everyone, a read-only file, a deny entry first, a null DACL, a
  missing path fails closed); a `restrictDir` round trip on a temp folder
  with files in it; `Install` refusals (missing config, config is a folder,
  binary in the config folder, config in the Windows folder) that change no
  access list; `checkOwners` (owners at any depth, the folder itself, another
  service's SID, a junction, a file symbolic link, a missing folder).
- `internal/querylog/zero_windows_test.go`: `ZeroFile` refuses both names
  of a hard-linked file and changes neither; with one name left, it
  overwrites the file.
- `internal/querylog/zero_test.go`: `truncateFile` empties the file while an
  append handle is open, refuses another file at the path and leaves it
  unchanged, and creates no missing file.
- `internal/querylog/logger_windows_test.go` (Windows only, b/105): `Purge`
  returns nil and leaves an empty file, the next line is the only content,
  and a second purge also empties the file. The existing
  `TestFileLogger_PurgeOverwriteKeepsLaterLines` covers the same case on
  every platform.
- `internal/querylog/logger_purge_test.go`: the existing rotation test
  (`TestFileLogger_PurgeDoesNotOverwriteAnotherFileAtThePath`, CL 105) now
  skips on Windows when the rename fails (decided with the maintainer).
  Windows refuses to rename a file that s-hole holds open (`being used by
  another process`), so a log rotation cannot move the open log there.

- `make check` passes. Coverage: `internal/service` 93.9 % (`acl.go` 100 %
  except one unreachable branch of `binaryPaths`), `internal/querylog`
  87.2 %.
- Mutation tests by the tester: 50 mutants of `acl.go` in the first round,
  48 caught (the two others cannot change behavior: an empty-string
  guard); 9 more for the second round (`foreignItems`, the token list,
  `truncateFile`, the purge truncate), all caught.
- The Windows-only tests, cross-compiled and run on a Windows 10 host (22H2)
  without elevation: all pass, `TestRestrictDir_RoundTrip`, the hard-link
  test, the junction test, and the b/105 tests included. The symbolic-link
  tests skip (the user has no right to make a symbolic link), and the
  owner tests skip (setting another owner needs an elevated prompt).
  In an elevated prompt, the `readACL`, `checkBinary`, `restrictDir`, and
  `checkOwners` tests (17) all pass with no skip, the owner and symbolic
  link tests included.
- `s-hole.exe -service install` on the same host without elevation, so the
  service manager refuses before any change: a binary in the config folder,
  a binary in a new folder under `C:\` (refused for write, append, and
  delete through Authenticated Users, on the file and the folder), a config
  in the user profile folder, and a missing config are refused with the
  expected error. A binary in the user profile with the config in a
  subfolder passes the checks and reaches the service manager.
- Live test in an elevated session (`-service install` in the standard
  layout, `icacls`, a write as the service account through a scheduled
  task, the service writing its files, a reinstall, the dashboard purge,
  the offline purge with a hard link, uninstall): 52 of 52 checks pass on
  Windows 10 22H2 (Hungarian locale, so the script compares SIDs, not names), in
  `C:\Program Files\s-hole` and `C:\ProgramData\s-hole`:
  - Install refuses a binary in a new folder under `C:\` (the old layout),
    a binary in the config folder, a missing config, a file in the config
    folder owned by LOCAL SERVICE, and a junction. No service is created; a
    refusal before `restrictDir` leaves the folder's access list unchanged.
  - `icacls` after install: the folder has SYSTEM `(OI)(CI)(F)`,
    Administrators `(OI)(CI)(F)`, `NT SERVICE\s-hole:(OI)(CI)(RX)`,
    `NT SERVICE\s-hole:(WD,AD)`, and CREATOR OWNER `(OI)(CI)(IO)(F)`;
    `config.yaml` has SYSTEM `(I)(F)`, Administrators `(I)(F)`, and
    `NT SERVICE\s-hole:(I)(RX)`; `s-hole.exe` and its folder have no entry
    for the service account.
  - A scheduled task that runs as `NT SERVICE\s-hole` cannot write or
    rename `s-hole.exe`, add a file next to it, or write, rename, or change
    the permissions of `config.yaml`. It can read `config.yaml` and create,
    write, and delete its own file in the config folder. `whoami /groups`
    in that task showed the groups that `serviceTokenSIDs` lists, CONSOLE
    LOGON (`S-1-2-1`) included, which the first run had missed.
  - The service creates and owns `queries.db`, `queries.log`, and the
    blocklist cache files, answers DNS, and records the queries. After an
    uninstall and a new install in the same folders, it still has full
    control of `queries.db` and records new queries.
  - The dashboard purge has no failed step and leaves `queries.log` empty
    (b/105). The first run failed here with `empty failed: truncate
    queries.log: Access is denied.`; a binary built from `master` gave the
    same result, and its file held only zeros.
  - The offline purge refuses a `queries.db-wal` hard-linked to another
    file and leaves that file unchanged; the service uninstalls; the script
    removes every folder.
