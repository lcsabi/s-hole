# CL 59: Make doStop the sole exit authority (b/043, b/044)

## Description

An ultrareview round (range `bc1a6a4..53c0ae2`) found that interactive shutdown
races its own ordered teardown, so the process can exit before the later steps
run. This CL closes that race, fixes the Windows coupling it exposes, and gives
the in-flight reload wait its own timeout budget (open question B).

- **b/043** (main): `doStop` runs `shutdown()` in the signal goroutine and then
  calls `os.Exit(0)`. Step 3 of `shutdown()` (`stopDNS`) unblocks
  `dnsServer.Start()` in the main goroutine, so `main()` returns and the Go
  runtime terminates the process. Nothing forces the remaining teardown steps
  (drain HTTP, wait for an in-flight reload, close the cache and loggers, close
  the DB) to finish first. The main goroutine's remaining work is trivial, so it
  usually wins the race and those steps are skipped.
- **b/044** (service, Windows): `handler.Execute` sends `StopPending`, calls
  `h.stop()`, and never sends `svc.Stopped`. It relies on `doStop` calling
  `os.Exit`. The b/043 fix removes that `os.Exit`, so the SCM would hang in
  `StopPending`. This CL keeps the two paths consistent.

## Motivation

The Linux binary takes the interactive path, not the Windows SCM branch. Every
`systemctl stop` and every restart sends SIGTERM into it. Two documented
shutdown guarantees are defeated in production:

- R34: the DBLogger final batch is never lost on a clean exit. If `closeDB` is
  skipped, buffered query rows are lost.
- R53: an in-flight blocklist refresh is waited on so it is not killed mid
  `os.Rename`. If `waitForReload` is skipped, a refresh can be cut off and leave
  a half-written cache `.tmp` file.

In-flight admin HTTP is also not drained. The bug is invisible to tooling.
`-race` detects memory races, not process-exit ordering, and
`TestShutdown_TeardownOrder` calls `shutdown()` directly, so it bypasses the
`main`-return exit route that causes the loss.

## What it does

**b/043.** Make `doStop` the sole exit authority for the interactive path.

- Extract the interactive wait into `blockUntilStopped(start, done)`, which runs
  `start` (the DNS server) in a goroutine and blocks until `done` is closed.
- `doStop` closes `done` only after `shutdown()` returns, and is wrapped in
  `sync.Once` so a second stop request cannot re-run teardown (the old
  `os.Exit(0)` made re-entry impossible; without it, guard explicitly).
- Remove the `os.Exit(0)` inside `doStop` and the `main`-return exit route, so
  the process exits only after the full ordered teardown completes.

A DNS listener failure at startup still surfaces as a non-zero exit. The serve
goroutine reports only a non-nil error (a clean `Shutdown` makes `Start()` return
nil, which is dropped so it cannot race `done`). So `blockUntilStopped` returns 1
on a startup bind failure and 0 on a clean stop.

**b/044.** After `h.stop()` returns in `Execute`, send an explicit
`svc.Status{State: svc.Stopped}` so the SCM sees the service reach `Stopped`
rather than hang in `StopPending`. The Windows shutdown path stays correct
whether or not `doStop` calls `os.Exit`.

**Open question B.** `shutdown()` gave `drainHTTP` and `waitForReload` one shared
5 s context, so a slow HTTP drain ate into the reload wait. Give each its own 5 s
context. `waitForReload` is the step that protects the R53 mid-`os.Rename`
guarantee that b/043 exists to restore, so it should get its full budget
regardless of how long the drain took. Build the reload context after
`drainHTTP` returns.

## Design decisions

- **One exit authority, not two.** The pre-CL code had two exit routes (the
  `main`-return after `Start()` unblocks, and `os.Exit(0)` in `doStop`) racing
  the same teardown. Collapsing to one route removes the race by construction
  rather than by adding a happens-before that a later edit could drop.
- **Keep the teardown order unchanged.** The order in `shutdown()` and its unit
  test are correct. The defect is that the order was not allowed to finish, not
  the order itself. This CL changes who waits for it, and splits the one shared
  timeout into two (below), but the step sequence is untouched.
- **Each teardown wait gets its own budget (open question B).** The single
  shared 5 s context let a slow HTTP drain starve the reload wait. Separate
  budgets make the R53 guarantee independent of drain latency. The only cost is
  that the worst-case shutdown grows from 5 s to 10 s. That is far inside
  systemd's default `TimeoutStopSec` (90 s) and the SCM's stop tolerance, and
  both waits normally finish near-instantly, so the cost is negligible.

## Files changed

- `cmd/s-hole/main.go`: extract `blockUntilStopped(start, done)`; run the DNS
  server in a goroutine and block on `done`; wrap `doStop` in `sync.Once` and
  close `done` after `shutdown()` returns; remove `os.Exit(0)` from `doStop`
  (b/043). Give `drainHTTP` and `waitForReload` their own timeout contexts in
  `shutdown()` (open question B). Update the package doc comment, which said
  interactive mode blocks "on the DNS server", to describe the `done` wait.
- `cmd/s-hole/main_test.go`: `TestBlockUntilStopped_WaitsForTeardown` (full
  teardown, ending in `closeDB`, runs before the exit is allowed),
  `TestBlockUntilStopped_StartupErrorExitsNonZero` (bind failure returns 1), and
  `TestShutdown_ReloadGetsOwnBudget` (a slow drain leaves the reload wait its full
  budget) (b/043, open question B).
- `internal/service/svc_windows.go`: send `svc.Stopped` after `h.stop()` returns,
  then return from `Execute` (b/044). Windows-only; verify on the R58 pass.
- `docs/BUGS.md`: b/043 and b/044 (Fixed in CL 59).
- `docs/CHANGELOG.md`: `Fixed` bullet for the shutdown data-loss race (b/043).
- `docs/CL.md`: index row.
- `docs/cls/CL-59.md`: this file.

## Testing

- `make check` (fmt + vet + lint + test) green.
- `CGO_ENABLED=1 go test -race ./cmd/s-hole/ ./internal/service/` green (WSL).
- `GOOS=windows go build ./...` compiles the `svc_windows.go` change.
- New tests: `TestBlockUntilStopped_WaitsForTeardown` asserts the last teardown
  step (`closeDB`) has run by the time the exit is allowed;
  `TestBlockUntilStopped_StartupErrorExitsNonZero` asserts a bind failure returns
  exit code 1; `TestShutdown_ReloadGetsOwnBudget` asserts the reload wait keeps
  close to its full timeout after a 120 ms drain (a shared context would leave it
  ~80 ms of a 200 ms budget). `TestShutdown_TeardownOrder` still pins the order.
- Windows verification is deferred to the R58 pass on an SCM host: a real SCM stop
  reaches `Stopped` and does not hang in `StopPending`.
