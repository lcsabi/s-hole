# CL 62: Minor robustness and cleanups from ultrareview (b/049-b/051)

## Description

The ultrareview P4 bucket held four heuristic or minor items, plus open question
A. This CL acts on the ones that fix real behavior or remove a latent footgun:

- **b/049** (blocklist): `Store.Sources()` returns `nil`, not the documented
  empty slice, so `/api/stats` emits `"sources": null` in the pre-first-refresh
  window.
- **b/050** (blocklist): `cacheFilename` is many-to-one, so two similar source
  URLs can map to one cache file and clobber each other.
- **b/051** (blocklist): `fetchList` truncates an over-cap source silently at the
  256 MiB `io.LimitReader` and renames it in as a fresh, non-stale cache (open
  question A).
- Cleanup, no bug number: rename the `min` local in `minAnswerTTL` so it stops
  shadowing the Go builtin.
- Cleanup, no bug number: reuse package-level `dns.Client` values in `exchange`
  instead of allocating a fresh pair per query.

One P4 item is deliberately not taken; see "Not done" below.

## Motivation

**b/049.** `Sources()` documents "an empty slice before the first Update", but
returns `nil`. Marshaled by `/api/stats` and read by `/metrics`, a `nil` slice
serializes as JSON `null`, not `[]`. A dashboard or scraper that expects an array
sees a type it did not document. Small, but it is doc-vs-code drift, which
CLAUDE.md treats as a bug.

**b/050.** `cacheFilename` collapses `://`, `/`, `.`, `?`, `&`, `=`, and `:` all
to `_`. Two source URLs that differ only in those characters map to the same
cache file. The per-URL stale-fallback guarantee (each source keeps its own
on-disk cache to serve when a fetch fails) then breaks silently: the two sources
share one file and overwrite each other's `os.Rename`. Low likelihood, since it
needs an unlucky operator config, but the failure is silent and defeats a
documented guarantee.

**b/051 (open question A).** `fetchList` streams the body through
`io.LimitReader(resp.Body, maxBodyBytes)` with `maxBodyBytes = 256 MiB`. If a
source exceeds the cap, the reader stops at the cap with no error, `parseHostsFormat`
parses the truncated bytes, and the result is renamed in as a fresh cache with
`stale: false`. The operator gets a partial blocklist presented as healthy, with
no signal. Theoretical at real blocklist sizes, but the failure is silent, so it
is worth a one-line warning and a note in operator docs.

**min shadow.** `minAnswerTTL` declares a local `min` (a `uint32`). Since Go 1.21
`min` is a predeclared builtin. A later edit that calls the builtin `min(...)`
inside this function would silently bind to the `uint32` local instead. It is not
a bug today; it is a latent footgun worth removing while the file is open.

**dns.Client per query.** `exchange` builds a fresh UDP `dns.Client` and, on a
truncated reply, a fresh TCP `dns.Client` on every cache-miss query. A
`dns.Client` is a reusable configuration object with no per-call mutable state,
and `miekg/dns` documents it as safe for concurrent use. Allocating one per call
is a mild anti-pattern, not a performance problem: the socket dial dominates. The
value of the change is precision. The same file already keeps `forwardTracker` as
a package-level singleton, so reused clients match the existing style.

## What it does

**b/049.** `Sources()` returns `[]SourceStatus{}` when no snapshot has loaded yet,
so `/api/stats` emits `[]`. The doc comment already promises an empty slice, so
the code now matches the doc.

**b/050.** `cacheFilename` hashes the URL: `blocklist_` + hex(sha256(url)) +
`.txt`. The mapping is injective in practice, so distinct URLs get distinct cache
files and the per-source stale fallback holds. The output keeps the `blocklist_`
prefix and contains only hex characters, so `FuzzCacheFilename` (prefix present,
no `/`, `\`, or `:`) stays green. Existing cache files under the old naming are
not migrated; they are simply re-downloaded once under the new name, which is the
same cost as a cache miss.

**b/051.** After `parseHostsFormat` drains the `io.LimitReader`, probe
`resp.Body` for one more byte (for example `io.ReadFull` into a one-byte buffer).
If the probe reads a byte, the source exceeded `maxBodyBytes` and the parsed
result is truncated. A source exactly at or under the cap leaves nothing to read,
so this does not false-positive. On truncation, remove the `.tmp` (do not rename
a partial body in as fresh) and handle it exactly like the existing non-200
branch: if a cache file exists, `WARN` ("response truncated at cap, using stale
cache") and serve the previous cache marked `stale: true`; otherwise return an
error naming the URL and the cap. This reuses the fallback pattern already used
for a failed `Get` and a non-200 response, so a truncated 200 is treated like the
other unusable-200 case. Document the 256 MiB cap and the truncation behavior in
the operator-facing blocklist docs.

**min shadow.** Rename the local in `minAnswerTTL` from `min` to `smallest`. No
behavior change.

**dns.Client per query.** Add two package-level `dns.Client` values in
`internal/dnsserver/upstream.go` (UDP and TCP, each with `Timeout:
perUpstreamTimeout`), and have `exchange` use them instead of constructing a pair
per call. Behavior is unchanged: each attempt still runs under its own
`context.WithTimeout(ctx, perUpstreamTimeout)`, and the TCP fallback on a
truncated reply is unchanged.

## Design decisions

- **Hash, do not escape, the cache filename.** An injective escape scheme is
  possible but fussy to keep correct across every URL character. A sha256 hex
  digest is short, deterministic, filesystem-safe on every target OS, and cannot
  collide in practice. The tradeoff is that the filename is no longer
  human-readable, which the fuzz target and the tests never depended on.
- **A truncated 200 is an unusable 200.** The existing code already refuses to
  cache a non-200 error-page body and falls back to the stale cache. A body
  truncated at the cap is unusable for the same reason, so it takes the same path:
  WARN, do not replace the cache, serve the previous good list marked stale. A
  real blocklist is far under 256 MiB, so hitting the cap signals a wrong URL or a
  broken source, which is worth surfacing rather than silently accepting.

## Not done

- **Admin-server bind failure degrades silently (P4 #10).** Handled in its own
  CL 63 (b/052), not bundled here: it needs an `api.Server` API change (split
  bind from serve) and rests on a fail-open decision, so it does not belong with
  these mechanical cleanups.

  (the old `len() != 0` check passed for `nil` too).
- b/050: `TestCacheFilename_DistinctURLsDistinctFiles` covers URLs differing only
  in the characters the old scheme collapsed; the colliding pair fails against the
  old scheme. `FuzzCacheFilename` (8 s smoke) and the existing cache-path tests
  stay green with the hash filename.
- b/051: `TestFetchList_TruncatedAtCapFallsBackToStale` (prior cache served stale,
  WARN, truncated body not written) and `TestFetchList_TruncatedAtCapNoCacheErrors`
  (no cache: error, nothing written). Both lower `maxBodyBytes` via the new
  package `var` and restore it with `t.Cleanup`.

  cooldown, failover, and second-sweep tests stay green with the reused
  `dns.Client` values (behavior unchanged), and `-race` confirms the shared
  clients are safe under concurrent queries.

  ./internal/cache/ ./internal/dnsserver/` green (WSL). Coverage: blocklist
