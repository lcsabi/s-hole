# CL 103: smaller Docker image, privacy-first README intro

## Description

- The Docker image sets the binary's file capability in the build stage. The
  image no longer stores the binary twice: 60.2 MB on disk before, 34.3 MB
  after (amd64). Compressed, the published 2.0.1 image is 18.1 MiB, and its
  `setcap` layer is 8.55 MiB of that, so the next image should be about
  10 MiB.
- The README intro now says what sets s-hole apart: it is privacy-first, it
  records nothing by default, and it sends its upstream queries encrypted
  over DNS-over-HTTPS.

## Motivation

The runtime stage copied the binary in one layer, then ran `setcap` on it in a
later layer. `setcap` writes an extended attribute, and a change to a file
that an earlier layer added makes the new layer hold a full copy of the file.
That layer also held the `libcap-utils` install and removal. It was 17 MB,
more than the 13.9 MB layer of the binary itself.

The README intro still described s-hole as "lightweight". Since CL 93 the
privacy design is the main difference from other DNS sinkholes, and the
repository description now says so too.

## What it does

- **Dockerfile:** the build stage installs `libcap-utils` (before the source
  is copied, so a source change does not fetch it again) and runs
  `setcap cap_net_bind_service=+ep` on the binary it built. BuildKit's
  `COPY --from=builder` keeps the extended attribute, so the runtime stage
  gets the capability with the binary. The runtime stage only creates the
  user. The build stage runs on the build host's platform, so the new step
  needs no emulation in a multi-arch build.
- **Docs:** the README intro and Docker feature bullet, and the Docker
  paragraph in DESIGN. The Dockerfile comment about `tzdata` no longer claims
  a 30 MB saving (`tzdata` is about 0.5 MB).

## Design decisions

- **Keep the file capability.** The image runs as UID 65532 and must bind
  port 53 also under `--network host`, where the host's
  `ip_unprivileged_port_start` (1024 by default) applies. A file capability
  needs nothing from the operator. The alternatives need a `docker run` flag
  (`--sysctl`) or run as root.
- **No change to the base image.** A distroless static base could also drop
  the rest of Alpine (about 9 MB on disk), but it removes the shell and the
  package manager that operators use to debug inside the container. That is
  a separate decision.

## Privacy impact

None. The image content and behavior are the same; only the layer layout
changes.

## Files changed

- `Dockerfile`: `setcap` moved to the build stage.
- `README.md`, `docs/DESIGN.md`, `docs/CHANGELOG.md`, `docs/CL.md`, this file.

## Testing

No Go code changed, so there are no unit tests for this CL. The image was
built and checked live:

- **Size (amd64, local Docker 29.7):** 60.2 MB on disk before, 34.3 MB after.
  The runtime-stage layer that created the user and set the capability went
  from 17 MB to 33 kB; it now only creates the user.
- **Capability kept:** `getcap /usr/local/bin/s-hole` gives
  `cap_net_bind_service=ep` in the new image, as in the old one.
- **Bind as non-root:** Docker sets `ip_unprivileged_port_start` to 0 in a
  container's network namespace, which would hide a missing capability. With
  `--sysctl net.ipv4.ip_unprivileged_port_start=1024`, the container runs as
  UID 65532 with `CapEff 0x400`, binds port 53 on UDP and TCP, and
  `s-hole -healthcheck` reports healthy. Negative control: with
  `--cap-drop NET_BIND_SERVICE` the exec fails with "operation not
  permitted". This shows that the binary carries the capability.
- **Host networking (Debian 13 VM, Docker 29.8):** `--network host` with the
  host's `ip_unprivileged_port_start` at 1024: UID 65532, `CapEff 0x400`,
  `doubleclick.net` answered `0.0.0.0`, health status `healthy`.
- **arm64 (Debian 13 VM, QEMU registered for the test with
  `tonistiigi/binfmt`, as in the release workflow):** the arm64 image builds,
  and under emulation it runs as UID 65532 on `aarch64` with `CapEff 0x400`
  and binds port 53. The arm64 build-stage binary (ELF machine `b7`) carries
  the capability.
- The QEMU registration, the test images, the build cache, and the source
  copy were removed from the VM afterwards.
