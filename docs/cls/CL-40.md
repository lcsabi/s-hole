# CL 40 — Add deploy/uninstall-linux.sh companion to the installer (roadmap #12)

## Description

`deploy/install-linux.sh` had no counterpart, so removing an installed s-hole
service was a manual, error-prone sequence: stop and disable the unit, delete
the unit file and `daemon-reload`, remove the binary, `/etc/s-hole`,
`/var/lib/s-hole`, and the `s-hole` system user and group. This CL adds
`deploy/uninstall-linux.sh`, which reverses the install in the correct order and
reports what it did.

## Motivation

A shipped installer with no uninstaller is an asymmetry an operator (and a
reviewer) notices — ROADMAP #12. Beyond tidiness, the manual removal is easy to
get wrong: forget `daemon-reload` and systemd keeps a ghost unit; forget
`/etc/s-hole` and the next install silently reuses a stale config (the installer
never overwrites an existing `config.yaml`). A single scripted, idempotent
removal closes that gap.

## What it does

Run as root: `sudo bash uninstall-linux.sh [--purge] [--restore-resolved] [-y]`.

Order of operations (each step guarded so a re-run or a partial install is a
no-op, not an error):

1. Stop and disable the service (`systemctl stop`/`disable`, safe on an
   absent/inactive unit).
2. Remove `/etc/systemd/system/s-hole.service`, then `daemon-reload` and
   `reset-failed`.
3. Remove the binary `/usr/local/bin/s-hole`.
4. Remove the config directory `/etc/s-hole`.
5. Data directory `/var/lib/s-hole`: **kept by default**, removed only with
   `--purge`.
6. Remove the `s-hole` system user, then the group if `userdel` left it behind.
7. `--restore-resolved` only: if the `DNSStubListener=no` drop-in
   (`/etc/systemd/resolved.conf.d/no-stub.conf`) is present, remove it and
   restart `systemd-resolved`.

It prints an "Uninstall summary" box listing everything removed and everything
kept, mirroring the installer's "Installed build" / "Router setup" boxes.

## Design decisions

- **Data preserved by default; `--purge` to destroy it.** The query log is a
  browsing history and the caches are cheap to rebuild — deleting them should be
  an explicit choice, not the default. Without `--purge` the summary points the
  operator at `/var/lib/s-hole` and the one-liner to remove it.
- **`--restore-resolved` is opt-in, not automatic.** Disabling the
  `systemd-resolved` stub is a system-wide change the operator may have made for
  reasons unrelated to s-hole, so the uninstaller never undoes it silently. When
  the drop-in is present but the flag is absent, the summary reports it and how
  to remove it. Only the exact `no-stub.conf` drop-in the README documents is
  touched.
- **Confirmation prompt with a `-y` bypass.** An uninstaller changes system
  state, so it prints the destructive set and asks before acting; `-y`/`--yes`
  (and a non-interactive stdin, which reads as "no") keep it scriptable and
  fail-closed.
- **Idempotent and style-matched.** Every removal is existence-guarded, and the
  script mirrors `install-linux.sh` (`set -euo pipefail`, root check, `==>`
  progress lines, bordered summary box) so the two read as a pair.

The uninstaller intentionally does **not** re-embed the systemd unit or any
install-time knowledge beyond the fixed paths, so it adds no new doc-sync
coupling with `s-hole.service`.

## Testing

No Go code changed. The script was validated with:

- `bash -n` (syntax) and `shellcheck` (clean, no warnings).
- Behavioural: `--help`, an unknown option (usage + non-zero exit), and a
  non-root invocation (root-required error).
- A sandbox harness that rewrites the absolute paths to a temp tree and stubs
  the system commands (`systemctl`, `userdel`, `groupdel`, `getent`, `id`) so
  nothing real is touched, exercising three scenarios:
  - **default** — unit/binary/config/user/group removed; `/var/lib/s-hole` and
    the resolved drop-in kept.
  - **`--purge --restore-resolved`** — data directory removed; drop-in removed
    and `systemd-resolved` restarted.
  - **not installed** — "Nothing to remove" summary, no errors (idempotent).
