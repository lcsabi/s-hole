# CL 39 — Move the Docker binary out of the /app volume (b/039)

## Description

The Docker runtime image placed the binary at `/app/s-hole` (`WORKDIR /app`,
`COPY --from=builder /build/s-hole .`, `ENTRYPOINT ["./s-hole"]`) while also
declaring `/app` a `VOLUME`. The README's recommended `docker run` bind-mounts a
host data directory over that path (`-v "$(pwd)/data:/app"`). A bind mount
replaces the target directory's contents, so the mount shadowed the binary and
container init failed:

```
exec: "./s-hole": stat ./s-hole: no such file or directory
```

Following the documented instructions exactly reproduced the failure — with a
data volume mounted (the recommended setup) the container could not start.

## Motivation

The single most common Docker deployment path was completely broken. Filed as
b/039 (P1): the service cannot start in its documented configuration.

The root cause is co-locating the executable with the data directory. A `VOLUME`
that operators bind-mount is meant to hold *persistent data* (config, blocklist
cache, query DB) — putting the binary there means the host mount hides it.

## Fix

- **Binary → `/usr/local/bin/s-hole`** (on `PATH`, outside `/app`), with
  `ENTRYPOINT ["s-hole"]`. It is now reachable regardless of what the operator
  mounts over `/app`.
- `/app` stays the `WORKDIR` and the persistence `VOLUME`; relative paths
  (blocklist cache, `queries.db`) still resolve into the mounted host directory.
- The baked-in `/app/config.yaml` is retained as the default used only when
  `/app` is *not* mounted; when a data volume is mounted the operator supplies
  their own config there (already the documented workflow — README step 1).

## Design decisions

**Keep `/app` as both WORKDIR and VOLUME; move only the binary.** This is the
smallest change that fixes the bug and leaves every documented `docker run`
command byte-for-byte unchanged (`-v "$(pwd)/data:/app"` still correct), so no
operator-facing instructions had to change. The alternative — renaming the data
directory to `/data` — would have churned the README, PowerShell variant, and
DESIGN with no functional gain.

**Baked config left in place.** Removing it would make an un-mounted `docker
run` (quick trial without a host directory) fail for lack of a config; keeping
it preserves that zero-setup path while the mounted path uses the host copy.

## Files changed

- `Dockerfile` — copy binary to `/usr/local/bin/s-hole`; `ENTRYPOINT
  ["s-hole"]`; comments explaining why the binary must stay out of the `/app`
  volume.
- `README.md` — grammar fix in the Docker section prose (unrelated typo tidied
  while in the file); the `docker run` commands were already correct and are
  unchanged.
- `docs/BUGS.md` — b/039 (Fixed in CL 39).
- `docs/DESIGN.md` — note that the binary lives on `PATH`, not in the `/app`
  volume.

- `docs/cls/CL-39.md` — this file.

## Testing

- `docker build -t s-hole .` succeeds; image size unchanged (~33 MB).
- The previously-failing command
  `docker run -d -v "$(pwd)/data:/app" s-hole` now starts the container: logs
  show blocklists loaded, DNS listeners (UDP+TCP) up, and the admin UI
  listening. The blocklist cache files are written into the host data directory,
  confirming persistence through the volume.
- No Go code changed; `make check` unaffected.
