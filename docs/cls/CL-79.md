# CL 79: Grafana dashboard + Prometheus scrape/alert examples

## Description

Ship three monitoring assets under `deploy/` so the existing `/metrics` surface
becomes a working Prometheus + Grafana setup with no code and no new dependency:
`prometheus.yml` (scrape config), `prometheus-alerts.yml` (alert rules), and
`grafana-dashboard.json` (an importable dashboard). Add a README "Monitoring"
subsection under Deployment. Implements ROADMAP #26.

## Motivation

s-hole exposes `shole_*` metrics in Prometheus text format, but shipped no
ready-made way to use them. An operator who already runs a Prometheus + Grafana
homelab had to build the scrape config, the dashboard, and the alert rules from
scratch. This ships those assets. It does not replace the built-in dashboard
(#20/#29/#31), which stays the zero-dependency default; Prometheus and Grafana
are an optional layer for operators who already run that stack.

#26 is the last item in the observability group. #29 (CL 76), #30 (CL 78), and
#31 (CL 77) all landed first, so the metric surface the dashboard and alerts draw
is complete and stable, and none of the panels or rules reference a metric that
does not exist yet.

## What it does

- **`deploy/prometheus.yml`**: a scrape config with one `s-hole` job targeting the
  default `api_listen` (`127.0.0.1:8080`), a `rule_files` entry pointing at the
  alerts file, and comments on the localhost-bind and the `0.0.0.0` requirement
  for a remote Prometheus.
- **`deploy/prometheus-alerts.yml`**: one `groups` block with seven example rules,
  thresholds documented inline as tunable: `SHoleDown` (`up == 0`), `BlocklistEmpty`
  (`shole_blocklist_size == 0`), `BlocklistSourceStale`
  (`shole_blocklist_source_stale == 1`, per source), `HighQueryLogDropRate`,
  `HighForwardFailureRate`, `UpstreamTransportFailing` (per upstream), and
  `GoroutineLeak` (the #30 leak canary, sustained growth over an hour).
- **`deploy/grafana-dashboard.json`**: an importable dashboard (schemaVersion 39,
  Grafana >= 10). A dashboard-level `datasource` template variable of type
  `datasource` (query `prometheus`) feeds every panel, so import prompts for the
  Prometheus source and the same file also works under provisioning. Panels: stat
  cards (blocklist/whitelist/cache size, query rate), block-ratio and cache-hit
  gauges, goroutines, a query-rate timeseries, a failures timeseries (with the
  per-upstream transport line), a back-pressure timeseries, a heap-memory
  timeseries, a per-source table, and a source-staleness state timeline.
- **README**: a `### Monitoring (Prometheus + Grafana)` subsection under
  Deployment names the three files, the bind note, and the "does not replace the
  built-in dashboard" framing. The repository-layout tree line for `deploy/` now
  mentions the Prometheus/Grafana examples.

## Design decisions

- **Portable assets only, no runnable stack.** No docker-compose or provisioning
  bundle in the repo: it would add non-repo-relevant infrastructure and duplicate
  the existing Docker deploy story. The three files import into an operator's own
  Prometheus and Grafana. A hands-on practice walkthrough lives outside the repo.
- **Panels and rules reference only metrics that exist today.** This honors the
  ROADMAP's "do not reference absent series" rule. Every `shole_*` name in the dashboard and
  the alerts was cross-checked against `internal/api/metrics.go`. The #19 pause
  gauge (`shole_blocking_disabled`) is not shipped, so no panel or rule uses it.
- **A datasource template variable, not `__inputs`.** The variable approach is the
  least brittle import path and also works under provisioning, so the one file
  serves both without an export/import dance.
- **Grafana schema pinned to 39 (Grafana >= 10).** The import format changes across
  major versions; 39 imports cleanly on current Grafana and uses only long-stable
  panel types (`timeseries`, `stat`, `gauge`, `table`, `state-timeline`).

## Testing

- `deploy/grafana-dashboard.json` parses as JSON (`python3 -m json.tool`); both
  YAML files parse (`yaml.safe_load`).
- Metric cross-check: every `shole_*` name used in the dashboard and the alerts
  is emitted by `internal/api/metrics.go`. No absent series.
- `promtool` was not available in the dev environment, so `promtool check rules`
  and `promtool check config` were not run; the YAML syntax was validated instead.
  A reviewer with Prometheus installed can run promtool before merge.
- `make check` stays green (no Go changed). No coverage impact.
- Manual (optional, not a merge gate): run s-hole with
  `S_HOLE_API_LISTEN=0.0.0.0:8080`, point a local Prometheus at
  `deploy/prometheus.yml`, import the dashboard into Grafana, and confirm the
  panels populate.
