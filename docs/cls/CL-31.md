# CL 31 — Skip and WARN on invalid config whitelist entries

## Description

`config.Load` now filters the `whitelist` slice through
`blocklist.ValidDomain` after decoding: entries that are not valid domain
names are dropped and each one is logged at `WARN`, rather than being passed
into the store. Valid entries are kept in order. The block-set and enum
validation paths are unchanged.

## Motivation

CL 30 made whitelist matching a suffix walk: a whitelisted domain now
exempts its whole subtree. That amplified a previously inert
misconfiguration. Under the old exact-match code, a config `whitelist:
["com"]` (a typo, a stray label, a bare TLD) only exempted a literal `com`
query — effectively never. With suffix matching, the same entry is reached
at the final label of every `.com` query and silently disables blocking for
the entire TLD.

The two whitelist entry paths had also drifted: the REST handler validated
with `ValidDomain` (`internal/api/api.go`), but the config path
(`store.SetWhitelist(cfg.Whitelist)` in `cmd/s-hole/main.go`) fed the raw
YAML slice straight into the store, and `config.Validate` checked only the
two enum fields.

## Design decisions

**Skip and WARN, not fatal.** The whitelist is a list of domains, so it
follows the blocklist loader — which already skips tokens that fail
`ValidDomain` (`internal/blocklist/loader.go`) — rather than the enum fields,
which are fatal (b/017). Two reasons make leniency the right call here that
do not apply to the enums:

- **A dropped entry fails safe.** An omitted whitelist entry just means that
  domain is not exempted, so it stays blockable. There is no security
  downside to dropping it, unlike a bad `block_mode` where a silent fallback
  could pick the wrong sinkhole behaviour — which is exactly why the enums
  stay fatal.
- **Blast radius.** s-hole is a DNS sinkhole; a fatal config error means the
  LAN loses DNS. Coupling a single whitelist typo to a total resolution
  outage is disproportionate to a mistake whose worst case is "one site you
  wanted allowed stays blocked" — a visible, self-correcting symptom.

The `WARN` keeps the anti-silent-fallback spirit of the config package: the
entry is dropped loudly, not swallowed. This is strictly louder than the
blocklist loader's silent skip.

**Filter in `Load`, not `Validate`.** `Validate`'s contract is "invalid value
→ fatal error"; folding a skip-and-continue step into it would blur that.
`Load` is where the raw YAML becomes the in-memory config, so the filter (and
its `WARN`) lives there via the `filterWhitelist` helper, keeping `Validate`
fatal-only. `config` gains a package `slog` logger, mirroring `blocklist`.

**Divergence from the REST path is intentional.** `POST /api/whitelist`
still rejects an invalid entry with `400`. That path is interactive — a human
gets the error immediately and retries — whereas config is batch startup,
where skip-and-continue avoids an outage. Different context, different right
answer; both use the same `ValidDomain` rule.

**No import cycle.** `config` importing `blocklist` is safe: `blocklist`
imports no internal package, and `config` imported none before this.
