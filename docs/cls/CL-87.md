# CL 87: installer frees the resolved stub on current systemd; banner skips virtual interfaces

## Description

Two bugs found on the maintainer's Debian 12 VM while setting up a DoT client
test for CL 86.

- **b/058 (P1).** `install-linux.sh --free-port-53` did not free port 53 on a
  host running `systemd-resolved`, so s-hole failed to start with `listen tcp
  :53: bind: address already in use`. The preflight matched the literal text
  `127.0.0.53:53`, but current systemd shows the stub as `127.0.0.53%lo:53` and
  also runs a second stub on `127.0.0.54:53`.
- **b/059 (P3).** The "Router setup" banner, in the binary and in the
  installer, offered the Docker bridge address (`172.17.0.1`) as a DNS server
  to enter in the router. A router cannot reach it.

## Motivation

The preflight exists so that the most common Linux install failure (the
resolved stub holding port 53) is either fixed (`--free-port-53`) or explained
(a warning). With the check blind to the current `ss` format, both paths failed
silently, and the install ended in a failed health check. The banner exists to
tell the operator what to type into the router; a bridge address there is wrong
advice.

## What it does

- **`deploy/install-linux.sh`**
  - A `resolved_stub_on_53` function matches `127.0.0.53` and `127.0.0.54` on
    port 53, with or without the `%interface` suffix, in `ss -H -lunt` output.
    It captures the output before `grep` reads it: under `pipefail`, an
    early-exiting `grep -q` can make `ss` die of SIGPIPE and read as no match.
  - After it writes the `DNSStubListener=no` drop-in and restarts
    `systemd-resolved`, the installer checks again and warns if a stub still
    holds the port.
  - When `/etc/resolv.conf` resolves to `/run/systemd/resolve/stub-resolv.conf`,
    it prints the `ln -sf /run/systemd/resolve/resolv.conf /etc/resolv.conf`
    command, because programs that read that file (including s-hole's blocklist
    download) have no DNS once the stub is off. It does not change the file.
  - The warning without the flag names both stub addresses.
  - The closing banner reads `ip -4 -o addr show up scope global` through a
    `lan_ipv4s` function that drops container, VM, and VPN interfaces by name,
    and falls back to `hostname -I` if `ip` is missing or finds nothing.
    `|| true` keeps `set -e` and `pipefail` from ending the script there, since
    the service is already running at that point (the doc sweep caught that the
    first version aborted when `ip` was absent).
- **`cmd/s-hole/main.go`**
  - `printNetworkHint` gets its addresses from `lanIPv4s(systemInterfaces())`.
    `systemInterfaces` reads `net.Interfaces`; `lanIPv4s` keeps IPv4 addresses
    on interfaces that are up, not loopback, not link-local, and not virtual by
    name (`virtualIfacePrefixes`: `docker`, `br-`, `veth`, `virbr`, `vboxnet`,
    `vmnet`, `lxcbr`, `lxdbr`, `incusbr`, `podman`, `cni`, `flannel`, `cali`,
    `vxlan`, `tailscale`, `wg`, `zt`, `tun`, `tap`), matched case-insensitively
    in both copies.

## Design decisions

- **Match by interface name, not address range.** A Docker bridge address is an
  ordinary private address, so a range check cannot separate it from a LAN
  address. The name can. `br-` keeps its hyphen so it matches Docker's
  `br-<id>` networks and not a real LAN bridge such as `br0`; Proxmox's `vmbr0`
  is also kept.
- **Display only.** The filter changes what the banners print. s-hole listens
  on the same addresses as before, so a user with an unusual interface name
  loses at most a banner line, never a working listener.
- **Windows virtual switches stay listed.** Hyper-V names its internal and
  external switches both `vEthernet (...)`, so the name cannot tell a reachable
  one from an internal one.
- **Two copies of the name list.** The Go banner and the installer banner each
  keep the list; a comment in each names the other. A shared file would add a
  build or install step for a list of nineteen prefixes.
- **The installer does not repoint `/etc/resolv.conf`.** It prints the command
  instead. Changing the file is a system-wide change that the uninstaller's
  `--restore-resolved` would then also have to undo, and some operators manage
  `resolv.conf` themselves.
- **Re-check after the restart.** If the drop-in does not take effect (for
  example, a later drop-in overrides it), the operator now gets a warning
  before the health check fails.

## Testing

- `make check` clean; `-race` clean on `cmd/s-hole`.
- **b/058, the real failure.** The old and new checks were run against `ss`
  output copied from the reporting VM, with `ss` stubbed:

  | `ss` output | Old check | New check |
  |---|---|---|
  | Reporting VM before the fix (`127.0.0.53%lo:53`, `127.0.0.54:53`) | no match | match |
  | Same VM after the stub is freed | no match | no match |
  | Older systemd (`127.0.0.53:53`) | match | match |
  | s-hole itself on `0.0.0.0:53` | no match | no match |
  | This host, live (systemd 255) | no match | match |

  The installer itself was not run end to end here, because `--free-port-53`
  would disable the resolver on the development machine. The maintainer's VM
  is the end-to-end check.
- **b/059.** The unit tests reproduce the reporting VM (`enp0s3` plus
  `docker0`). On this host the old banner listed `172.18.69.208` and
  `172.17.0.1` (docker0, no carrier), and both new banners list only
  `172.18.69.208`. On `ip` output shaped like the reporting VM, the installer's
  `lan_ipv4s` kept `enp0s3` and `br0` and dropped `docker0`, a Docker network
  bridge, and `wg0`.
- `shellcheck` clean.
