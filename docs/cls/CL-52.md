# CL 52: add benchmarks for the stats, cache-write, and parse paths

## Description

Add three benchmarks that close gaps in the existing set:
`BenchmarkCounter_RecordQuery` (with a prune-exercising variant), `BenchmarkCache_Set`,
and `BenchmarkParseHostsFormat`.

## Motivation

The four existing benchmarks cover the block decision, the cache read, and reply
construction. A profiling review found three paths that run on the request cycle
or the refresh cycle but were never isolated:

- `Counter.RecordQuery` runs on every query (a lock plus two top-N map updates),
  and the top-N prune (`pruneBottomHalf`) had no coverage at all:
  `BenchmarkHandler_ServeDNS` reuses one domain, so its top-N map never grows past
  one entry and the prune never fires. The prune reassigns the map pointer (R31),
  so it is worth a guard.
- `Cache.Set` is the write path on every cache miss, the counterpart to the
  already-benchmarked `Cache.Get`.
- `parseHostsFormat` runs on startup and every refresh over an 80k-100k-line list.
  Correctness is fuzz-tested; an accidental O(n^2) in parse or validation was not
  guarded.

## What it does

- `BenchmarkCounter_RecordQuery` has two sub-benchmarks: `SteadyState` (a small
  fixed key set, no prune) and `ManyDomains` (twice `topNMaxEntries` distinct
  domains, so the prune fires repeatedly). A prune regression shows up as
  `ManyDomains` diverging from `SteadyState`.
- `BenchmarkCache_Set` stores distinct keys into a cache sized to hold them, so it
  measures the validate-plus-key-build-plus-store path rather than the
  drop-on-full early return.
- `BenchmarkParseHostsFormat` parses a 100 000-line synthetic hosts-format list.

All three call `ReportAllocs` and run under `make bench` (each once, at
`-benchtime=1x`).

## Baseline (informational, i7-8700K, n=6)

| Benchmark | ns/op | allocs/op |
|---|--:|--:|
| `Counter_RecordQuery/SteadyState` | 27.5 | 0 |
| `Counter_RecordQuery/ManyDomains` | 27.7 | 0 |
| `Cache_Set` | 497 | 7 |
| `ParseHostsFormat` (100k lines) | 17.8 M | 200k |

The two `RecordQuery` variants sit together today, which records that the prune is
cheap in amortized terms. The benchmark exists to catch a future change that makes
it not.
