# CL 66: Harden the Linux install/uninstall scripts and add -check-config (ROADMAP #27)

## Description

The Linux deploy scripts took sound steps but trusted their inputs and their own
outcome too much, so a bad deploy could end at exit 0 with the "Router setup"
banner over a dead service. This CL closes the six gaps ROADMAP #27 names, in one
CL, and adds a `-check-config` flag to the binary. No runtime behavior changes:
the hardening is around the service, not in it.

## Motivation

This is the exact path ROADMAP #1 (the real-hardware Raspberry Pi deploy) depends
on, and each gap had bitten a real deploy or could bite one silently:

- The installer ran `systemctl restart` and printed `status`, but never read the
  result, so a crash-loop (bad config, port 53 taken, wrong-arch binary) still
  reached the "Installed build" and "Router setup" boxes at exit 0. That defeats
  the b/030 intent that a bad deploy must not look installed.
- The most common Linux DNS-server install failure is the `systemd-resolved`
  stub holding `:53`. The uninstaller offered `--restore-resolved`, but the
  installer neither detected the conflict nor created the drop-in, so the
  uninstaller reversed a step the installer never performed.
- The installer took `BINARY` then `CONFIG_SRC` as positional args, both with
  defaults, and validated neither. Swapping them made `install` copy the YAML
  over `/usr/local/bin/s-hole` and the ELF over `config.yaml`.
- The uninstaller had `-h`/`--help` and a usage block; the installer had neither.
- There was no way to validate a config without starting the service.
- The scripts are hand-maintained bash with non-trivial quoting, and nothing
  guarded a regression.

## What it does

**`-check-config` (binary).** A new flag loads and validates the config exactly
the way startup does, then exits: `0` and a `config OK` line when valid, non-zero
with the failing field otherwise. To keep the flag and the running service from
drifting, the startup sequence (`Load` -> `Validate` -> the three `Parsed*`
duration checks) is extracted into one `config.LoadAndValidate`, which both the
flag and `main` call. `main`'s five separate config-error blocks collapse into
one call; each field error already names itself, so the single log line loses no
detail.

**Installer hardening (`deploy/install-linux.sh`).**

- Usage block and `-h`/`--help`, mirroring the uninstaller. Flags parse first,
  then the two positional paths keep their short form.
- Argument validation before `install` copies anything: the config must be a
  readable non-ELF file and the binary a native ELF for this host. A cheap
  `file` structural check runs first, then a `-version` exec proves the file runs
  here and is s-hole. A swapped invocation fails loudly with the correct order.
- A `-check-config` dry-run against the installed config before the start, so a
  bad config surfaces on screen instead of as a failed start.
- Port-53 preflight: a listener on `127.0.0.53:53` is the `systemd-resolved`
  stub. By default the installer warns and prints the exact drop-in to create;
  `--free-port-53` writes `/etc/systemd/resolved.conf.d/no-stub.conf` and
  restarts `systemd-resolved`, mirroring the uninstaller's `--restore-resolved`.
- Post-install health check: it polls `systemctl is-active` for a bounded window
  (a `Type=simple` unit reports `active` as soon as the process is up and
  `failed` on a crash), and on failure prints `journalctl -u s-hole -n 20` and
  exits non-zero. The success boxes print only on the success path.

**shellcheck.** A `lint-sh` CI job (its own job, like `vuln`) and a `make lint-sh`
target, folded into `make check`. The scripts pass at shellcheck's default level.

## Design decisions

- **One shared load-and-validate, not a second copy.** `config.LoadAndValidate`
  is the single startup sequence, so a config the installer's dry-run accepts is
  one the service will start on. Full startup parity was the chosen depth: it
  parses the three duration fields as well, so a bad duration string cannot pass
  `-check-config` yet crash the service on start.
- **Structural check before exec.** The `file` ELF/arch check gates the
  `-version` exec of an unvetted file as root; the exec is the real proof, the
  structural check just stops an obviously-wrong file from running and gives a
  clearer swap message. On a host without `file`, the `-version` exec is the
  backstop (a swapped text-file "binary" fails to run).
- **Warn about the port-53 conflict, do not fix it by default.** Creating the
  drop-in and restarting `systemd-resolved` briefly drops the operator's own DNS,
  so it stays behind the explicit `--free-port-53` flag. That closes the
  installer/uninstaller asymmetry without changing resolver state by default.
- **Generous, `active`-means-pass health check.** `is-active` can read
  `activating` during a slow first refresh, so the timeout is generous; a
  slow-start false negative must not fail a good install.
- **The systemd unit is untouched.** The heredoc in `install-linux.sh` stays
  byte-identical to `deploy/s-hole.service` (doc-drift rule); the hardening is
  around the unit, not in it.
- **Non-transactional, unchanged.** The installer does not roll back a partial
  install. At this scale a re-run after fixing the cause is the recovery path,
  and each step is guarded or overwrite-safe. The health check is not a promise
  of rollback.

## Files changed

- `internal/config/config.go`: add `LoadAndValidate` (and a small
  `parsedDurations` helper), reusing the existing `Load`, `Validate`, and
  `Parsed*` methods.
- `internal/config/config_test.go`: happy-path and per-stage failure tests for
  `LoadAndValidate`, plus a missing-file case.
- `cmd/s-hole/main.go`: add the `-check-config` flag and dispatch; rewire startup
  to `config.LoadAndValidate`.
- `deploy/install-linux.sh`: usage/`-h`, argument validation, `-check-config`
  dry-run, port-53 preflight + `--free-port-53`, post-install health check.
- `.github/workflows/ci.yml`: new `lint-sh` (shellcheck) job.
- `Makefile`: `lint-sh` target, `.PHONY` entry, folded into `check`.
- `README.md`, `CONTRIBUTING.md`: document `-check-config`, `--free-port-53`,
  `make lint-sh`, and the installer's new behavior.
- `docs/ROADMAP.md`: flip #27 to done (CL 66) and add the "Shipped" paragraph.
- `docs/CHANGELOG.md`, `docs/CL.md`, `docs/cls/CL-66.md`: changelog, index, this
  file.

## Testing

- `make check` green (gofmt + vet + golangci-lint 0 issues + shellcheck clean +
  tests).
- New config tests: `TestLoadAndValidate_HappyPathReturnsDurations` (returns the
  parsed default 24h/5m/30s), `TestLoadAndValidate_RejectsEachStage` (bad YAML,
  bad `block_mode`, bad `refresh_interval`, non-positive `db_flush_interval`,
  each returning all-zero values on error), and `TestLoadAndValidate_MissingFile`.
- `-check-config` exercised manually: exits 0 with `config OK` on the sample
  config, and non-zero with the field-named error on a bad `block_mode`, a bad
  `refresh_interval`, and a missing file.
- `deploy/install-linux.sh` unit heredoc confirmed byte-identical to
  `deploy/s-hole.service`; `bash -n` and `shellcheck` clean on both scripts;
  `-h` and the unknown-flag path verified.
- The root/systemd paths (swapped-arg rejection under install, port-53 preflight,
  health check) are exercised by the VM installer rehearsal under ROADMAP #1, not
  by unit tests (`cmd/s-hole` and the scripts sit below the gated floors).
