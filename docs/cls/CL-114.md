# CL 114: Update golang.org/x/net to v0.60.0

## Description

Update the indirect dependency `golang.org/x/net` from v0.57.0 to v0.60.0
(`go.mod` and `go.sum` only). No other module changes, and no s-hole code
changes.

## Motivation

On 2026-10-08 (22:31 UTC) the Go vulnerability database published five
HTTP/2 advisories: GO-2026-6603 (CVE-2026-78659), GO-2026-6610
(CVE-2026-78660), GO-2026-6611 (CVE-2026-78669), GO-2026-6612
(CVE-2026-78663), and GO-2026-6617 (CVE-2026-97032). Each one lists the Go
standard library (fixed in go1.26.9) and `golang.org/x/net` (fixed in
v0.60.0).

The v2.1.0 release was built with go1.26.9 (the pin from CL 108), but its
Linux binaries carry `golang.org/x/net` v0.57.0. `govulncheck -mode=binary`
reports the five advisories for each of the three Linux binaries (exit
status 3). The container image holds the same binary, so an image scanner
reports them too. The Windows binary does not link the module and is clean.
The weekly scan (`.github/workflows/vulncheck.yml`, CL 108) scans the
binaries of the latest release in binary mode and fails on a finding. Its
next run would fail until a release carries v0.60.0.

s-hole is not affected:

- From `golang.org/x/net`, the Linux binary links only `ipv4` and `ipv6`
  and the packages they import (`bpf`, `internal/iana`, `internal/socket`),
  through `github.com/miekg/dns` (`udp.go`, built for every OS except
  Windows and macOS). It does not link the module's `http2` package.
- The HTTP/2 code in the binary is the standard library's bundled copy
  (`net/http/h2_bundle.go`, with `vendor/golang.org/x/net/http2/hpack`),
  which go1.26.9 fixes.
- Before this change, the source-mode scan with go1.26.9 (the CI
  `govulncheck` job) reported "affected by 0 vulnerabilities". It listed the
  five advisories in a required module that the code does not call.

Binary mode cannot see which packages of a module are reachable, so it
reports the module version. The update removes the finding instead of a
scan exception.

## What it does

- `go get golang.org/x/net@v0.60.0`, then `go mod tidy`. The module stays
  `// indirect`. `go.sum` changes the two lines for the module.

## Design decisions

- **Update, not an exception.** The weekly scan has no allowlist, and an
  exception would hide a later advisory for the same module. The update is
  small and needs no code change.
- **No change to the dependency list in the docs.** README and CLAUDE.md
  list the direct dependencies only, and DESIGN names no indirect module;
  `golang.org/x/net` is indirect.
- **A patch release follows.** The fix reaches the weekly scan and the
  image only when a release carries it (v2.1.1).

## Files changed

- `go.mod`, `go.sum`: `golang.org/x/net` v0.57.0 to v0.60.0.
- `docs/CHANGELOG.md`: a Security bullet under `[Unreleased]`.
- `docs/CL.md`: index row for CL 114.
- `docs/cls/CL-114.md`: this file.

## Testing

- `make check` passes.
- Built the four release targets with go1.26.9 and the release flags
  (`-trimpath -ldflags="-s -w"`, `CGO_ENABLED=0`): linux/amd64, linux/arm64,
  linux/arm (GOARM 7), and windows/amd64. `go version -m` shows
  `golang.org/x/net v0.60.0` in the Linux binaries.
  `govulncheck@v1.8.0 -mode=binary` exits 0 for all four. On the v2.1.0
  release binaries of linux/amd64, linux/arm64, and linux/armv7 it exits 3
  with the five advisories.
- `govulncheck@v1.8.0 ./...` with go1.26.9: "No vulnerabilities found".
- No test was added: the change moves a dependency version and no behavior.
  The existing suite covers the `miekg/dns` paths that use `ipv4` and `ipv6`.

## Privacy impact

None. The change updates a dependency version. It collects, stores, and
sends no data.
