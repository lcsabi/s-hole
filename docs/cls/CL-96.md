# CL 96: Graduate the CHANGELOG to v2.0.0

## Description

Graduate the CHANGELOG's `[Unreleased]` section to `[2.0.0] - 2026-10-07` and add
a fresh empty `[Unreleased]` above it. A `v2.0.0` tag push needs this step:
`.github/workflows/release.yml` draws the GitHub Release notes from the matching
`[2.0.0]` CHANGELOG section, so that section must exist at the tagged commit. No
workflow or Go code changes.

## Motivation

`v1.0.0` shipped on 2026-09-18. Since then the `[Unreleased]` section has
collected the operator-visible work from CL 85-95. CL 93 changes the config
format (2.0) and makes every default the most private value, so this release is
a major version. The maintainer decided to release 2.0.0 only after CL 94
(minimal upstream query, local-only names) closed the remaining gap where client
EDNS options and LAN names reached the upstream. CL 94 merged on 2026-10-07
(PR #89), and CL 95 (wildcard blocklists) merged before it.

## What it does

- Rename `## [Unreleased]` to `## [2.0.0] - 2026-10-07`, then insert a fresh empty
  `## [Unreleased]` above it.
- Rewrite the section's intro line. It said "The next release is **2.0.0**",
  which is wrong in the published release notes. It now says that this release
  changes the config format and every default, and points to the upgrade notes.

The graduated section keeps the bullets already written under `[Unreleased]`:
the "Upgrade to 2.0 (read first)" notes, then Added, Changed, Fixed, and
Security. CL 84 (a dashboard refactor) and CL 92 (a test helper fix) have no
operator-visible behavior, so they have no release-notes bullet.

## Design decisions

- **Graduation is its own CL, merged before the tag.** CONTRIBUTING's "Cutting a
  release" requires that the tag points at a commit whose CHANGELOG already has
  the release section. Otherwise the `awk` notes extractor falls back to a
  placeholder.
- **The section keeps a short prose intro.** CL 83 kept the `[1.0.0]` section
  bullet-only. This release breaks every 1.x config, so the first line of the
  GitHub Release tells the operator to read the upgrade notes. The extractor
  copies everything between the two headings, so the intro does not change how
  it works.
- **No CHANGELOG bullet of its own.** The graduation changes no runtime
  behavior. The README examples already show `2.0.0` (CL 93), so this CL does
  not change them.

## Files changed

- `docs/CHANGELOG.md`: graduate `[Unreleased]` to `[2.0.0] - 2026-10-07`, add a
  fresh empty `[Unreleased]`, and rewrite the intro line.
- `docs/CL.md`: index row for CL 96.
- `docs/cls/CL-96.md`: this file.

No Go code changed. `internal/version` already reads the ldflags, so a build
tagged `v2.0.0` reports the tag with no source change.

## Testing

- `make check` (fmt + vet + lint + test) stays green; no Go code changed.
- Ran the release-notes `awk` extractor from `release.yml` against the graduated
  `docs/CHANGELOG.md` with `version=2.0.0`. It returns the `[2.0.0]` body (434
  lines, about 28 KB, under the GitHub Release body limit) from the intro line to
  the last Security bullet, and nothing from `[1.0.0]`.
- End-to-end validation follows CONTRIBUTING "Cutting a release" after this CL
  merges: push `v2.0.0-rc1`, verify the archives, `SHA256SUMS`, `-version`, the
  `ghcr.io/lcsabi/s-hole:2.0.0-rc1` image, and the rendered notes, then delete the
  rc and cut `v2.0.0`.

## Privacy impact

None. The change edits release notes only. It collects, stores, and sends no
data.
