# CL 56: add /api/check "why is this domain blocked?" diagnostic

## Description

Add `GET /api/check?domain=NAME`, a read-only endpoint that runs a domain
through the block decision and returns the outcome plus the full suffix walk.
Add a matching "check a domain" box to the dashboard Actions panel. Implements
ROADMAP #18.

## Motivation

A false-positive report ("site X is broken") makes the operator dig through
blocklists to find which entry matched and whether a whitelist entry should
override it. s-hole holds all of that in memory (the suffix walk from CL 30) but
exposed no way to ask it. This endpoint makes the block decision inspectable
without reading Go, reinforcing the "auditable in an afternoon" identity.

## What it does

- **`Store.Explain(domain) Explanation`** (`store.go`): runs the same suffix walk
  as `IsBlocked` under `RLock`, but records every level and returns the reason.
  `Explanation` carries the normalized `Domain`, the `Decision` ("blocked",
  "whitelisted", or "allowed"), the most-specific `MatchedBlock` and
  `MatchedWhitelist` suffixes, and the full `Walk`. Decision semantics mirror
  `IsBlocked`: a whitelist match at any level wins over a block match at any
  level, so a domain can report both a matched block entry and the whitelist
  entry that overrides it (the exact over-broad-entry diagnostic an operator
  needs). `IsBlocked` is untouched: it stays the zero-alloc hot path
  (`TestStore_IsBlocked_ZeroAlloc`), while `Explain` allocates freely because it
  is a diagnostic, not a per-query call.
- **`GET /api/check`** (`api.go`): validates `?domain=` with `blocklist.ValidDomain`
  (400 on missing/invalid), calls `Explain`, and returns the JSON. It never
  enters the DNS handler path, so it bumps no stats counter and writes no
  query-log row by construction. It reveals nothing the UI could not already
  infer from the block set and whitelist, so it does not widen the read surface.
- **Dashboard** (`static/index.html`): a "check a domain" form in the Actions
  panel shows the decision, the matched block entry, any overriding whitelist
  entry, and the full suffix walk (each checked level, with a BLOCK/ALLOW badge
  on the level that matched). The walk itself is rendered, so the block decision
  stays inspectable from the UI, matching the "auditable in an afternoon"
  motivation for the endpoint.

First cut covers the Store's blocklist/whitelist decision only. The handler's
private-PTR short-circuit and future local records (#15) are separate paths and
out of scope here.
