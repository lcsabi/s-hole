# CL 118: The installer health check fails a crash-looping service (b/107)

## Description

`deploy/install-linux.sh` checks the service after `systemctl restart s-hole`
with a new function, `wait_for_stable_service s-hole 5 30`. The check passes
only when the unit is `active/running` for 5 polls in a row (one a second),
within 30 polls. It waits one second before each poll. It fails at once on the `auto-restart` sub-state, on a
`failed` or `inactive` unit, or on a higher `NRestarts` than at the start.

On failure the installer prints the reason and the last 20 journal lines, as
before. It now also stops the service, so that systemd does not restart it
every 5 s. The unit stays enabled. When the `systemd-resolved` stub still holds
port 53, the installer says to re-run with `--free-port-53`. Then it says that
the service is stopped and how to start it again, and exits 1.

The unit file does not change.

## Requirements

The tests cite these as "CL 118 req N".

1. `wait_for_stable_service UNIT STABLE TIMEOUT` reads the unit state with
   `systemctl show` (`ActiveState`, `SubState`, `NRestarts`; the first restart
   count with `-p NRestarts --value`) and waits with `sleep 1` between polls.
2. It returns 0 only when the unit is `active/running` for STABLE polls in a
   row, within TIMEOUT polls.
3. A poll that is not `active/running` resets the count; a slow start that
   then runs passes.
4. It returns 1 at once on the `auto-restart` sub-state, on a `failed` or
   `inactive` unit, or on a higher `NRestarts` than at the start.
5. It returns 1 when the unit does not run for STABLE polls in a row within
   TIMEOUT polls.
6. Each failure prints a reason that names the state to stderr; a pass prints
   nothing to stderr.
7. A bad first `NRestarts` counts as 0; a bad current `NRestarts` does not fail
   the check by itself.
8. The installer calls `wait_for_stable_service s-hole 5 30` after `systemctl
   restart s-hole`. On failure it prints the last journal lines, stops the
   service (it does not disable it), gives the `--free-port-53` hint when the
   resolved stub holds port 53, says how to start the service again, and exits
   1. On success it prints `(service is running)`.
9. No `systemctl is-active` poll remains.

## Motivation

On the Debian 13 VM, an install without `--free-port-53` printed the port-53
warning and then `(service is active)` and the success banners, and exited 0.
s-hole could not bind port 53, and systemd restarted it every 5 s (27 times in
about two minutes). The dashboard did not open, because s-hole exits at the
port-53 bind, before the admin server starts. The CL 66 health check exists
for this case, but it caught it only by chance (it failed the same conflict
in b/058):

- The unit is `Type=simple`, so systemd reports `active` as soon as the process
  starts, before s-hole tries the bind. The check passed at the first `active`.
- After the crash, `Restart=on-failure` keeps the unit in `activating
  (auto-restart)` for `RestartSec=5s`. It never shows `failed`, so the fail
  branch of the check could not run either.

## Design decisions

- **5 s of running, with no restart.** s-hole binds port 53 first at startup
  (`dnsserver.Listen` in `main`, before the blocklist download), so a bind
  failure shows within a second. The installer's config dry run catches a bad
  config before the start. An admin port conflict does not stop s-hole (it
  logs a WARN and serves DNS). So the window covers the failures that can stop
  s-hole at startup. A slow first blocklist download does not fail a good
  install, because s-hole runs while it downloads.
- **The restart counter and the sub-state, not only time.** A crash shows as
  the `auto-restart` sub-state at once, and a restart that happens between two
  polls raises `NRestarts`. Either one fails the check without waiting out the
  window. `NRestarts` exists since systemd 235; Debian 13 has 257 and Raspberry
  Pi OS bookworm has 252.
- **Stop the service on failure, keep it enabled.** The maintainer decided
  this. A unit that restarts every 5 s fills the journal and gives no benefit
  until the cause is fixed. It stays enabled, so `systemctl restart s-hole` or
  a re-run of the installer starts it after the fix. The installer stays
  non-transactional, as CL 66 decided: it does not roll back the files.
- **No DNS gap from the check.** The check only reads the unit state. The DNS
  gap of an upgrade is the existing `systemctl restart`; the check runs while
  the new process starts and does not touch it on success. The installer takes
  about 5 s longer.
- **Keep the warning.** The port-53 preflight still warns and continues
  without `--free-port-53` (CL 66: restarting `systemd-resolved` drops the
  host's DNS for a moment, so the installer does it only on request). The
  health check now turns that case into a clear failure.

## Testing

A separate agent wrote the tests from the requirements, without the diff
(`cmd/s-hole/installer_health_test.go`). They copy `wait_for_stable_service`
and `resolved_stub_on_53` out of the installer and run them with bash under
`set -euo pipefail`, with a fake `systemctl`, `journalctl`, `ss`, and a no-op
`sleep` first on `PATH`. The fake answers each poll from a scripted list of
states and logs every call.

- Pass: a steady run (STABLE 1, 3, 5), a slow start, a non-running poll
  that resets the count, an unchanged non-zero `NRestarts`.
- Fail at the poll that shows the bad state: the b/107 sequence
  (`active/running`, then `activating/auto-restart`), `auto-restart` under
  every active state, `failed` and `inactive`, a higher `NRestarts` (also
  9 to 10, a numeric compare).
- Fail at the timeout and not before: a unit that never runs, and one that
  flaps.
- A bad initial or current `NRestarts` value.
- The installer lines from `systemctl restart s-hole` to the success line,
  with and without the resolved stub: the order of the journal lines, the
  stop, the hint, and the exit code; no `disable`; no `is-active` poll.

The shell tests skip on Windows and on a host without bash. Mutation testing:
27 mutations of the installer, each caught (for example: no `auto-restart`
case, no reset, no `NRestarts` check, the old `is-active` check, `disable`
in place of `stop`, no `exit 1`, a 60 s timeout).

`make check` passes.

Live check on the Debian 13 VM (systemd 257): `uninstall-linux.sh --yes
--purge --restore-resolved` put the resolved stub back on port 53. The new
installer without `--free-port-53` then printed `s-hole is not running
(state: activating/auto-restart)`, the `address already in use` log line,
and the `--free-port-53` hint, and exited 1. Twelve seconds later the unit was
`inactive` and `enabled`, and s-hole had started once. The re-run with
`--free-port-53` passed (`(service is running)`, `NRestarts=0`). A re-run
with the original binary (an upgrade) passed and left the VM as it was
before the check.

Live check on the Raspberry Pi 5 (systemd 252): with a Python program on
UDP port 53, the installer exited 1 with the bind error and did not print
the `--free-port-53` hint (the stub was not the cause). The unit was
`inactive`, `enabled`, `NRestarts=0`. After the port was free,
`systemctl restart s-hole` started it. The Pi was then uninstalled with
`--purge`.
