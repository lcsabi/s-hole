# CL 37 — Cache-hit-rate load-order fix (b/036); case-sensitivity by design (b/037)

## Description

A cloud `/ultrareview` of the branch up to CL 36 returned two `nit` findings,
both in the load-order / case-folding family the previous round already worked
in. One is a genuine fix (b/036); the other is a real but deliberately-unfixed
trade-off (b/037), recorded as such.

## b/036 (ultrareview bug_001) — `Snapshot` reads `cacheHit` after `total`

**What was wrong.** `Counter.Snapshot` read the `cacheHit` counter *after*
`total`. On the cache-hit path the handler calls `RecordQuery` (bumps `total`)
then `RecordCacheHit` (bumps `cacheHit`), so `cacheHit` is a strictly-later
counter — the same precondition as `blocked` (b/021) and `localPTR` (b/033).
Reading it after `total` lets a concurrent cache hit complete between the two
atomic loads, so the observed `hits` can exceed
`forwardable = total − blocked − localPTR` and the CL 25 "Cache Hit Rate"
dashboard card (and `/api/stats` `cache_hit_pct`) can transiently render above
100 %. No crash, no data loss, no divide-by-zero.

This was also a doc-vs-code contradiction: CL 36 rewrote this very docstring to
state the general rule ("every counter incremented after `total` must be read
before `total`") while fixing `localPTR`, but left `cacheHit` on the wrong side.

**Fix.** Read `cacheHit` before `total`. The docstring now names all three
later-counters (`blocked`, `localPTR`, `cacheHit`) as the general invariant.
Added `TestCounter_CacheHitRateNeverExceeds100UnderLoad`, a concurrent regression
modelled on the b/033 test (every query an all-hit, the worst case where
`forwardable == hits`); it passes under `-race`.

## b/037 (ultrareview bug_002) — case-sensitive post-blocklist keys: Won't Fix (by design)

**What was observed.** DNS names are case-insensitive (RFC 1035 §2.3.3) and
miekg/dns preserves the wire-format case in `q.Name`. The blocklist/whitelist
paths fold case (`blocklist.normalize`), so filtering is correct regardless of
case, but the cache key, the in-memory top-domains tally, and the SQLite query
log all key on the raw `q.Name`. So `Google.com.` and `google.com.` produce
distinct cache entries and distinct dashboard rows. The only trigger is a
dns-0x20 case-randomising resolver chained in front of s-hole; a normal LAN of
stub resolvers emits lowercase and never hits it.

**Decision: not changed (deliberate trade-off).** The obvious fix — fold `q.Name`
and reuse it for the cache key and the returned response — would make a cache hit
echo a *different* case than the client sent, which breaks the dns-0x20 spoofing
check in exactly the case-randomising downstream resolvers that are this issue's
only trigger. Today's per-case cache entries always echo the client's exact case.
So the case-sensitive keys buy correct case-echo for 0x20 downstreams at the cost
of a lower cache hit rate and possible dashboard duplicates under that uncommon
topology; on a normal LAN there is no observable duplication, and filtering is
unaffected either way. Recorded in `docs/BUGS.md` as b/037,
**Status: Won't Fix — by design**. A future case-insensitive-cache design would
have to rewrite the response's question/owner names back to the client's case
before sending — more machinery than the nit justifies today.

The decision was confirmed with the maintainer before landing.
