# CL 99: Activity data and application log privacy

## Description

The application log no longer holds query counts, queried names, or client
addresses, and the per-minute graph follows `query_log.mode`:

- The periodic stats line holds the uptime only (b/098).
- A failed reply write and the unresolved-query summary never name a domain.
  A failed reply write goes into a once-a-minute summary.
- An admin API write error is logged without socket addresses (b/099).
- The allowlist audit line names the requester only while `query_log.mode`
  records queries, masked with `query_log.clients`.
- The per-minute graph records nothing under `query_log.mode: "none"`, and
  the dashboard says why.

Review findings: PRIV-01 (b/098), PRIV-03, PRIV-04 (b/099), PRIV-09,
PRIV-10. Target release: v2.0.1.

## Motivation

s-hole sees every DNS query on the LAN. `CLAUDE.md` names "the counts over
time that show activity" as personal data, and says that s-hole does not
write query data by default where it cannot delete it, such as the system
journal or the Docker log.

- **PRIV-01 (b/098).** Every `stats_interval` (5 minutes), the `msg=stats`
  line logged the counters since startup, also under the default
  `query_log.mode: "none"`. The difference between two lines is the number of
  queries in those 5 minutes, so the journal held a timeline of when the
  household was awake and at home, under the journal's own retention.
  `PRIVACY.md` and the uninstaller said that the journal held no query data
  under the defaults.
- **PRIV-03.** Under `query_log.mode: "all"`, a failed reply write logged one
  WARN with the domain, and the unresolved-query summary had `last_domain`.
  The query database holds the same name under retention and purge; the
  journal holds it out of their reach. The per-write WARN was also one line
  per query, which the logging rules avoid.
- **PRIV-04 (b/099).** An admin API write error is a `*net.OpError` whose text
  holds both socket addresses. The export and `writeJSON` logged it
  unchanged, so with `admin.listen` on the LAN the journal recorded the
  address of the device that read the history.
- **PRIV-09.** The per-minute graph (24 hours in memory) counted every query
  under every setting, `"none"` included. It is an activity timeline, and
  every local account can read it through the dashboard.
- **PRIV-10.** The allowlist audit line logged the requester's address under
  every setting. The line links a device to a domain and a time, and it
  bypassed `query_log.clients: "drop"`.

## What it does

- **Stats line** (`internal/stats/stats.go`, `Counter.Log`): one INFO line,
  `msg=stats uptime=...`, with no counts. The counts stay on the dashboard,
  `/api/stats`, and `/metrics`. The `privacy and security warnings in effect`
  line still follows it every `stats_interval`, and the final stats line at
  shutdown is the same uptime-only line.
- **Per-minute graph** (`internal/stats/timeline.go`): `Counter.SetQueryLogMode`
  sets the mode that the timeline follows, with the same rule as the query
  loggers: `"all"` records every query, `"blocked"` records blocked queries
  only (no cache hits or failures, which are allowed queries), and `"none"`,
  an unknown value, or no call records nothing. `Counter.GraphMode` reports
  it. `main` calls `SetQueryLogMode(cfg.QueryLog.Mode)`. The since-start
  counters and the Top lists do not depend on it. A purge still empties the
  timeline.
- **`/api/history`** (`internal/api/api.go`, `handleHistory`): the memory
  series reports `logging` as the timeline's mode instead of always `"all"`.
  Under `"none"` the series is all zeros. The database path is unchanged.
- **Dashboard** (`internal/api/static/index.html`, `drawHistory`): under
  `"none"` the graph panel hides the legend and the canvas and says that the
  graph is off because `query_log.mode` is `"none"`, and how to turn it on.
  Under `"blocked"` the note says "blocked queries only" for the memory series
  too.
- **Failed reply writes** (`internal/dnsserver/edns.go` `send`,
  `failures.go` `replyLog`): a write error is no longer logged at once. It
  goes into `replyLog`, and `RunFailureReport` logs one `replies could not be
  sent` WARN a minute with `replies` (the count), `interval`, `errors` (the
  distinct error texts, at most 8), and a hint. The line names no domain and
  no client. `send`, `writeRcode`, and `writeLocalNXDOMAIN` lost their
  message and domain parameters, and `warnAttrs` is gone.
- **Unresolved-query summary** (`failures.go`, `failureLog`): `last_domain` is
  gone, and `record` takes only the error.
- **Network errors** (`internal/redact/redact.go`, `NetError`): replaces
  `dnsserver.writeErr`. For a `*net.OpError` it keeps the operation and the
  underlying error and removes the addresses. Text that wraps the error is
  kept; if the wrapping text does not quote the `*net.OpError`, only the safe
  part is returned. A `*net.OpError` with no underlying error gives the
  operation only, because its `Error` method would panic. The export (CSV
  and JSON), `writeJSON`, and the DNS failed-reply summary use it.
- **Allowlist audit line** (`api.go`, `auditAttrs`): `allowlist entry added`
  and `allowlist entry removed` keep the domain. They have a `client`
  attribute only while `query_log.mode` is `"blocked"` or `"all"` (from
  `PrivacyInfo.Mode`), masked with `querylog.MaskClientIP` and
  `query_log.clients` (`PrivacyInfo.Clients`): none under `"drop"`, the subnet
  under `"subnet"`, the address under `"full"`. Under `"none"`, an unset mode,
  or another value, the line has no address.
- **Purge report** (`cmd/s-hole/purge.go`): the `system log` step is gone. It
  said, under `query_log.mode: "all"`, that a warning line can name a domain,
  which is no longer true.
- **Rule:** the `CLAUDE.md` privacy rule now says that a slog record from the
  DNS path never names a domain or a client, that no log line carries the
  total query count, and that the allowlist audit line names the requester
  only while the mode records queries, masked with `query_log.clients`.
- **Docs:** PRIVACY (the application log row and paragraph, the graph row,
  the audit exception), SECURITY (the application log bullet), README (the
  advice for a query that times out, the graph and `stats_interval` texts, the

## Design decisions

- **Uptime only in the stats line.** Decided with the maintainer: the counts
  stay on the dashboard and `/metrics`, where s-hole controls them. An opt-in
  setting for counts in the log was the other option; it was not taken. The
  line stays, because the warnings line follows it and an operator can see
  that s-hole is alive.
- **A counted summary for failed writes.** A failed write is a per-query
  event, so it follows the `RunFailureReport` pattern: one line a minute
  with a count. The summary does not say which kind of reply failed
  (sinkhole, cached, forwarded): under `"none"`, "a sinkhole reply failed"
  would say that a blocked query happened in that minute.
- **The graph follows the mode, not a new setting.** Decided with the
  maintainer: the graph is activity data like the Top lists, so the same
  setting governs both. The default `"none"` therefore shows no graph, which
  the CHANGELOG calls out.
- **The zero value records nothing.** A `Counter` that `main` did not
  configure keeps no timeline, so a wiring mistake fails private.
- **Mask the audit line with the existing function.** `querylog.MaskClientIP`
  is the single masking rule, so the audit line can never hold more than a
  query-log row.
- **No address in the audit line under mode `"none"`.** `config.Warnings`
  warns about `query_log.clients` only while the mode records queries,
  because the setting has no other effect. With the masking alone,
  `clients: "full"` and `mode: "none"` would log the admin device's address
  with no warning. Decided with the maintainer: under `"none"` the line has
  no address, so the warning rule stays as it is.
- **No `system log` purge step.** Decided with the maintainer: s-hole writes
  no query data to the application log now, so the step had nothing true to
  report. The uninstaller and `TROUBLESHOOTING.md` say how to clear the
  journal and that s-hole 2.0.0 logged the counts.
- **The helper lives in `redact`.** `redact` hides secrets and personal data
  in what s-hole shows, and both `api` and `dnsserver` already import it.

## Privacy impact

- **Collects:** less. Under the default `query_log.mode: "none"`, s-hole no
  longer keeps per-minute counts in memory. The since-start counters are
  unchanged.
- **Log (system journal, Docker log, Windows Event Log):** no query counts in
  the stats line; no queried domain in any record from the DNS path, under
  every mode; no client address in an admin API write error; the allowlist
  audit line holds the requester's address only while `query_log.mode`
  records queries, masked by `query_log.clients` (none under the defaults). The new `replies could not be sent` line holds a
  count and error texts with no address.
- **Shown:** the dashboard graph is empty under `"none"`, with a note. Under
  `"blocked"` the in-memory graph shows blocked queries only.
- **Kept:** the in-memory graph keeps 24 hours, until a restart or a purge, as
  before. What s-hole wrote to the journal before this change stays there;
  `uninstall-linux.sh` prints the command that clears the journal.
- **Who can read it:** unchanged.
