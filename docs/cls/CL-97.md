# CL 97: DNS answer integrity

## Description

Four changes make the answers that s-hole caches and serves trustworthy and
private:

- The cache key holds the query's CD and DO bits (b/096).
- An upstream reply must match the question that s-hole sent.
- A cached answer lives one day at most.
- A query with RD=0 gets REFUSED.

Review findings: SEC-01 (b/096), SEC-17, SEC-18, and PRIV-05. Target
release: v2.0.1.

## Motivation

- **SEC-01 (b/096).** s-hole sends the client's CD and DO bits upstream (CL
  94), but the cache stored the reply under the name, type, and class only.
  Quad9 and Cloudflare validate DNSSEC, and with CD=1 they return data that
  failed validation. One CD=1 query from any device put that data in the cache
  for every device until the TTL ran out. A validating stub on the LAN sends
  CD=1 in normal use. A DO=1 client got a cached DO=0 reply without RRSIG
  records. Both were reproduced live on v2.0.0 (see Testing).
- **SEC-17.** miekg/dns checks only the message ID of a reply. On the
  plain-DNS fallback, an off-path attacker who guesses the ID and the source
  port could answer with records for another name, and s-hole cached them
  under the name it asked for. The guess is hard, but the check costs nothing.
- **SEC-18.** The cache kept an upstream TTL with no upper limit, so a bad
  answer (for example a b/096 one) or a huge TTL stayed until it expired or
  s-hole restarted.
- **PRIV-05.** A LAN device could send RD=0 ("do not recurse") and read the
  cache without adding to it. The remaining TTL of a cached answer counts
  down, so it told to the second when another device looked the name up. On
  the VM, a lookup returned TTL 163 and an RD=0 probe 7 s later returned 156.

## What it does

- **Cache key** (`internal/cache/cache.go`, `key`, `keyOf`): the key is the
  name, type, and class plus a tag for the CD and DO bits. `Get` and `Set`
  now take the client's query (`Get(req)`, `Set(req, resp)`) and build the
  key from it, so a caller cannot leave the bits out. A query without an OPT
  record counts as DO=0, which is what the upstream gets in that case. AD is
  not in the key: it only asks the upstream to report the AD bit. RD is not
  either, because an RD=0 query no longer reaches the cache.
- **Lifetime cap** (`maxTTL`, `capTTLs`): `Set` stores a copy with every
  record TTL above 86,400 s lowered to 86,400 (Unbound's default
  `cache-max-ttl`), so the entry expires within a day and a cached answer
  does not tell a client to keep it longer than s-hole does. A forwarded
  reply that is not from the cache keeps the upstream's TTLs. There is no
  setting.
- **Reply check** (`internal/dnsserver/upstream.go`, `checkReply`): after a
  UDP, TCP, or DoH exchange, s-hole accepts the reply only when the QR bit is
  set, the opcode is QUERY, and the one question equals the sent one (the
  name in any letter case, the type, and the class). Any other reply is a
  failed attempt for that upstream (`reply does not match the query`), so the
  forwarder tries the next one, the cooldown tracker records the failure, and
  `shole_upstream_transport_failures_total` counts it.
  When a valid UDP reply is truncated and the TCP retry returns a reply that
  does not match, s-hole keeps the truncated UDP reply, as for a failed TCP
  retry. The error text names no query, because it reaches the
  once-a-minute failure summary.
- **RD=0 refused** (`internal/dnsserver/handler.go`, `ServeDNS`): after the
  question-count and opcode checks, a query with RD=0 gets REFUSED through
  `writeRcode`, so the reply has the client's ID and OPT record. It does not
  touch the stats, the cache, the query log, or the upstream, and it is not
  counted in `shole_refused_total`, which counts sources outside the LAN.

## Design decisions

- **The key, not "never cache CD=1".** Not caching a CD=1 reply would fix the
  CD case only. The key change also fixes the DO case, and same-bit queries
  still share an entry. The key grows by three bytes; the cache benchmarks
  show no change in allocations.
- **`Get` and `Set` take the query.** Passing the bits as two booleans would
  let a caller swap or forget them. The cache derives the bits from the
  query, which is the same source that `upstreamQuery` copies them from.
- **Every RD=0 query is refused,** also a blocked name, a local name, or a
  private PTR query. Unbound answers local data to RD=0 and refuses only
  cache reads, but a uniform rule is simpler to check, and a stub resolver
  always sets RD. Decided by the maintainer: refuse with REFUSED, and touch
  no cache, stats, or query log.
- **The cap also lowers the stored TTLs.** Capping only the entry lifetime
  would still tell a client to keep an answer for up to the upstream's TTL
  after the entry expired in s-hole.
- **A mismatched reply is a failed attempt,** not a relayed error. The
  upstream did not answer the question, so the next upstream gets a chance,
  as after a timeout.

## Privacy impact

Less data reaches s-hole's stores and other devices.

- **Collects:** nothing new. An RD=0 query is no longer counted, logged, or
  forwarded.
- **Cache:** an answer stays in memory one day at most. The cache holds one
  entry per CD and DO combination, which is the same data as before.
- **What a device can learn:** a device can no longer read the cache with
  RD=0. A normal lookup still shows from the response time and the remaining
  TTL that another device looked a name up recently, and it adds the name to
  the cache on a miss. `PRIVACY.md` says so in the cache row.
- **Log:** the new failure cause names no query.

## Testing

- `make check` passed.
- **Live run on the Debian 13 VM** (amd64), this branch and v2.0.0 side by
  side on loopback with the default DoH upstreams:

  | Step | This branch | v2.0.0 |
  |---|---|---|
  | `dig dnssec-failed.org` | SERVFAIL | SERVFAIL |
  | `dig +cd dnssec-failed.org` | NOERROR `96.99.227.255` | NOERROR `96.99.227.255` |
  | `dig dnssec-failed.org` again | **SERVFAIL** | NOERROR `96.99.227.255` |
  | `dig isc.org`, then `dig +dnssec isc.org` | **1 RRSIG** | 0 RRSIG |
  | `dig wikipedia.org`, then `dig +norec wikipedia.org` 3 s later | **REFUSED** | NOERROR, TTL 3 s lower |

  Quad9 asked directly: SERVFAIL for `dnssec-failed.org`, 1 RRSIG for
  `isc.org`. After the run, `/metrics` on the branch showed 10 queries and
  `shole_refused_total 0`: the two RD=0 queries were not counted. Every
  s-hole file and process was removed from the VM afterwards.
- **Cache benchmarks:** `BenchmarkCache_Get`, `_Set`, and `_Get_Parallel`
  keep their allocation counts (6, 7, 6 per op); the longer key adds 7 bytes
  per op to `Set` and to `Get_Parallel`. The times are within run-to-run noise
  of master.
- **Cold sub-agent tests:** a `general-purpose` sub-agent with the
  requirements only (no diff) wrote `internal/cache/integrity_test.go` and
  `internal/dnsserver/integrity_test.go` (23 tests).
  - b/096: the full CD/DO matrix in the cache (only equal bits hit), one entry
    and one answer per combination, AD not in the key, no OPT as DO=0, the
    name case still in the key; through the handler, a CD=1 answer is not
    served to a CD=0 client (which gets the upstream's SERVFAIL), and RRSIG
    records reach only DO=1 clients.
  - SEC-17: replies with another name, type, or class, QR clear, opcode
    NOTIFY or UPDATE, no question, or two questions, over UDP and DoH, give
    SERVFAIL and cache nothing; a reply that differs only in the name case is
    accepted; `forwardWith` goes on to the next upstream and charges the
    failure to the bad one; a mismatched TCP retry keeps the truncated UDP
    reply; the failure summary's `causes` never holds the queried name, and
    under modes `none` and `blocked` the application log holds no name.
  - SEC-18: TTL 10^6 is a hit at 86,399 s and a miss at 86,400 s; TTLs above
    the cap are lowered in all three sections, others kept; a reply from the
    cache carries no TTL above 86,400.
  - PRIV-05: RD=0 over UDP and TCP gets REFUSED with the client's ID and
    question for a cached, blocked, uncached, localhost, `.onion`, LAN-only,
    and private PTR name. Negative checks: no stats counter or tally, no
    query-log call, no change to the cache counters or size, no upstream
    packet, no application-log line, and `RefusedQueries` does not move. An
    RD=1 control query in the same setup is counted and logged. The check
    order: outside the LAN, then the question count, then the opcode, then RD.
  - The three removed tests are re-covered with RD=1 queries
    (`TestUpstreamQuery_CopiesEachClientBit`,
    `TestUpstreamQuery_DoHHasIDZeroAndOnlyPadding`, and a new
    `TestServeDNS_CacheKeepsNoOPT` in which a different DO bit causes one more
    upstream query).
  - Mutation testing: 31 of 31 mutations killed (the key without CD, DO, or
    the name case, AD in the key, the cap raised or removed, each part of
    `checkReply` removed, the DoH and TCP checks removed, the name in the
    error text, the RD=0 check removed, moved before the LAN or question
    check, or counted through `refuse`). No test failed against the code.
  - `CGO_ENABLED=1 go test -race -short` on `cache`, `dnsserver`, and
    `cmd/s-hole`: no data races.
