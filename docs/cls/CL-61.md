# CL 61: Robustness and doc fixes from ultrareview (b/046, b/047, b/048)

## Description

Three self-contained items from the same ultrareview round (range
`bc1a6a4..53c0ae2`):

- **b/046** (querylog): `NewDBLogger` accepts a non-positive `db_flush_interval`
  and later panics a background goroutine on `time.NewTicker(d.flushInterval)`.
- **b/047** (config): `S_HOLE_LOCAL_PTR` uses a case-sensitive hand-rolled truthy
  check, so truthy-but-unmatched input silently turns a default-on privacy
  feature off.
- **b/048** (docs): `docs/DESIGN.md` mis-states the stats counter load order and
  reintroduces the b/033 hazard in prose. The code is correct.

## Motivation

**b/046.** `config.ParsedDBFlushInterval` accepts well-formed non-positive
durations such as `"0s"` and `"-5s"`, and `Validate()` never checks the value. A
non-positive interval slips past the startup config-error path. It then crashes
the daemon from a goroutine stack after the SQLite file is already open. Every
other malformed-config value does a clean `log + os.Exit(1)`. This one does not.

**b/047.** `applyEnvOverrides` sets
`c.LocalPTR = v == "1" || v == "true" || v == "yes"`. So `TRUE`, `On`,
`enabled`, and a present-but-empty value all evaluate to false. `LocalPTR`
defaults to true, so an operator who sets the var intending to keep local PTR on
instead flips it off. Local PTR answering stops, and LAN reverse-DNS queries leak
upstream, which is the exact thing the feature prevents, with no warning. The
same pattern is used for `S_HOLE_ENABLE_PPROF`; its default is false, so its
direction is harmless, but the parse is fixed for consistency.

**b/048.** `docs/DESIGN.md` says `Snapshot` loads `blocked` before `total`, then
`localPTR` after `total`, and justifies it with "`total >= localPTR` always
holds". Reading `localPTR` after `total` is exactly the b/033 regression: two
atomics read at different instants can yield `local_ptr / total > 100%`. The code
reads `blocked`, `localPTR`, and `cacheHit` all before `total`, and its comments
agree. The DESIGN sentence contradicts the code. CLAUDE.md treats doc-vs-code
drift as a bug.

## What it does

**b/046.** Reject a non-positive interval at the config gate, and guard the
constructor as defense-in-depth.

Primary fix, in `ParsedDBFlushInterval`:

```go
if d <= 0 {
    return 0, fmt.Errorf("db_flush_interval %q: must be positive", c.DBFlushInterval)
}
```

`main` already calls `ParsedDBFlushInterval` and exits with a clean config error
on failure, so a non-positive value now fails the same way a malformed string
("abc") already does. This keeps one consistent behavior for the field rather than
two (fatal for a bad string, silent for a bad number).

Defense-in-depth, in `NewDBLogger`:

```go
if flushInterval <= 0 {
    return nil, fmt.Errorf("flush interval must be positive, got %s", flushInterval)
}
```

The config gate means `main` never passes a bad value, so the constructor guard
protects only a direct library caller or a test. It ensures the type can never
panic its own goroutine regardless of caller, which is the robust boundary.

**b/047.** Add a shared case-insensitive helper and use it for both boolean env
vars:

```go
// parseBoolEnv reads a boolean env override. It accepts the documented tokens
// (1/true/yes and 0/false/no) case-insensitively and returns def on anything
// else, so an unrecognised value never flips the setting.
func parseBoolEnv(v string, def bool) bool {
    switch strings.ToLower(strings.TrimSpace(v)) {
    case "1", "true", "yes":
        return true
    case "0", "false", "no":
        return false
    default:
        return def
    }
}
```

Then `c.LocalPTR = parseBoolEnv(v, c.LocalPTR)` and
`c.EnablePprof = parseBoolEnv(v, c.EnablePprof)`.

This is not `strconv.ParseBool`. `ParseBool` rejects `yes` and `no`, but
README documents `1`/`true`/`yes` and `0`/`false`/`no` for these vars, so
`ParseBool` would break documented input and create fresh README drift. The
helper accepts exactly the documented tokens, adds case-insensitivity (so `TRUE`,
`Yes`, and `NO` now work), and leaves the default in place on unrecognised input.
It also removes the duplicated inline expression from the two fields.

**b/048.** In the Statistics section, change "then `localPTR` after `total`" to
"then `localPTR` and `cacheHit`, all before `total`", and drop the
"`total >= localPTR` always holds" justification. No code change.

## Design decisions

- **Fail closed at startup, not at first tick.** b/046 moves a runtime crash to a
  startup-time clean error, at the same gate that already rejects a malformed
  duration string, so the field behaves one way for all bad input.
- **Never flip a default-on setting on garbage input.** b/047 leaves the setting
  alone on unrecognised input, so an operator typo cannot silently disable a
  privacy default. It keeps the documented `yes`/`no` tokens working rather than
  narrowing to `strconv.ParseBool`, which would drop them.
- **The doc follows the code.** b/048 is a prose fix; the code and its
  load-order invariant comment are already correct and are not touched.
