# CL 73: client name attribution in the log and dashboard

## Description

Add a `client_names` config map that gives clients friendly display labels in the
recent-query log and the Top Clients panel. A key is an exact IP or a CIDR, and the
value is the label. The label is resolved read-only at display time in the API read
path, against the stored (already masked) client value. Implements ROADMAP #22.

## Motivation

The log and the Top Clients panel showed raw client values. A device name such as
"kids-ipad" is easier to read and act on during false-positive triage than an IP.
The label is a display cosmetic, not a policy input: it changes no filtering
behavior. This is read-only attribution, distinct from the per-client-policies
non-goal.

## What it does

- **Config (`internal/config/config.go`)**: a new `ClientNames map[string]string`
  field (`client_names`), the first map field in the config. `filterClientNames`
  runs in `Load` next to `filterWhitelist` and drops any key that is neither an IP
  nor a CIDR, with a WARN. A bad key never aborts startup, because the map is a
  display cosmetic. There is no `S_HOLE_*` override (env overrides cover only
  scalars). An empty or all-invalid map collapses to nil, which reads as
  "attribution off".
- **Resolver (`internal/api/clientnames.go`)**: a `clientLabeler` built once from
  the map. It holds an exact-key map and a slice of CIDRs sorted by prefix length
  descending. `label(stored)` returns the exact match first, then the most specific
  containing CIDR, else the empty string. An empty stored value (`query_privacy`
  `drop`) and an unparseable value both return the empty string. This is the first
  `net.ParseCIDR` / `IPNet.Contains` use in the repo.
- **API read paths (`internal/api/api.go`)**: `handleStats` attaches the label to
  each Top Clients entry, and `handleQueries` attaches it to each recent-query row.
  The label rides as an adjacent `label` JSON field, so the stored value is never
  overwritten. `statsResponse` redeclares `top_clients` with a local `clientEntry`
  type that carries the label; the outer field shadows the one embedded from
  `stats.Summary` for JSON, so the payload key is unchanged and the `stats` and
  `querylog` packages are untouched. The join runs in the handler, so the future
  #24 export inherits it for free.
- **Dashboard (`internal/api/static/index.html`)**: a shared `clientCell` helper
  renders the label as the primary line with the masked IP as a small subtext line
  beneath it, or the IP alone when no label resolved. The Top Clients column header
  changes from "Client IP" to "Client". The `drop` and `subnet` captions are
  unchanged.

## Interaction with `query_privacy` (CL 72)

The label keys off the value the store holds, which CL 72 masks once at write time.
So the label can never reveal more than the active privacy mode already exposes:

| `query_privacy` | stored client value | what a `client_names` key resolves |
|---|---|---|
| `raw` | full IP (`192.168.1.42`) | an exact-IP or CIDR key (host labels work) |
| `subnet` | network address (`192.168.1.0`) | a CIDR or network-address key only; a host-IP key never resolves, because the host bits are masked before the lookup |
| `drop` | empty | nothing (no client is stored) |

There is no path from a label back to a device the mask hid. This is why CL 72 had
to land first, and why the join reads the stored value and never a pre-mask IP.

## Design decisions

- **Join in the API handlers, not the UI.** One place feeds both the dashboard and
  the future #24 export, so a filtered or exported view stays consistent. The join
  is non-destructive: the masked value stays in `name` / `client_ip`, and the label
  is a new adjacent field.
- **Warn and skip a bad key, not fatal.** This mirrors `filterWhitelist`. A label
  map is a display cosmetic, so a typo must not take DNS down. `query_privacy` and
  `block_mode` stay fatal in `Validate`, because a bad value there changes real
  behavior; a bad label key does not.
- **Exact wins over CIDR; the most specific CIDR wins.** A named host beats its
  segment label, and overlapping CIDRs resolve deterministically to the longest
  prefix (the CIDRs are sorted once at build time, so map iteration order does not
  leak in).
- **No UI hint about the privacy interaction.** The client never receives the
  `client_names` map, so the UI cannot tell the one case worth warning about
  (subnet mode with only host-IP keys, so nothing resolves) from the common
  no-labels-configured case. The guidance belongs where the operator sets the map.
  So the interaction is documented on the `config.yaml` key, in the README row, in
  DESIGN, and here, the way CL 72 put its flat-LAN caveat on the `subnet` config
  comment rather than in the UI.
- **No config-map env override.** Only scalars have `S_HOLE_*` overrides today, and
  a map has no single-string form. The config comment records this.
- **No PTR reverse-lookup in this cut.** Config-only keeps the feature free of any
  lookup cost or new network call. Opportunistic PTR resolution can be a later CL.

## Security considerations

The labels are device-identity PII on the unauthenticated admin API. This opens no
new hole: there is no new endpoint, and the map is parsed once at config load, so
no new input is read from the wire. The label cannot exceed the `query_privacy`
granularity (see the table above), so it cannot re-identify a device the mask hid.
Labels are HTML-escaped in the UI, so an operator-supplied label cannot inject
markup. The mitigation is the existing one: keep `api_listen` on localhost or a
trusted LAN. See SECURITY.md and the DESIGN Security and Privacy sections.

## Testing

- `make check` clean.
- `TestClientLabeler` covers exact-beats-CIDR, most-specific-CIDR-wins, a subnet
  network address matching its `/24`, no match, an empty (drop) value, and an
  unparseable value. `TestClientLabeler_NilAndEmpty` covers the feature-off paths.
- `TestHandleStats_AttachesClientLabels` and `TestHandleQueries_AttachesClientLabels`
  assert the label rides the JSON for a named client and is absent for an unnamed
  one, including the exact-beats-CIDR case end to end.
- Config tests pin that a valid IP and CIDR key are kept and a malformed key is
  dropped, and that `Load` drops the bad key.
- Manual smoke: set `client_names` in a scratch config, drove queries from two
  source IPs, and confirmed the label with the masked-IP subtext in both panels,
  the `label` field in `/api/stats` and `/api/queries`, the `subnet`/`drop`
  behavior, and the WARN on a malformed key.
